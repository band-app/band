# Band

IDE-agnostic agent orchestrator.

## Terms

- A **repo** is one registered repository (or plain folder). `repos.*` in tRPC, `band repos` in the CLI, the `repos` table.
- A **worktree** is one working copy of a repo that an agent works in, identified by `<repo>-<branch>`. `worktrees.*` in tRPC, `band worktrees` in the CLI, `BAND_WORKTREE_ID` in an agent's environment. It is a git worktree for a git repo. The one exception is a plain (non-git) repo's single folder, which keeps the name without being a git worktree. See `docs/glossary.md`.
- A **worker** is a computer connected to the hub that runs worktrees and agents. The hub's own machine is the built-in worker `local`. In code a worker is a `Host` (`Host`, `HostRegistry`, `hostId`, the `hosts` table, `packages/host-*`, `@h-` ids), and users read "worker". The tRPC router is `workers.*` with `hosts.*` kept as an alias, and the CLI is `band workers` with `band hosts` hidden. The old names still work where they were read before: the hub reads `BAND_LOCAL_HOST` and `BAND_DEFAULT_HOST`, a runner hook's `BAND_HOST_REPO_PATH` line is parsed, the provisioning script exports `BAND_HOST_LABELS` beside the new name, runner hooks get `BAND_HOST_ID` beside `BAND_WORKER_ID`, and `band notify` reads `BAND_HOST_ID`. The `band-worker` binary reads only `BAND_WORKER_*`. The `BAND_WORKER_*` names win. See `docs/glossary.md` (Renamed names and their aliases).
- A project was the cross-repo unit (a context repo, a project folder and a coordinator). It was removed in favour of origin links (plan section 15, `docs/glossary.md`). Third-party meanings of the word remain: Claude's `~/.claude/projects` directory, tsserver and Playwright projects.
- `tasks.*` in tRPC is the queue of agent turns. There are no task folders.
- `.band/config.json` keeps its `workspace` key (`workspace.copyFiles`, `workspace.defaultVia`, `workspace.terminal`), because file formats in a user's repo are not renamed.

## Testing Strategy

This repo uses **integration tests** as the primary testing approach. Do not write unit tests with mocked dependencies.

> **When writing, adding, or modifying tests — backend OR frontend — invoke the [`write-integration-test`](.claude/skills/write-integration-test/SKILL.md) skill FIRST.** It is the canonical reference for this repository: real-server boot, Express stubs for external services, no tRPC mocking, no `page.route()` on own routes, Page Object Model for Playwright, locator priority, the universal checklist, and worked examples for both layers. The rules below are the summary; the skill is the source of truth.

### Why Integration Tests

Unit tests with heavy mocking verify that your mocks work, not that your system works. Integration tests exercise the real system through its public interfaces — the same way a client or user would interact with it.

### Rules

- **Never modify production code to make a test pass.** No test-only branches, no exporting internals, no `NODE_ENV` checks in business logic.
- **Black-box testing only.** Test through public interfaces: HTTP endpoints, CLI commands, file system outputs, the rendered DOM (frontend).
- **Real infrastructure.** For databases use test containers, not mocks. For file-based state use temporary directories. Start real servers on random ports.
- **External-only stubs at the network boundary.** Mock only services your process calls *out* to (third-party APIs, agent binaries, GitHub, etc.) using an **Express stub on a random port + env-var override** read at request time. Do NOT use MSW (it misses subprocess-originated traffic, and the env-var indirection is what forces the production code into a testable shape). Do NOT use `page.route()` to intercept your own backend routes from a Playwright test. Do NOT add a tRPC mock layer.
- **Coding agents are stubbed at the ACP boundary.** Chats talk to agents over the Agent Client Protocol; tests set `BAND_TEST_ACP_AGENT` to the scripted stub agent `apps/hub/tests/fixtures/acp-stub-agent.mjs` (scenario, capabilities and request log are env-configured — see its header and `apps/hub/tests/helpers/acp-chat.ts`). Don't mock the ACP SDK or the agent-session service.
- **Test framework: match the package.** `node:test` with `node:assert/strict` is the default for new code. The web app (`apps/web`) and the hub (`apps/hub`) are the exception: they already standardised on **vitest** before this convention was written down (the existing test suites use `describe`/`it`/`expect`/`beforeAll` from `vitest`), so new tests under `apps/hub/tests/` and `apps/web/tests/` should use vitest too rather than mix runners in one package. Don't add test framework dependencies elsewhere unless already present.

See the `write-integration-test` skill (`.claude/skills/write-integration-test/SKILL.md`) for the full doctrine — backend + frontend integration tests, Express-stub patterns, page-object conventions, the universal checklist, and worked examples.

### Frontend tests (web app)

**Frontend tests follow the same integration doctrine as backend tests** — they boot the real server (the production `dist/start-server.mjs` bundle), drive it through a real Chromium via Playwright, and assert on the real rendered DOM / `localStorage` / URL state. Read [`docs/integration-testing.md`](docs/integration-testing.md) and the `write-integration-test` skill (`.claude/skills/write-integration-test/`) before authoring frontend tests.

The non-negotiables for any new frontend test:

- **Boot the real server** with `apps/web/e2e/helpers/server.ts` (`startServer` + `createTmpHome` + `seedState` + `seedSettings`). No in-process React mounting. No shallow renders. No `jsdom` + `renderHook` for behaviour that's user-observable.
- **No tRPC mocking.** No `createTrpcMock`. No `page.route('**/trpc/**', …)`. The existing `apps/web/e2e/helpers/trpc-mock.ts` and the two `worktree-switch-*.spec.ts` files that use it are technical debt to be migrated, not a pattern to copy.
- **Page Object Model.** Locators (`getByRole`, `getByTestId`) live on a page object class under `apps/web/e2e/pages/`. The test body never calls `page.goto()`, `page.getByRole()`, `page.getByTestId()` directly — only methods like `worktreePage.maximizePanel()`.
- **Locator priority for elements your code owns:** `getByRole({ name })` when the ARIA name is system-controlled; otherwise `getByTestId("page__element")` (BEM convention). Banned: CSS selectors, element IDs, `getByText` for localisable copy.
- **External services get Express stubs** under `apps/web/e2e/fixtures/` (or `apps/hub/tests/fixtures/` if shared with backend tests). One stub per env var. Subprocess-originated traffic (`codex`, `claude-code`, `git`) is exactly the case where MSW would silently fail — Express stubs cover it.
- **Production code reads outbound URLs from env vars at request time**, not at module load (`axios.create({ baseURL })` at module top is wrong). Refactoring that pattern is the only allowed production-code change a test may introduce, alongside `data-testid` attributes on JSX.
- **Wait properly.** `expect(locator).toBeVisible()` and `expect.poll(() => …)` auto-retry. Never `page.waitForTimeout(N)`.

Look at `apps/web/e2e/worktree-maximize-state.spec.ts` and `apps/web/e2e/pages/WorktreePage.ts` as the model — they follow the doctrine end-to-end. Run frontend tests with `pnpm --filter @band-app/web test:e2e`; backend integration tests with `pnpm --filter @band-app/server test`.

### Mobile app (apps/mobile)

`apps/mobile` (`@band-app/mobile`) is the Expo iOS app. Its unit tests are `node:test` over the pure modules (`pnpm --filter @band-app/mobile test`), and `pnpm --filter @band-app/mobile typecheck` runs tsc. To verify a mobile change end to end, follow the `mobile-verify` skill (`.claude/skills/mobile-verify/SKILL.md`): it starts a throwaway hub, builds and installs the app on an iOS simulator, runs the Maestro flows in `apps/mobile/e2e/` and saves screenshots for `/am-verify`.

### Running the hub suite locally

`pnpm install`, then `pnpm --filter @band-app/server test`. The `pretest` script builds the web app and the hub bundle first. Use Node 24 (`.nvmrc`); the default Node on some machines is newer and breaks other suites.

- The band CLI: `apps/hub/tests/global-setup.ts` runs `cargo build --manifest-path apps/cli/Cargo.toml` once when no CLI newer than `apps/cli/src`, `skills` and `Cargo.*` exists, after which tests find it under `apps/cli/target`. It needs Rust. Without it the run stops with one message saying how to build the CLI. Set `BAND_CLI_PATH` to use a binary you built yourself.
- pnpm under a temp HOME: `vitest.config.ts` sets `COREPACK_HOME` to the cache of your real HOME (`~/.cache/node/corepack`, or `XDG_CACHE_HOME`) and turns the download prompt off, so `dev-server` and `plain-repos` find pnpm without the network. Run pnpm once (any `pnpm install`) so the cache holds it.
- Network: after the install and the CLI build, the suite needs none. `runner-docker`, `runner-k8s-kind` and `environment-build-docker` skip without Docker or a cluster.
- Teardown: start servers with `startServer` from `tests/helpers/server.ts`, which waits for the server's process group before the test deletes its temp home, and delete the home with `removeTmpHome` (`tests/helpers/tmp-home.ts`), which lists leftover files when the delete fails with ENOTEMPTY.

### Running the suites inside a Band worker

An agent session runs in a Band worker, so its environment carries the worker's identity: `BAND_WORKER_ID`, `BAND_HUB_URL`, `BAND_SERVER_URL`, `BAND_TOKEN`, `BAND_WORKTREE_ID`, `BAND_CHAT_ID`, `BAND_GIT_CREDENTIAL_SOCK`, a credential helper in `GIT_CONFIG_*`, and possibly `GIT_ASKPASS`, `SSH_ASKPASS` and `GH_TOKEN`. A test that starts a hub, a `band-worker` or the CLI used to inherit them. The hub then refused a test worker's bootstrap token with HTTP 401 (the id belonged to the real worker), and the CLI talked to the real hub (`Repo "my-repo" not found`). Tests that fetch fake repos such as `acme/widgets` (`pr-checks`, `subscriptions-github*`, `subscriptions-guards`) also made the real hub log credential requests through the inherited helper. The suites now drop these variables themselves, through `scripts/test-env.mjs` (called by `apps/hub/vitest.config.ts` and `apps/web/playwright.config.ts`) and `command()` in `apps/cli/tests/integration.rs`. A new helper that spawns a process still builds its environment from `process.env`, which is clean by then. Do not add a spawn that reads the real `~/.band`.

- Use Node 24: `export PATH=~/.nvm/versions/node/v24.22.1/bin:$PATH` (the default Node here is newer).
- Hub: `pnpm --filter @band-app/server test`. The full run takes 30+ minutes.
- Web e2e: `pnpm --filter @band-app/web test:e2e`. Specs that start a real `band-worker` failed at the 5 s `expect` default, because the worker runs from TypeScript source through tsx and needs longer on a cold start. `playwright.config.ts` sets `expect.timeout` to 30 s. The `webkit-iphone` project is skipped, with a message, when WebKit is missing. Install it with `pnpm --filter @band-app/web exec playwright install webkit` to run it.
- CLI: `cargo test --manifest-path apps/cli/Cargo.toml`. It needs `apps/hub/dist`, so run `pnpm --filter @band-app/server build` first.
- macOS has no `timeout`. Bound a command with `node scripts/with-timeout.mjs <seconds> <command> [args...]`. It stops the whole process group after the limit and exits 124.
- `pnpm install --ignore-scripts` leaves node-pty's `spawn-helper` non-executable, so terminal tests fail until you run `chmod +x node_modules/node-pty/prebuilds/*/spawn-helper`.

### Where tests run

Pull requests run the Linux jobs only: lint, the hub suite in 3 shards, the web unit and package suites, the web e2e suite, the remote-loopback job, Docker and k8s (kind). No macOS job runs on a pull request. The merge queue and pushes to main run the macOS jobs in full: the CLI integration tests, the whole hub suite with the web unit and package suites (`web-macos`), the iOS simulator build and both desktop e2e jobs. A macOS-only break therefore fails in the queue, before it reaches main. A test that needs macOS to fail is still written as an ordinary test, with no list to join.

The `web-macos` job runs the hub suite with `vitest run` after its own `pnpm build:web`, not `pnpm --filter @band-app/server test`, so the `pretest` build does not repeat. Locally, `pnpm --filter @band-app/server test` still builds first.

### Exceptions

- `apps/web/tests/theme-derive.test.ts` calls the pure functions in `apps/web/src/lib/theme/` (color math, surface derivation, contrast) with colors in and CSS variables out. There is no state to fake, and the 4.5:1 contrast guarantee for arbitrary user colors can only be checked across many inputs at this level. The e2e suite `apps/web/e2e/appearance.spec.ts` covers what the user sees.

- `apps/web/tests/hub-boundary.test.ts` scans the UI sources (`apps/web/src`, `vite.config.ts`) for a value import from the hub. The rule is about what the UI bundle may contain, so there is no server or client surface to drive. It stays a source scan because a lint rule cannot tell `import type` from a value import of the same module.

- `apps/hub/tests/branch-status-poller-ci-throttle.test.ts` drives the exported `getBatchedCIStatuses` directly instead of booting the full server. It covers an internal, non-user-observable throttle: the CI poller must log a persistent `gh` failure only once per worker until it recovers, rather than every ~5–60 s tick. The throttle state has no HTTP/DB projection to assert against, and a hermetic `gh` *success* (needed to observe the recovery reset) would require network + auth, so a full real-server test is impractical. Instead the test exercises the real batching function through its public surface with real `git` + real (offline-failing) `gh` subprocesses — the same direct-function style as `git.test.ts` — which is why `getBatchedCIStatuses` is exported. This is the allowed alternative to a mocked-out fake; do not add a tRPC/`console` mock layer or a `NODE_ENV` test branch to the poller.

- `apps/hub/tests/branch-status-query.test.ts` calls `buildBranchStatusQuery`, `parseBranchStatusResponse` (`plugins/github/src/server/branch-query.ts`) and `statePriority` directly. They are pure functions (response JSON in, statuses out) with no state to fake, and the GitHub responses for each state are recorded fixtures. The path from the poller to the badge is covered end to end by `apps/web/e2e/worktree-pr-badge.spec.ts` and `apps/hub/tests/ci-status-sync.test.ts`.

- `apps/hub/tests/terminal-pool-nudge-resize.test.ts` drives `TerminalPool.nudgeResize` directly (real PTY in a temp dir, no mocks). The nudge is the shrink-and-restore SIGWINCH pair fired after a reconnect replay so a live TUI repaints; its only hermetic observable is the PTY dims themselves — asserting the resulting repaint over the `/terminal` WS would require a SIGWINCH-aware TUI binary in CI. The serialized-replay payload (the user-observable half of that feature) is covered at the WS layer in `terminal-ws.test.ts`.

- `apps/hub/tests/terminal-pool-spawn-dedup.test.ts` drives `TerminalPool.spawn` directly (real PTY in a temp dir, no mocks) instead of booting the full server. It guards the spawn-dedup fix (issue #617): a terminal is created via two concurrent paths — the WebSocket handler's spawn-on-`getSession`-miss and the tRPC `terminal.create` mutation — and without dedup both spawned competing PTYs, so the client attached to one while the server's session map / scrollback pointed at the other. That double-spawn is a genuine nondeterministic race that can't be forced reliably through the full WS + tRPC stack, so the test asserts the pool-level invariant (concurrent + repeated spawns of one terminalId share a single PTY) through the pool's public surface — the same direct-function style as `git.test.ts`. Do not weaken it into a mocked test.

- `apps/hub/tests/terminal-daemon-build-mismatch.test.ts` sets up its scenario through `startDaemonOfBuild` (`tests/helpers/terminal-daemon.ts`), which starts a daemon with another `--build-id` (or from an entry file it then deletes) and puts a shell on it over the daemon's socket protocol, using `launchDaemon` and `DaemonClient` directly. No server of the current build will ever start a shell on such a daemon (issue #652), so there is no server path to create that state. Every assertion still goes through the real server: tRPC, the `/terminal` WebSocket, and the process table.

- `apps/web/tests/browser-guest-retention.test.ts` drives `registerBrowserGuest` + `activateBrowserGuestWorktree` (`apps/web/src/lib/browser-guest-retention.ts`) directly, with no mocks. It covers the hidden-worktree browser guest budget: at most 4 hidden worktrees keep live `<webview>` guests, least recently activated evicted first, the active worktree never evicted. The only consumer, `BrowserPaneComponent`, mounts `<webview>` elements only on the desktop build (`isDesktop`), and the e2e harness boots the web build in plain Chromium, which has no `<webview>`, so a real-server Playwright test cannot observe it. What stays untested is the glue in `BrowserPaneComponent` (register while its `<webview>` exists, remove the element on evict, recreate it at the last URL when the worktree is shown). For the same reason (no Electron, so no `<webview>`, in e2e) the rest of the desktop browser wiring has no automated test either: the `will-attach-webview` handler in `apps/desktop/src/main/webview-security.ts` (its admit/harden rules are pure functions in `browser/guest-policy.ts`, covered by `apps/desktop/tests/guest-policy.test.ts`), the guest navigation guard and session `file:` block in `browser/guest-manager.ts`, page popups opening a Band tab (`WorktreeCenter`), and `apps/web/src/lib/browser-webview-dom-bridge.ts`. Verify changes there against a real desktop build.

- `apps/desktop/tests/chrome-import.test.ts` drives `listChromeProfiles`, `isChromeRunning`, `readChromeCookies` and `readChromeHistory` (`apps/desktop/src/browser/chrome-import/`) directly, against a real temp Chrome user-data dir with a `Local State` file, a `SingletonLock` symlink, a SQLite cookie DB encrypted the way Chrome encrypts on macOS, and a SQLite `History` DB. The Keychain lookup is replaced by passing a known password, because the real one is an interactive macOS dialog. The e2e harness boots the web build, where browser panes and the profile menu don't render and `window.__BAND_DESKTOP__` doesn't exist, and Electron's `session.cookies` needs the Electron runtime, so these stay untested: the import dialog (`ChromeImportDialog.tsx`, including its toggles and the "close Chrome" hint), the pane's profile menu, choosing the `<webview>` partition per tab (`BrowserPanel.tsx`, `profiles.ts`, the offscreen pages in `guest-manager.ts`), and the read-everything-then-write order and cookie writes in `chrome-import/import.ts`. The server side (profiles, repo defaults, the CDP block, `history.import`) is covered through the real server in `apps/hub/tests/browser-profiles.test.ts`, `apps/hub/tests/browser-history-import.test.ts` and `apps/web/e2e/settings-browser-profiles.spec.ts`.

- `apps/desktop/tests/updater.test.ts` covers the auto-update flow through `UpdateController` (`apps/desktop/src/main/updater.ts`), with a fake in place of the `electron-updater` singleton, which cannot load outside Electron. It asserts the statuses the controller broadcasts: silent background checks, the checking, up-to-date and error steps of a menu check, download progress, restart, dismissal, overlapping checks and scheduling. The renderer's `UpdateToast` and `use-app-update.ts`, and the `updater_*` IPC handlers and preload allowlist entries, stay untested: the toast renders only when `window.__BAND_DESKTOP__` exists, and the e2e harness boots the web build without Electron (the same gap `resources.spec.ts` records for `ElectronCard`).

- `apps/desktop/tests/keep-awake.test.ts` calls `KeepAwakeController` and `loadKeepAwake` (`apps/desktop/src/main/services/keep-awake.ts`) directly, with a recording fake in place of Electron's `powerSaveBlocker`, against a temp HOME. The real blocker needs the Electron runtime, which the e2e harness (the web build in plain Chromium) doesn't have, so the `keep_awake_*` IPC handlers, `restore()` in `bootstrap` and the PreventUserIdleSystemSleep assertion stay untested. Verify them against a desktop build with `pmset -g assertions`. `apps/web/e2e/sidebar-footer-usage-menu.spec.ts` covers the absent toggle in a browser.

- `apps/desktop/tests/window-state.test.ts` calls `loadWindowState`, `saveWindowState` and `fitToDisplays` (`apps/desktop/src/main/services/window-state.ts`) directly, against a temp HOME. Applying the state needs an Electron `BrowserWindow` and `screen`, which the e2e harness (the web build in plain Chromium) doesn't have, so the glue in `apps/desktop/src/main/window.ts` stays untested: restoring bounds on create, maximizing and entering full screen after `ready-to-show`, and saving on move, resize, maximize, full screen and close. Verify changes there against a real desktop build.

- `apps/worker/tests/host-checks.test.ts` calls `readLinuxHostSettings`, `hostWarnings` and `formatHostWarnings` (`apps/worker/src/host-checks.ts`) directly against a fake `/proc` in a temp dir. The memory, swap and inotify limit of the machine running the test can't be chosen, and `band-worker doctor` reads the real `/proc`, so the no-swap and low-watch cases are only reachable through the fake. `doctor.test.ts` runs the command and checks that it ends with the block those functions give for the real `/proc`. On a worker with swap and a high watch limit, such as GitHub's runners, that block is empty, so the printing of a non-empty block is checked only on a Linux worker that has low limits.

- `apps/hub/tests/terminal-daemon-launch-retry.test.ts` drives `DaemonTerminalBackend.spawn`/`openConnection` directly (real daemon processes, real PTYs, no mocks) instead of booting the full server. It covers the launch retry-once behavior (a failed launch attempt is worth a second try with a fresh process before falling back to in-process terminals): `createTerminalBackend` (`packages/host-local/src/terminals/create-backend.ts`) hardcodes the daemon entry path with no test override, so there is no way to make the *server's own* daemon launch fail on its first attempt and succeed on its second through the real HTTP/tRPC surface. The daemon `entry` each test points at is a small standalone Node script (not a mock of production code) that decides whether to fail based on an invocation counter recorded in a plain file on disk — a deterministic stand-in for "the first launch attempt happens to fail" that avoids racing a real timing window.

- `apps/hub/tests/terminal-daemon-nodepty-preflight.test.ts`'s first scenario (the daemon exits with `EXIT_NODE_PTY_UNAVAILABLE` and a fresh launch on the same paths recovers) calls `launchDaemon` directly for the same reason as the launch-retry file above: the broken-node-pty scenario is a daemon-startup failure the server's own entry-path resolution can't be pointed at, so it can't be reached through the public HTTP/tRPC surface either. That file's second scenario covers the same failure through a real server and `terminal.create`.

- `BAND_DESKTOP_SECRET_STORE=test` (`apps/desktop/src/main/index.ts`) swaps the Keychain-backed `safeStorage` for a fixed-key store (`createTestSecretStore`). It is a production branch added for testability, beyond TEST-1's carve-outs, because the desktop e2e harness (including the packaged job) has no Keychain to unlock. It is read once at startup from the app's own environment, which an agent cannot set, and the stored file is still ciphertext. `hub-choice.test.ts` and `desktop-hub-picker.spec.ts` rely on it.

- `apps/web/tests/mic-blocked-message.test.ts` calls `micBlockedMessageFor` (`apps/web/src/lib/voice-recorder.ts`) directly. It is a pure function (user agent, touch points and shell in, text out). The e2e harness runs one Chromium user agent, so the iOS, Android and desktop-app texts are reachable only through fixtures. `apps/web/e2e/voice-dictation.spec.ts` covers the notice in the composer.

- `packages/shared/tests/file-icon-name.test.ts`, `apps/mobile/tests/file-icons.test.ts` and `apps/web/tests/file-icon-parity.test.ts` call the pure icon resolvers (`resolveFileIconName`, `resolveFolderIconName`, `agentIconFor`, the mobile SVG lookups) directly. A file name goes in and an icon name or SVG string comes out, so there is no state to fake. The e2e harness does not run the mobile app, and the parity test imports the mobile generated maps by relative path because the point is to check that both apps give the same answer.

- `apps/web/tests/sidebar-drop.test.ts` calls `planParentDrop` (`apps/web/src/dashboard/lib/sidebar-drop.ts`) directly. They are pure functions (a worktree, a target and the list in, a reason, a plan or null out). The refusals (a drop onto itself or a descendant) are checked here so the spec needs only one case of each. The drops themselves are covered by `sidebar-grouping.spec.ts` through the real UI.

- `apps/hub/tests/hub-version-unreleased.test.ts` calls `isUnreleasedVersion` and `updateTargetFor` directly. They are pure functions (a version string in, a boolean or target out). The hub's version is imported from `package.json` at build time, so no server can be started at a stamped nightly version such as `0.1.0-nightly.<date>.<sha>`, and `BAND_HUB_VERSION` accepts only plain MAJOR.MINOR.PATCH. `worker-versions-dev-hub.test.ts` covers the same rule through a real hub at `0.1.0`.

- `BAND_CLI_SYMLINK_PATH` (`symlinkPath()` in `apps/hub/src/server/services/cli-service.ts`) replaces `/usr/local/bin/band` as the install link on POSIX. It is a production setting read on every call, beyond TEST-1's carve-outs, because the CLI check and install tests cannot write `/usr/local/bin`. `apps/hub/tests/cli-check.test.ts` and `apps/web/e2e/cli-banner.spec.ts` rely on it.

- `apps/hub/tests/agent-idle-stop.test.ts` runs with `BAND_AGENT_IDLE_TIMEOUT_MS` set to 2 s. That opt-in idle stop of a chat's agent process (unset by default) is a production change made for testability, beyond TEST-1's `data-testid` and outbound-URL carve-outs. `agent-session-service.ts` reads it each time it arms the timer, and it is a real setting for anyone who wants idle agents stopped. Without it the idle tests could not run in seconds.

- `apps/hub/tests/direct-path.test.ts` runs with `BAND_DIRECT_TOKEN_TTL_MS` set to 3 s. That override of the 10-minute lifetime of a direct token is a production change made for testability, beyond TEST-1's `data-testid` and outbound-URL carve-outs. `direct-access-service.ts` reads it on every token. Without it the expiry case would wait ten minutes.

- `BAND_USAGE_KEYCHAIN=off` (`packages/host-local/src/usage/claude-usage.ts`) skips the macOS Keychain lookup for Claude Code's login, which can open a prompt. It is a production branch added for testability, beyond TEST-1's carve-outs, because the usage tests run on developer Macs whose Keychain holds a real login. It is read on every call from the worker's own environment, which an agent cannot set, and it only removes a credential source.

- `packages/host-local/tests/account-usage-mapping.test.ts` calls `mapClaudeUsage` and `mapCodexUsage` directly with recorded provider responses, including the Fable window spellings (`fable_weekly`, `seven_day_fable`, a `limits[]` entry of kind `weekly_scoped`). They are pure functions (response JSON in, windows out) with no state to fake, and the real endpoints are undocumented, so the variants cannot be provoked through a server. The hub test covers the same mapping end to end for the default spelling.

- `apps/hub/tests/agent-status-states.test.ts` runs with `BAND_AGENT_QUIET_MS` set to 1 s. That override of the 10 s silence after which a turn the agent started itself counts as over is a production change made for testability, beyond TEST-1's `data-testid` and outbound-URL carve-outs. `chat-status-service.ts` reads it each time it arms the timer. ## Git Hooks & CI

This repo has a pre-push hook (`.husky/pre-push`) that runs linting, formatting, and clippy checks. **Never bypass git hooks** — do not use `--no-verify` on `git push` or `git commit`. If a hook fails, fix the underlying issue instead of skipping the check.

**Always run `/review-and-apply` before pushing code.** This invokes the `review-and-apply` skill, which runs Band's CI-style PR review locally against the current branch, auto-applies the resulting fixes, and verifies them with lint/clippy/tests. Do the local review *before* `git push` so the same criteria CI uses catch issues while they're still cheap to fix.

PRs merge through GitHub's merge queue: once a PR is approved and its checks are green, run `gh pr merge <n> --auto --squash`. The queue builds a temporary branch of the PR on top of main and waits for `Lint, Test & Build` and `macOS, Docker & k8s` (the macOS, Docker image and k8s (kind) jobs, where a skip counts as a pass) on that branch before it squash-merges. Pull requests run Linux jobs, Docker and k8s (kind) only: every macOS job has `github.event_name != 'pull_request'`, so the macOS jobs first run in the merge queue, and a macOS-only failure surfaces there. Do not merge by hand, and do not update the branch or rebase to chase main; the queue tests against current main for you.

## Architecture: Hub and UI packages

`apps/hub` (`@band-app/server`) is the API server: tRPC, the raw HTTP and WebSocket handlers, the MCP endpoint, the database, the terminal daemon and its build (`scripts/build-server.sh`). `apps/web` (`@band-app/web`) is the React UI and its Playwright e2e specs. `packages/shared` (`@band-app/shared`) holds the types and small pure helpers both sides import (`chat-events`, `client-state-keys`, `toWorktreeId`, …); it was chosen over keeping them in the hub because the UI imports runtime values from it, and the UI may import only `type { AppRouter }` from `@band-app/server` (`apps/web/tests/hub-boundary.test.ts` enforces it).

The hub serves the built UI from `--ui-dir <path>` or `BAND_UI_DIR`. By default it looks for `apps/web/dist/client` in the worktree, then `client/` beside its bundle (the desktop app, the Docker image and the npm tarball ship it there). In dev, `pnpm dev` runs the hub with Vite mounted as middleware over `apps/web` (`BAND_UI_ROOT` overrides the root), so there is still one port with HMR.

## Architecture: repos by remote URL

A repo on the hub is `{name, remoteUrl, defaultBranch}` (`repos.remote_url`, `repos.remote_key`). Each worker maps the URL to a folder, so the hub needs no checkout. The terms are in `docs/glossary.md` (Repo mapping).

- Identity (`packages/shared/src/remote-url.ts`): `parseRemoteUrl` and `normalizeRemoteUrl` give one key for `git@host:o/r.git`, `ssh://`, `https://` and `git://` spellings, with or without `.git`, with the host lowercased. A local path or `file://` URL keys as `file:///abs/path` (tests use local bare repos as remotes). `stripUrlCredentials` removes web userinfo and any password, and the hub stores and logs only the stripped URL.
- `repos.path` stays a non-null column because SQLite cannot relax it without rebuilding the table that `worktrees` cascades from. `""` means the hub holds no checkout on its own machine (the `local` worker), and every reader of `repo.path` treats it as absent (`sync-service.ts`, `repo-service.ts`, `repo-avatar-service.ts`). A repo with `remoteUrl` and no path is the normal case on a headless hub. `setHostPath` for `local` also sets `repos.path`.
- Workers: `Worker.repos` (`HostRepos`, `packages/worker-api`) has `inspect(path)` (git root, origin URL without credentials, default branch from `origin/HEAD`), `ensure({remoteUrl, defaultBranch})` (the mapped folder while it exists, else `git clone` to `~/band/repos/<owner>/<name>`, or `BAND_REPOS_DIR` / the worker's `--repos-dir`, with one clone shared by concurrent calls), `map`, `unmap`, `list` and `addRoot`. `Worker.fs.browse(path?)` lists directories for the picker. `LocalRepos` (`packages/worker-local/src/repos/worker-repos.ts`) implements them. A worker keeps the table in `<state dir>/repos.json`, the hub's local worker in `<BAND_HOME>/repo-mappings.json`. `worker.info` carries `repoMappings`, and `WorkerLinkService.onConnected` copies them into `repo_hosts`, the hub's cache. Worker methods `repos.*` and `fs.browse` live in `apps/worker/src/methods-basic.ts`. They may look under the worker's home as well as its roots, but `repos.addRoot` is the only way to add a root (saved in `<state dir>/roots.json` and served again at the next start), and the hub calls it only after the UI confirmed (`addRoot: true`).
- Hub: `repos.addFromWorker { hostId, path, addRoot?, name? }` (admin, left out of the MCP endpoint) inspects the folder on the worker, answers PRECONDITION_FAILED with `OUTSIDE_ROOTS:` for a folder outside the roots until `addRoot` is true, creates the repo (or records the mapping on the repo that already has that remote), and maps the folder on the worker. `repos.addByUrl { remoteUrl, defaultBranch?, ... }` resolves the branch with `git ls-remote --symref` on the local worker or an online worker, then the GitHub API when the vault has a git credential for github.com (`BAND_GITHUB_API_URL` overrides the API base). `workers.browse { hostId, path? }` is admin only. A second repo with the same remote key is a 409. `worktrees.create` calls `checkoutOn` (`worktree-service.ts`): a caller's `hostRepoPath` (recorded, and mapped on the worker), else the folder the hub last saw while it still exists on the worker, else `worker.repos.ensure`. A repo with no remote can only run on a worker that holds it. `RunnerService.repoUrls` hands the hooks the stored URL as `BAND_REPO_URLS`.
- Boot (`RepoService.backfillRemotes`, run by `runFirstTimeSetup` after the first sync, which repairs repo kinds first): a repo with a path and no key reads its `origin` from the hub's checkout and stores it, and the folder goes into the local worker's mapping. It is safe on every boot. The migration `repo_remote_url` only adds columns.
- UI: a repo is added from the "+" in the sidebar's Repos panel header (or its empty state), with the form in `AddRepoDialog.tsx`: a worker folder browser (breadcrumbs, a filter, and a preview of the remote URL and branch from `repos.inspectFolder` before anything is added, with a note when the folder has no remote and so stays on that worker), confirmation outside the roots, and By URL showing the default branch `repos.resolveRemote` read. With no worker online it shows a notice linking to Settings > Workers and still offers By URL. The desktop app's native folder button shows only for the hub's local worker when the hub URL is loopback. There is no hub-side path probe (`repos.checkPath` is gone). Settings > Repos is an overview list with no add (`ReposOverview.tsx`: each repo's name, remote and, for a limited repo, its workers; a filter that has focus and opens the first match on Enter; a worker filter) and one page per repo (`RepoSettingsPage.tsx`, laid out with `repo-page-ui.tsx`): label, remote, default branch, workers (`RepoWorkers.tsx`: All workers or Only these, "Add worker…" in a dialog with a filter, a Primary switch and Remove per worker, each change saved at once; Only these on a repo whose checkpoints follow the default asks whether to keep them, because turning them off deletes them; a worker the repo is no longer allowed on stays listed, marked), agent login overrides, environment, checkpoints and auto-continue, the default browser profile, the MCP servers and cronjobs that reach the repo, and Remove once the repo has no worktrees. The repo pages have no Save button. The Add repo dialog keeps `RepoHostsFields.tsx`. Tests: `apps/web/e2e/settings-repos.spec.ts`. CLI: `band repos add --url <url> [--branch]`, `band repos add --from <worker> <path> [--add-root]`, and `band repos list` shows the URL and the clones.
- Tests: `packages/shared/tests/remote-url.test.ts` (node:test), `apps/hub/tests/repos-by-url.test.ts` (real hub, real worker, local bare repos as remotes, runner hook env), `repos-url-migration.test.ts` (seeded pre-change DB, then a real boot), `apps/web/e2e/repos-add-repo.spec.ts` (the Repos panel's Add repo, with a real worker), `repos_add_*` in `apps/cli/tests/integration.rs`.
- Not done yet: GitHub App token source for the clone, pruning a stale `repo_hosts` row when the worker's folder disappears (the next `ensure` repairs it), importing a plain worker folder's existing worktrees, and a placement picker.

## Architecture: hub tokens

The hub authenticates with revocable tokens in the `tokens` table (`services/token-service.ts`, `infra/db/queries/tokens.ts`). Only a SHA-256 of a token is stored, and no log line carries one.

- Device tokens (`bdt_…`) are for UIs and the CLI. The auth middleware and the WebSocket upgrade in `start-server.ts` accept any live device token (not revoked, not expired) as a Bearer header, the `band_token` cookie, a `?token=` link login, or the `band-token.<token>` subprotocol. `settings.tokenSecret` is the device token with id `shared`, re-synced at every boot (a changed secret replaces its hash). `tokens.revoke` refuses it, because the desktop app and the CLI read it from `settings.json`. A device token has an `admin` flag (default false). The shared token is admin, and `tokens.createDevice` / `band tokens create-device --admin` makes others. Every `tokens.*` procedure uses `adminProcedure` (`api/trpc.ts`) and answers 403 to a non-admin token; the token that authenticated a request is resolved in `start-server.ts` (`requestIsAdmin`) for both the HTTP and the WebSocket tRPC handlers, and dev mode, which has no auth, counts as admin. `workers.list` is readable by any device token. Revoking any other token also destroys the sockets it opened. SSE streams are not tracked and last until the client reconnects. Dev mode still runs with no auth.
- Pairing (`device_pairing` kind, `bdp_…`, `TokenService.pairing` and `exchangePairing`). `tokens.createUnpairedDevice` makes a device with a secret nobody holds, and `tokens.pairing { tokenId, regenerate? }` returns a one-time code bound to that device row (`tokens.device_id`). It lasts 15 minutes (`BAND_PAIRING_TTL_MS`, read on every code) and works for one exchange, spent by a guarded SQL update. The pending code is kept sealed in `tokens.sealed` (AES-256-GCM with the vault key, the row id as authenticated data, `services/_utils/vault-crypto.ts`) so Connect details can show the same link again. The seal is cleared when the code is spent, and the hash is what lookups use. `POST /api/pair/exchange {code}` (`api/pairing/handler.ts`, answered before the device-token check) replaces the device's secret with a new one (same id, label and admin flag), closes its sockets, answers `{ token, deviceId, label, admin }` and sets the `band_token` cookie. A refusal is 401 with one message for every reason. `GET /?pair=<code>` serves a small page that makes that POST, so a link preview does not spend the code. `?token=bdt_…` links still work. `tokens.revoke` of a device deletes its row and its pairing codes, and `tokens.list` deletes revoked or expired device rows first. `tokens.pairingAddresses` returns `BAND_PUBLIC_URL`, the hub machine's interfaces (`services/_utils/pairing-addresses.ts`: no loopback, `fe80::/10` or `198.18.0.0/15`, ordered Tailscale, IPv4, IPv6, then bridges by name) and `settings.pairingAddresses`, which `tokens.addPairingAddress | removePairingAddress` edit. A custom address is checked to be an http(s) URL and not probed. The Connect details dialog is `PairingDialog.tsx`, the choices are built by `dashboard/lib/pairing-options.ts`, and the mobile app exchanges codes in `apps/mobile/src/lib/pairing.ts`. Tests: `apps/hub/tests/device-pairing.test.ts`, `apps/web/e2e/settings-devices.spec.ts`, `apps/mobile/tests/pairing.test.ts`.
- Worker tokens: `tokens.issueWorkerBootstrap` creates a `hosts` row (`h-<12 hex>`, offline) and a one-time bootstrap token (`bwb_…`, 1 hour by default, 7 days at most) whose `host_id` is the worker id. `TokenService.authenticate` has the shape `LinkServer` takes: a live session token (`bws_…`) for the hello's workerId passes as `token` or `sessionToken`, anything else must be a bootstrap token for that workerId, which is exchanged once (the update that spends it is guarded in SQL) for a session token. A wrong workerId doesn't spend the token. Refusals reach the worker as one generic reason. `/api/workers/exchange` and `/api/workers/connect` call it (see Architecture: remote workers), and `apps/hub/tests/remote-host.test.ts` covers the exchange and `authenticate` through them. Session tokens aren't rotated yet.
- `tokens.*` is left out of the MCP endpoint (`src/mcp/server.ts`), so an agent can't mint or list tokens, and neither is `workers.*` (nor its alias `hosts.*`). `tokens.current` (any device token) returns the caller's own token id and admin flag, never a secret. The UI is Settings > Devices (`DevicesSettings.tsx`, admin only: Add device shows a sign-in link, QR code and token once; Revoke asks for confirmation on the session's own token) and Settings > Workers (`HostsSettings.tsx`, worker tokens). The CLI is `band tokens list | create-device | revoke`. Tests: `apps/web/e2e/settings-devices.spec.ts`.

## Architecture: voice dictation

The composer's mic sends a recording to the hub, and the hub calls one hub-wide OpenAI-compatible speech-to-text endpoint (guide: `docs/voice-dictation.md`). Band downloads and runs no models.

- Call path. A client posts the clip to `POST /api/voice/transcribe` (`api/voice/handler.ts`, after the device-token check, raw body, `Content-Type` is the clip's MIME type, 25 MB cap) and gets `{ text }` or `{ error: { code, message } }`. `services/voice-service.ts` reads `settings.voice` (`enabled`, `baseUrl`, `model`, `language`, `hostId`, `apiKeyItemId`), reads the key from the vault (`vaultService.getCredential`), and either calls `requestTranscription` itself or, with `hostId` set, calls `host.speech.transcribe` so that worker's worker makes the request from its own network. A server on a Mac's `127.0.0.1` is reached that way from a hub elsewhere. An offline worker answers `host_offline` and nothing falls back to the hub.
- The request builder is `packages/shared/src/speech-transcription.ts`: multipart `file`, `model`, `response_format=json` (mlx-audio defaults to `ndjson`) and optional `language`, a `.webm`/`.m4a` file name and part type read from the clip's first bytes (`detectAudioType`, the request's MIME type only when the bytes match nothing), a 2 minute timeout, no redirects, and a `SpeechError` code per failure. Messages never hold the key (`scrubSecrets` also strips echoes of it from provider bodies). The hub and `LocalHost.speech` both use it.
- Worker. `speech.transcribe` (`apps/worker/src/methods-basic.ts`) takes the clip as `{ base64 }` up to 256 KB and as a link channel above that, and the URL, model and key from the hub on every call. It is not in `DIRECT_PROCEDURES`, so the direct listener answers 404. Only the hub's link reaches it, and it returns a provider failure as a coded result so the code survives the link.
- Access. `voice.status` is readable by every device (a boolean and a reason, no URL). `voice.config` and `voice.test` are admin only, and `settings.update` with `voice` needs an admin token. `voice.*` is left out of the MCP endpoint and the relay, `/api/voice/transcribe` is not a relayed route, and it answers 403 to a request carrying `x-band-chat-id`, `x-band-worktree-id` or `x-band-terminal-id`.
- Clients. Web: `PromptInputMic` (`components/ai-elements/prompt-input-mic.tsx`, `lib/voice-recorder.ts`), shown only when `voice.status` says available and the browser can record (`getUserMedia` needs a secure context). Settings > Voice is `VoiceSettings.tsx`. Mobile: `lib/composer/dictation.ts` (state machine over a recorder port, upload) and `use-dictation.ts` (`expo-audio`). Desktop: the `com.apple.security.device.audio-input` entitlement and `NSMicrophoneUsageDescription` in `electron-builder.yml`. Electron has no permission handler that blocks media.
- Tests: `apps/hub/tests/voice.test.ts` (real hub, real worker, `fixtures/stt-stub.ts`), `apps/worker/tests/speech.test.ts`, `apps/web/e2e/voice-dictation.spec.ts` (Chromium fake microphone), `apps/mobile/tests/dictation.test.ts` (fake recorder port, real HTTP server), `apps/desktop/tests/microphone-config.test.ts` (reads the packaging config, because a TCC prompt cannot be automated).
- Not done yet: streaming partials, Realtime, auto-stop on silence, dictation into terminals, per-device endpoints.

## Architecture: credential vault

The hub stores credentials encrypted in `vault_items` (`services/vault-service.ts`, `infra/db/queries/vault.ts`, `services/_utils/vault-crypto.ts`). Kinds are `api_key`, `env`, `oauth` and `git`. Scope is `global` or `repo:<name>`, and a name is unique per scope.

- Encryption is AES-256-GCM with a random 12-byte nonce per write and the item id as authenticated data, so a blob copied onto another row fails to decrypt. The key is `BAND_VAULT_KEY` (32 bytes as base64 or 64 hex characters) or, with that unset, `<BAND_HOME>/vault.key` (mode 0600, generated on first use). `band vault rotate-key` (`vault.rotateKey`) re-encrypts every item in one transaction and then replaces the key file. It is refused when the key comes from the environment.
- No API returns a secret. `vault.list` shows metadata (kind, scope, OAuth account, scopes, expiry), and `getSecret` and `getAccessToken` are for hub services only (the MCP proxy and environment `secrets` in later steps). Metadata never holds a secret, and no log line or error message does. `vault.*` uses `adminProcedure`, is left out of the MCP endpoint, and is not in `RELAY_PROCEDURES`, so a worker's agent gets 403.
- OAuth (`services/_utils/oauth-client.ts`): `vault.startOAuth` discovers the server (RFC 9728 protected resource metadata, also from a 401's `resource_metadata`, then RFC 8414 or OpenID metadata), registers a public client with RFC 7591 when the server offers it (otherwise the caller supplies `clientId`), and returns a PKCE (S256) authorization URL with the RFC 8707 `resource`. Endpoints must be https, or http on loopback. The redirect URI is `<redirectBase>/api/oauth/callback`, where `redirectBase` is the origin the UI is served from, `BAND_PUBLIC_URL` or the loopback address.
- `GET /api/oauth/callback` is answered before the device-token check, because the browser that returns may not hold the hub's session. The state is the credential: it is random, held as a SHA-256 in memory, compared in constant time against each pending flow, valid for 10 minutes and used once. A response whose `iss` names another issuer is refused. The UI follows a flow with `vault.oauthStatus`.
- A sweep every `BAND_VAULT_REFRESH_POLL_MS` (default 30 s) refreshes a token that expires within `BAND_VAULT_REFRESH_SKEW_MS` (default 2 minutes), and `getAccessToken` refreshes on demand. Concurrent refreshes of one item share one request. A failed refresh stores `refreshError` in the metadata. Deleting an OAuth item revokes its token at the server (RFC 7009, best effort) before removing the row.
- UI: Settings > Credentials (`CredentialsSettings.tsx`). CLI: `band vault list | put | delete | rotate-key` (`put` reads the value from stdin).
- Tests: `apps/hub/tests/vault.test.ts` (real hub, real local OAuth server in `fixtures/oauth-stub.ts`), the vault probes in `remote-relay.test.ts`, `apps/web/e2e/settings-credentials.spec.ts`, `vault_put_list_delete` in `apps/cli/tests/integration.rs`.
- Git credentials (`git` kind) let workers fetch, clone and push private repositories. The item's metadata holds `host`, `pathPattern` (matched against `owner/repo`, `*` within a segment, `**` across segments) and `username` (default `x-access-token`), and the secret is the token. `band vault put <name> --kind git --host github.com --path 'owner/*'`. A worker's git runs a credential helper (`apps/worker/src/git-credentials.ts`: `band-worker git-credential`, wired through `GIT_CONFIG_*` in the worker's own environment, which every git command, agent and terminal inherits) that asks the worker over a Unix socket, and the worker calls `git.credential` on its link (`services/git-credential-service.ts`). On a static worker the helper comes after the machine's own helpers (keychain and so on), so the machine answers first and the hub is the fallback. An ephemeral worker, or one started with `--hub-git-credentials-only` (`BAND_WORKER_HUB_GIT_CREDENTIALS_ONLY=1`), resets the list with an empty `credential.helper` entry first. The hub answers only for a remote of a repository placed on that worker (a repo with a checkout or worktree there, matched against the URL the hub stored in `repos.remote_url` and the remotes of the hub's own checkout, never the worker's, because agents can edit that, or a clone it is about to make) and refuses the rest with an RPC error. `RepoService.backfillRemotesFromWorker` runs on every worker connect and fills an empty `remote_url` from the origin of the repo's folder on that worker, once, never overwriting a URL. A remote with no matching item answers `found: false`. The token goes only in that reply: nothing on the worker's disk or environment, no log line (the log has worker, worker and path). The source is behind `GitTokenSource` (`services/_utils/git-token-source.ts`), so a GitHub App can replace the vault lookup. A runner whose repository has a vault git credential gets `BAND_CLONE_BY_HUB=1`, skips its own clone, and the hub clones through the worker after hello (`RunnerService.cloneOnHost`). The `local`, `ssh`, `docker` and `k8s` hooks honor it, the VM hooks do not. Tests: `apps/hub/tests/git-credentials-no-checkout.test.ts` (a hub with no checkout, repo added from the worker, restart), `apps/hub/tests/git-credentials.test.ts` (real hub, real `local` hook and worker, `fixtures/git-http-auth-stub.ts` for a basic-auth git server), the private clone in `runner-docker.test.ts`, `vault_put_git_credential` in `apps/cli/tests/integration.rs`. Not done yet: a GitHub App token source, and the VM hooks' clone.
- `gh` auth (`services/_utils/hub-gh-auth.ts`, `apps/worker/src/gh-token.ts`, link method `gh.token`). Both images ship `gh`. The hub's own `gh` calls (GitHub poll and webhook services) run with `GH_TOKEN` from the broadest `git` vault item for github.com when the machine has no `gh` login, and a failure with no credential names the missing one. A worker asks `gh.token` at each `acp.spawn` and `pty.spawn` and puts `GH_TOKEN` in that child's environment only (never disk or logs). The hub answers workers a runner started (a `runner_machines` row) and workers with `BAND_WORKER_GH_TOKEN=hub`. Guide: `docs/runner-hooks.md#git-and-github-auth`. Tests: `apps/hub/tests/gh-token-worker.test.ts` (real hub and worker) and the `gh credentials` cases in `subscriptions-github-poll.test.ts`. Not done yet: a dedicated `github` vault kind.
- The MCP proxy that uses these credentials is below (Architecture: MCP proxy). Not done yet: injecting `env` items into environments.

## Architecture: agent logins

An admin gives coding agents credentials from the vault (guide: `docs/agent-logins.md`). A login is `agent_logins { id, agentType, label, kind, vaultItemId }`, and `agent_login_choices { agentType, repo, loginId }` holds the default (`repo` is `""`) and the per-repo overrides. Neither table holds a secret. `AgentLoginService.create` with a `secret` writes a global `api_key` vault item named `agent-login:<id>`, and `remove` deletes that item.

- Kinds (`packages/shared/src/agent-logins.ts`, `AGENT_LOGIN_KINDS`) say which variable carries the secret and which inherited variables of the same agent are removed. The UI and the hub read the same table.
- Resolution at every agent start (`AgentLoginService.resolve`): the chat's `loginId` (stored in the chat's panel state), the repo's override, the agent's default, else nothing. It reads the vault each time, skips a login whose item is gone, and returns `{ env, unsetEnv }`.
- Injection: `withAgentLogin` in `agent-session-service.ts` (`ensureProcess`, `probe`, `oneShot`), `launchForOwner` (the `unsetEnv` field of `ChatLaunchReply`), and `TerminalService.spawn` with `opts.agentType` (set by `AgentLaunchService.launchTui`; the login goes in the backend request and not in `addTerminalToLayout`). `AcpLaunch.unsetEnv` and `SpawnOptions.unsetEnv` carry the removals through `acp.spawn` and `pty.spawn`, and `spawnAgentProcess` and `TerminalPool` apply them before `env` is merged.
- A worker that reports an agent as not logged in still counts as able to run it when a login exists for the agent type (`hasUsableLogin`, used by `usableAgents`, `follow-service.ts` and `workers.list`).
- API: `agentLogins.list | create | update | remove | setDefault | setRepoOverride`, all `adminProcedure`, left out of the MCP endpoint and the relay. `models.listAll` returns each agent's `logins` (id, label, kind label, `isDefault`) for the chat picker, and `chats.update { loginId }` sets the chat's pick (only a login of the chat's agent type, and a chat that switches agent drops it).
- UI: Settings > Agent logins (`AgentLoginsSettings.tsx`), the repo override in Settings > Repos (`RepoLoginOverrides`), and `ChatLoginMenu.tsx` beside the model menu.
- Codex: a login or model provider already configured on the machine still wins over a Codex API key login, because the adapter signs in with the key only when Codex needs authentication. Per-login `CODEX_HOME` is a later phase.
- Trust: restricted workers receive logins too. The relay refuses `agentLogins.*` and `chats.update { loginId }` at every level, and the MCP handler (`apps/hub/src/mcp/server.ts`) refuses `chats.update { loginId }`. `AcpAgentProcess` scrubs login secret values from stderr and error messages (`loginSecretScrubber`).
- Terms: a Claude setup token is a Claude.ai credential. See the warning in `docs/agent-logins.md`.
- Tests: `apps/hub/tests/agent-logins.test.ts`, `agent-logins-worker.test.ts`, `apps/web/e2e/settings-agent-logins.spec.ts`. The ACP stub records variables named in `BAND_TEST_ACP_LOG_ENV` under `env.NAMED`.
- Not done yet: `band agent-logins` in the CLI, logging in on a worker from the UI, the Codex `auth.json` pool, gateway logins and a model API proxy.

## Architecture: MCP proxy

The hub proxies HTTP MCP servers at `/mcp-proxy/<name>` and adds the credential from the vault, so an agent never holds it (plan step 4.2). The request flow is `api/mcp-proxy/handler.ts`, the state is `services/mcp-proxy-service.ts` (`mcp_servers`, `mcp_proxy_tokens`, `mcp_proxy_audit`), and `services/_utils/mcp-policy.ts` and `mcp-sse.ts` hold the pure filter rules and the SSE rewriting.

- Servers: `mcp.list | add | update | remove` (admin only, `band mcp list | add | remove`). A server has a `url` (https, or http on loopback, no credentials in it), an optional `vaultItemId` (an `api_key` or `oauth` item), `allowTools` (null means every tool), `readOnly`, `readOnlyTools` and `enabled`. An API key goes out as `<headerName>: <headerPrefix><key>` (default `Authorization: Bearer <key>`), an OAuth access token always as `Authorization: Bearer`. Only streamable HTTP upstreams work over a URL. Legacy SSE transport is not proxied.
- Session tokens: `mcpProxyService.issueSessionToken(sessionId, servers, ttlMs)` (also `mcp.issueSessionToken`, admin only, for the agent launcher in step 4.3) returns an `mcp_` token once. Only its SHA-256 is stored. A token names the servers it may use, expires (1 hour by default, 24 at most) and is revoked when `agent-session-ended` or `chat-removed` fires for its session id (`mcp.revokeSession` does it by hand). A missing, unknown, expired or revoked token gets 401, a token that does not name the server gets 403, a disabled server 404. The route is answered before the device-token check, and the hub's own tokens are no credential for it.
- Filters: `tools/list` answers keep only tools in `allowTools` and, with `readOnly`, tools named in `readOnlyTools` or annotated `readOnlyHint`. A `tools/call` for any other tool is answered by the hub with JSON-RPC error -32602 and never reaches the upstream. A read-only call for a tool the proxy has not seen in a `tools/list` makes the proxy list the upstream's tools first, and an unknown tool is refused. A batch with a refused call is answered whole, with one error per request. `resources/*` and `prompts/*` pass through unfiltered.
- Streaming: a request with no `tools/list` or `tools/call` in it streams through unbuffered. When one is in flight, a JSON answer is read whole (up to 8 MiB) and an SSE answer is parsed one event at a time, so progress notifications reach the client while the call runs. Request bodies are capped at 4 MiB, and the client leaving aborts the upstream request.
- Credentials: the client's `Authorization` and every other header except `content-type`, `accept`, `mcp-protocol-version`, `mcp-session-id` and `last-event-id` stay on the hub. An upstream 401 on an OAuth server makes the hub refresh the token (`vaultService.getCredential(id, true)`) and retry once. A second 401, or a refresh that fails, answers the client 502, never 401, so it is not mistaken for a bad proxy token. Redirects from the upstream are refused.
- Audit: one `mcp_proxy_audit` row per `tools/call` (server, tool, session, ok, and `not-allowed`, `upstream-error`, `no-response` or `upstream-<status>` as the error), kept 30 days, read with `mcp.audit`. Arguments and results are never stored, and no token or credential is logged.
- Workers: an agent on a worker calls `<relay>/mcp-proxy/<name>` with `Authorization: Bearer <mcp token>` and its relay token in the `band_token` cookie or `X-Band-Relay-Token`. On this route the worker relay reads its credential from there, forwards the `Authorization` header, and the hub replays the call without its own token. The relay lets any `/mcp-proxy/<name>` call from a worktree on that worker through, and the proxy's token check decides the rest. `mcp.*` is left out of the MCP endpoint and the relay's procedure list.
- Tests: `apps/hub/tests/mcp-proxy.test.ts` (real hub, the SDK's MCP client, real SDK MCP servers in `fixtures/mcp-stub.ts`, the vault's OAuth stub), `mcp-proxy-relay.test.ts` (real worker), `mcp_add_list_remove` in `apps/cli/tests/integration.rs`.
- Stdio servers (step 4.4, `api/mcp-proxy/stdio.ts`, `services/mcp-stdio-service.ts`). `mcp.add` with `transport: "stdio"`, `hostId`, `command`, `args`, `env` and `cwd` (admin only, like every `mcp.*` call) makes a server that runs as a process on that worker. The command is an executable, not a shell line, and only an admin sets it. `env` entries hold a literal value or a vault item id (`api_key` or `env` kind). The hub reads the vault plaintext when it opens a process and sends it inside `mcp.stdio.open`, and the worker hands it to the process. No log line, audit row or file holds it, and the worker drops the process's stderr for the same reason. The route and the session tokens are the same as for HTTP servers. The `initialize` POST starts one process and answers with an `Mcp-Session-Id`. A later request must carry that id with the token that started it, or it gets 404. `DELETE`, a revoked token (`mcp.revokeSession`, `agent-session-ended`), a changed or removed server, 15 idle minutes (`BAND_MCP_STDIO_IDLE_MS`, also enforced on the worker) and a lost link all kill the process. The worker method `mcp.stdio.open` (`apps/worker/src/methods-streams.ts`, `HostMcp` in `packages/host-api`) opens one link channel for the process, checks `cwd` against the worker's roots, and kills the process when the hub resets the channel. A worker that is offline or unknown answers 503 with its id. Filters and audit run through `api/mcp-proxy/filter.ts`, shared with the HTTP path. Each POST answers with one JSON body. A server message that answers no request goes to the `GET` stream if one is open, and is dropped otherwise. A call that takes longer than `BAND_MCP_STDIO_CALL_TIMEOUT_MS` (10 minutes) answers 504. Test: `apps/hub/tests/mcp-stdio-relay.test.ts` (real worker, `fixtures/mcp-stdio-server.mjs`).
- Sessions (step 4.3): `agent-session-service.ts` (`sessionMcpServers`) puts the servers a chat may use in `mcpServers` of `session/new`, `session/load` and `session/resume`, as `http` entries `<hub URL>/mcp-proxy/<name>` with `Authorization: Bearer <mcp token>`. A server reaches a session when it is enabled and the session's repo is in `scopeRepos` and its worker id in `scopeHosts` (null means no limit; set with `mcp.add` / `mcp.update`, no CLI flag yet). The token's session id is the chat id, each attach revokes the chat's older tokens and issues a new one, and the agent process exiting also revokes them. An agent on a worker gets the relay URL and an extra `X-Band-Relay-Token` header. An agent whose `initialize` lacks `mcpCapabilities.http` gets no entries and the hub logs "agent does not support HTTP MCP servers". Tests: `apps/hub/tests/mcp-session-servers.test.ts` and `mcp-session-servers-relay.test.ts` (the stub agent's `mcpCall` step calls a tool through the entry Band passed).
- Settings > MCP (step 4.5, `McpSettings.tsx`): list with status, add and edit form, tool allowlist, read-only, scope (all, repos or workers) and a per-server audit log. `mcp.test` (admin) connects to an upstream with the SDK client and returns every tool with its `readOnlyHint`, ignoring the allowlist, for a saved server (`name`) or an unsaved form (`url` and credential fields). The status on each row is the same call. `mcp.audit` takes `offset` and returns `hasMore`. The form also takes a stdio server (worker, command, args, cwd, env with vault references). A non-admin token sees only a notice. `mcp.test` also takes a stdio form (worker, command, args, env, cwd) or a saved stdio server: it opens the process through `mcpStdioService`, runs `initialize` and `tools/list`, and kills it. A stdio row's status is whether its worker is online, because a status check never starts a process. Tests: `apps/hub/tests/mcp-settings-api.test.ts`, `apps/web/e2e/settings-mcp.spec.ts`, `apps/web/e2e/settings-mcp-stdio.spec.ts` (real worker).
- Not done yet: the CLI flags for a stdio server, and streaming a stdio server's progress notifications into the POST reply.

## Architecture: repo workers

A repo can be limited to workers and a branch lives on one worker (guide: `docs/repo-hosts.md`). `repos.allowed_host_ids` (JSON worker ids, null for all) and `repos.primary_host_id` are written only by `RepoQueries.setHostPolicy` (`saveAll` keeps what the database holds). `repos.update { name, allowedHostIds, primaryHostId }` (admin) and `band repos set --workers --primary` edit them, and `repos.addFromWorker` and `repos.addByUrl` take the same fields. A repo added from a worker starts with `[that worker]` and that primary, one added by URL with all workers, and `checkoutOn` sets the primary to the first worker that clones it.

- Enforcement is hard and central. `assertHostAllowed` (`services/_utils/repo-host-policy.ts`) runs in `WorktreeService.create` and `checkoutOn` and throws `RepoHostNotAllowedError` ("<repo> is only available on <names>", 412). `PlacementService.placeWorktree` places only among allowed workers and never queues a runner request for an allowed-workers repo. The shared helpers are in `packages/shared/src/repo-workers.ts`.
- `WorktreeService.create` refuses a branch that has a listed worktree on another worker with `BranchOnOtherHostError` ("<branch> is already on <worker>", 409). `api/trpc.ts` puts `existingWorktreeId` and `existingHostId` in the error's `data`.
- `repos.list` returns `allowedHostIds`, the effective `primaryHostId`, `hostNotAllowed` on a worktree whose worker is no longer allowed, and leaves out the default-branch worktree of every worker but the primary (`listedWorktrees`). Hidden rows stay in the database and resolve by id.
- Tests: `apps/hub/tests/repo-allowed-hosts.test.ts`, `repo-primary-host.test.ts`, `apps/web/e2e/repo-allowed-hosts.spec.ts`, `repos_set_hosts_*` in `apps/cli/tests/integration.rs`. `seedState` takes `hosts`, `hostId` on a worktree and the repo policy. `worktree-two-hosts.spec.ts` seeds B's copy of the branch with `seedHostWorktree`, because Band no longer creates it.

## Architecture: worker trust levels

Each worker has a trust level, `restricted`, `standard` or `admin` (`workers.trust`, `packages/shared/src/host-trust.ts`, `services/host-trust-service.ts`). `workers.setTrust` and `workers.audit` are admin-device-token procedures (`band workers trust | audit`, the selector and "Cross-worker activity" in Settings > Workers). The relay reads the level on every call (`ScopeLookups.trustOf`, absent means `standard`), so a lowered level applies at once. Guide: `docs/agent-host-access.md#trust-levels`.

- `relay-scope.ts` keeps the allowlist style: `RESTRICTED_PROCEDURES` is `RELAY_PROCEDURES` without worktree creation and removal, `repos.*` writes, cronjobs and `workers.list`; `standard` is `RELAY_PROCEDURES`; `admin` adds `ADMIN_EXTRA_PROCEDURES` (`settings.get`, `settings.update`, the latter limited to `AGENT_SETTABLE_SETTINGS` and neither over `/mcp`). `NEVER_FOR_AGENTS` (`tokens.*`, `vault.*`, `workers.setTrust`, `workers.audit`) is refused first at every level. `checkNamed` lets an admin worker name worktrees, chats, terminals and browsers on any worker that exists (a `cwd` stays on the caller's worker); the other scope checks are unchanged. A refusal on a restricted worker ends with "(this worker's trust level is restricted)". `checkRelayRequest` returns the level it used and the `audit` entries (`RelayAudit`) of an allowed call, which `WorkerRelayService` records and uses to shape the call (`pinWorktreeHost` keeps an admin's `hostId` on `worktrees.remove` too) and the reply (`repos.list` and `workers.list` stay unredacted for admin, `settings.get` is cut to `AGENT_SETTABLE_SETTINGS`).
- `crossHostRefusal` (`cross-host-policy.ts`) answers for the built-in `band` MCP tool as well: a restricted worker may not create worktrees at all (`restrictedHostRefusal`), an admin worker skips the `agents.crossHostWorktrees` setting, but no level may target `local`, and `checkNamed`, `worktrees.create` and `remove`, cronjob keys, origins and subscriptions refuse the hub's own machine (`HUB_HOST_ID`). Static-worker, online and repo-allowed-worker rules still hold.
- Defaults: the migration `host_trust` makes every existing worker `standard` and leaves the column null for new rows. A null level is `restricted` for a worker whose mode is ephemeral and `standard` otherwise (`defaultHostTrust`), and `RunnerService` stores `restricted` on the workers it starts. `workers.list` returns the effective `trust`. An unknown worker is `restricted`.
- Tests: `apps/hub/tests/host-trust-levels.test.ts` (real hub, two real workers, a shell on A), `host-trust-migration.test.ts`, `apps/web/e2e/settings-hosts-trust.spec.ts`.

## Architecture: worktree ids

A worktree id names its worker: `<repo>-<branch>` on the hub's own worker (`local`) and `<repo>-<branch>@<hostId>` on any other, so the same repo and branch on two workers would be two worktrees. Band creates only one of them now (see Architecture: repo workers), but rows from before that rule keep their ids. `toWorktreeId(repo, branch, hostId)` in `packages/shared/src/worktree-id.ts` is the only function that makes one (it returns the branded `WorktreeId`, and `hostId` has no default). `scripts/check-worktree-ids.sh` runs in `pnpm lint` and CI and fails on an id built by hand in production code. `WORKTREE_ID_MATCH` in `infra/db/queries/worktrees.ts` is the SQL twin. `worktrees.remove | setPinned | gitPull | gitPush` take an optional `hostId` to tell two same-named worktrees apart (the worker relay writes the caller's worker into `worktrees.remove`). The migration `worktree_host_ids` rewrites stored ids; where several workers shared one old id, state that names no worker goes to the lowest worker id. Not migrated: `<BAND_HOME>/sleep/<id>/`, `workspace-prompts/<id>.json`, a worker's WIP files, the ids inside `runner_snapshots.worktree_ids`, open `host_requests` (keyed by the worker-less id until a worker is chosen), and the chats and terminals of a remote worktree whose old id equals a local worktree's (they stay with the local one).

- A worktree whose folder is gone from a reachable worker gets `missing: true` in `repos.list` (the Missing badge and Remove in `WorktreeCard`). `repos.list` and `syncWorktrees` hand such rows to `worktreeService.pruneMissing`, which removes the record and runs `git worktree prune`, unless a chat there has a running task, a live agent or queued messages. `worktrees.remove` of a worktree whose folder or branch is already gone does the same and deletes no file and no branch.
- `BAND_LOCAL_WORKER=off`: `runFirstTimeSetup` calls `forgetLocalWorktrees` first, which deletes the local-worker worktree rows and the hub checkout path of git repos (files stay; plain folders stay). `repos.add` by path, `backfillRemotes`, the local part of `syncWorktrees` and `repos.list`, and `checkoutOn`'s clone all refuse or skip the hub's machine. The Worker grouping in the sidebar has no "This hub" group when `workers.list` has no `local` row. Tests: `apps/hub/tests/worktree-host-identity.test.ts`, `worktree-host-ids-migration.test.ts`.

## Architecture: remote workers

A worker (`apps/worker`, `band-worker`) is a machine the hub runs worktrees on. It dials the hub, so it needs no inbound port.

- Registering: Settings > Workers (or `tokens.issueWorkerBootstrap`) creates a `hosts` row and a one-time bootstrap token. `band-worker --hub <url> --token <bootstrap>` calls `POST /api/workers/exchange` (answered before the device-token check, in `services/worker-link-service.ts`). The hub binds the token to the worker id it was issued for, answers `{ sessionToken, workerId }`, and the worker adopts that id. A second exchange of the same token gets 401, with one generic message for every reason. The worker then opens `GET /api/workers/connect`, a WebSocket whose `hello` carries the session token. `LinkServer` authenticates it with `TokenService.authenticate`, which accepts worker tokens only. A device token cannot connect as a worker, and a worker session token fails the device-token check on every other endpoint.
- Revoking a worker's session token calls `LinkServer.drop`, which closes its socket and channels. The worker's redial then fails the hello, and it exits with code 1.
- `WorkerLinkService` keeps the `hosts` row current: `online` with the worker's `info` and build on connect, `offline` when the socket closes or the session expires, `lost` after three missed heartbeats. Each change goes out as a `host-status-changed` status event, which Settings > Workers follows. At boot every non-local `hosts` row becomes a `RemoteHost` in `HostRegistry`, and a hub restart sets `online` rows to `offline` until the worker redials.
- `RemoteHost` (`packages/host-remote`) implements `Host` over the link session, so a service that calls `worktree.host.*` needs no change. A call to an offline worker rejects with `HostOfflineError`. `TerminalService` skips an unreachable worker when it looks a terminal up, so local terminals keep working.
- A worktree on a remote worker has `worktrees.host_id` set. `worktrees.create` takes `hostId` and, the first time a repo is used on that worker, `hostRepoPath` (the repository on the worker, kept in `repo_hosts`). The worktree goes under `<first worker root>/.band-worktrees/<repo>/<branch>`. `syncWorktrees` and `repos.list` pass remote worktrees through, since this machine's `git worktree list` cannot see them, and `RepoQueries.saveAll` keeps the `repo_hosts` rows of remote workers.
- Files the hub keeps for a worktree live on its worker. A worker reports `dirs` in `host.info` (`<first root>/.band-uploads` and `.band-shared`). `saveWorktreeUploads` (`services/_utils/upload-utils.ts`) writes a remote worktree's chat uploads to `<uploads>/<worktreeId>/` through `host.fs`, and the hub keeps no copy. The chat renders them from `/api/uploads/<worktreeId>/<name>`, which streams from the worker. The shared dir (`services/_utils/shared-dir.ts`) is `<shared>/<worktreeId>/<chatId>/` on the worker, one folder per chat so two chats in a worktree never see each other's files. It is listed with `host.fs.list` after each completed tool call and served from `/api/shared/<worktreeId>/<chatId>/<name>`. The older `/api/shared/<worktreeId>/<name>` form still serves files in the old per-worktree folder. The web card opens the file in a center `file` tab whose path is `shared:<chatId>/<name>` (`SharedFileLeaf.tsx`). ACP `additionalDirectories` name these worker paths.
- Explorer download. `GET /api/worktree-file/<worktreeId>/<path>?download=1` (device token, after the auth check) serves one file as `Content-Disposition: attachment` (`attachmentDisposition`, RFC 6266 `filename*`) with `nosniff`, streamed through `worktree.host.fs.readStream`, so a remote worktree's bytes come from its worker and the stream is destroyed when the client leaves. The UI's Download item (`FileBrowser.tsx`, `adapter.downloadWorktreeFile`) fetches with the Bearer header or cookie and saves a Blob, so no token goes in a URL and it works from `app://`. The worker relay lists no such route, so an agent gets 403. Tests: `worktree-file-serve.test.ts`, `worktree-file-serve-remote.test.ts`, `apps/web/e2e/explorer-download.spec.ts`. The web viewer's `VideoPreview` (`.mp4 .m4v .mov .webm .ogv`) and the Expo app's `VideoPlayer` (`components/files/video-view.tsx`, `expo-video`, Bearer header) play it; images already preview in both. The Expo player needs a native rebuild for `expo-video`. Not done yet: folders (zip), and streaming to disk instead of a Blob for very large downloads.
- Worker relay (`apps/worker/src/relay.ts`, `services/worker-relay-service.ts`, `services/relay-scope.ts`). `host.relay.issue({ worktreeId, chatId })` sends `relay.register` with a hub-generated `brt_` token, and the worker answers with its relay URL (`http://127.0.0.1:<port>`, loopback only, started on the first registration). The hub puts `BAND_SERVER_URL` and `BAND_TOKEN` in the env of the agent (`ensureProcess`) and of each terminal on a remote worker (`TerminalService.spawn`, never saved in the layout), and revokes the token when the process exits. A call to the relay needs that token as a Bearer header or `band_token` cookie, or it gets 401. The worker forwards it as one `relay.http` request on its link, and the hub checks it (`checkRelayRequest`), replays it against its own HTTP server on loopback, and streams the answer down a channel. The worker's session token and the hub's tokens never reach an agent. Agents may call only the procedures in `RELAY_PROCEDURES` (`services/relay-scope.ts`, an exact list, so a procedure added to a router later stays refused until it is listed), `/mcp` and the chat routes. Every call must name a worktree (or a chat, a browser tab, a terminal or a `cwd`) on that worker's worker, and `chats.create` / `browsers.create` refuse a chosen id that already belongs to another worktree. `repos.list` is allowed too, and the hub cuts its answer down to that worker's worktrees (`filterReposReply`). Cronjobs are allowed, keyed by a worktree on the worker (a create names it in `worktreeId`, and an update that moves the job to another worktree is refused). `worktrees.create` from a worker always creates on that worker (the relay writes `hostId` into the body and refuses another), and `worktrees.remove` is limited to worktrees on it. `settings` stays refused. Repo management is allowed (`repos.add`, `addFromWorker`, `addByUrl`, `inspectFolder`, `resolveRemote`, `gitInit`, `promoteToGit`, `update`, `reorder`, `remove`): these name a repo or a worker instead of a worktree, so `checkRepoCall` skips the worktree check, and the hub replays them with its own admin token. The one limit is a repo's allowed workers (`repoHostRefusal` in `cross-host-policy.ts`): a call on a repo limited to workers that exclude the caller's gets 403 naming the repo, and `addFromWorker` refuses an `allowedHostIds` that excludes the folder's `hostId`. `addFromWorker` may name any worker but is refused with `addRoot` (widening a worker's roots needs a person). A re-add found only by the folder's remote is checked against the folder's worker by `assertHostAllowed`, not against the caller's. `apps/hub/tests/helpers/relay-cli-commands.ts` lists the CLI commands the skills name, and `relay-cli-skills-drift.test.ts` fails when a skill names one that is neither tested through the relay nor listed as refused with a reason. A refused tRPC call answers in tRPC's error shape (code FORBIDDEN, message naming the procedure), so the CLI prints it. Anything else, or a worktree on another worker, gets 403. WebSocket routes are not relayed, and a request body is capped at 512 KiB. Hooks work through it unchanged: `band notify` reads `BAND_SERVER_URL` and `BAND_TOKEN` from the agent's env. Tests: `apps/hub/tests/remote-relay.test.ts`.
- `worktrees.remove` of a worktree on an offline worker removes it from the hub at once and records the checkout in `pending_removals`. `WorktreeService.finishPendingRemovals` deletes it when the worker connects. `system.listWorktrees` also lists each remote worker's worktrees (with `hostId`) and `duBytes` runs on that worker. `formatFile` reads a remote worktree's JSON Prettier config through `host.fs` and ignores its `plugins`. `killAllLspServers` stops them on every worker.
- What a worker offers. `workers.list` returns `agents`, `roots`, `capabilities` and `home` for each worker, filled from the worker's hello and `host.info` (the local worker is described live). `models.availability` says per worker whether each configured agent can start, and `models.refresh` takes a `hostId`: without one it uses the local worker when it can start the agent, else the first online worker that can, so a Docker hub with no agents refreshes on a worker. Settings > Agents has a worker picker per agent. A `hostRepoPath` for a remote worker may start with `~` (the worker's `home`) and must otherwise be absolute. An error for a missing directory or a path outside the roots names the roots, and the New Worktree dialog lists them under the field.
- `workers.remove` (admin) deletes a worker that is offline with no worktrees, after revoking its live tokens. The local worker, an online or lost worker and a worker with worktrees are refused. UI: Remove in Settings > Workers. CLI: `band workers remove <id>`.
- The `band` CLI on a worker. A worker carries its own CLI and the hub serves none (`apps/worker/src/cli.ts`, `resolveCliBinary`). The lookup order is `BAND_CLI_PATH`, the optional dependency `@band-app/worker-cli-<platform>-<arch>` (darwin-arm64, linux-x64, linux-arm64, published by the release workflow before the worker and pinned by `apps/worker/scripts/cli-packages.mjs`), `Resources/binaries/band` beside the desktop app's bundled worker, then `apps/cli/target/{release,debug}/band` in a checkout. At start the worker points `<state dir>/bin/band` (a symlink, replaced by rename) at that binary, runs `band skills install` with it, and puts `<state dir>/bin` first on PATH for every agent (`acp.spawn`) and terminal (`pty.spawn`) it starts, so a shell or agent that outlives an update still finds `band` after the update moves the CLI package. On Windows, or when the link cannot be made, the CLI's own folder goes on PATH. With none found it logs one line naming the package and runs without `band`. The `cli.fetch` link method is gone, so an older worker's call gets method-not-found, which it logs and survives, keeping any copy it cached. The worker image builds the CLI in a cargo stage and sets `BAND_CLI_PATH`. Tests: `apps/hub/tests/remote-relay.test.ts`.
- Stable agent environment (`apps/worker/tests/stable-agent-env.test.ts`). What an agent or shell holds in its environment must work after a worker restart. The git credential socket is `<state dir>/run/git-credential.sock` (0600 in a 0700 dir; a hashed name under `/tmp/band-<uid>/` when the path is too long for a socket), unlinked and recreated by each start. The relay listens on the loopback port saved in `<state dir>/relay.json` (0600) and listens at start when that file exists. The file also holds the live grants as token SHA-256 hashes with their scopes, never the tokens, and `relay.revoke` removes one. A saved port taken by another process falls back to a random one. The band CLI path is described above. A revoke the hub sends while the worker is down is not replayed, so that grant stays valid until the hub revokes it again.
- Persistent terminals on a worker (`apps/worker/src/terminals.ts`, `packages/host-local/src/terminals/daemon/exit-records.ts`). `band-worker` runs terminals in the terminal daemon (the hub's daemon code, entry `apps/worker/src/terminal-daemon.ts`, bundled to `dist/terminal-daemon.mjs`), with its run dir at `<state dir>/run`, so shells outlive the worker. One daemon per worker state dir, not one holder per terminal: the daemon already has the scrollback mirror, replay, reattach and supersede-on-upgrade. The socket is 0600 in a 0700 dir (in `/tmp/band-<uid>/` when the state dir path is too long). A daemon started with `--record-exits` writes `run/exits/<id>.json` for a shell that exits while no server is connected, and `DaemonTerminalBackend.recoverExits` (called on each link connect) connects and sends those as `pty.exit` once. `Worker.start` takes `persistentTerminals` (only `main.ts` sets it, so in-process test workers leave no daemon), and `BAND_TERMINAL_DAEMON=0` turns it off. `install-service` writes `KillMode=process` and `AbandonProcessGroup`, and `uninstall-service` ends the daemons (`stopTerminalDaemons`). The hub's own local worker is unchanged. Test: `apps/worker/tests/terminal-persistence.test.ts` (real `band-worker` binary killed and restarted).
- Remote browser (plan step 7.3, `packages/host-local/src/browser/chromium.ts`, `host.browser`). `browser.open` on a worker starts one Chromium per worktree with `--remote-debugging-port=0 --remote-debugging-address=127.0.0.1` and a profile in `<state dir>/browser/<worktree id>` (headless unless the worker has `DISPLAY`; the binary is `BAND_CHROMIUM_BIN`, a system Chromium or a Playwright download). `browser.connect` opens a `browser.cdp` channel to the browser-level endpoint, one length-prefixed frame per CDP message (`encodeFrame` in `packages/link/src/frames.ts`). The hub's `/cdp?worktreeId=<id>` (`infra/browser-host/cdp-proxy.ts`; `bandTabId` alone keeps the desktop path, and a `bandTabId` with a `worktreeId` must belong to it) opens the browser through `setRemoteCdpOpener` (`services/browser-service.ts`) and relays frames both ways, with no Default-profile check because the profile belongs to the worktree. A local worktree gets close code 4000 there. `browser.close` sends `Browser.close` so cookies are written, then SIGTERM and SIGKILL. `worktrees.remove` and the worker stopping close it. The relay reply carries `browserPortFile`, and the agent's env gets `BAND_CDP_PORT_FILE` (Chromium's `DevToolsActivePort`, first line the loopback port). Tests: `apps/worker/tests/browser.test.ts` (cookies across a reopen) and `apps/hub/tests/remote-browser.test.ts`, both skipped with no Chromium. Not done yet: `band browsers` commands driving this browser, and the pane choosing it in the UI.

## Architecture: local direct path

The desktop app talks to its own machine's worker on `127.0.0.1` for that worker's worktrees: terminal sockets and `worktree.listFiles | getFile | saveFile | getDiff | getChanges | getFileDiff | searchFiles | searchContent` (`DIRECT_PROCEDURES`, `packages/shared/src/direct-access.ts`). Guide: `docs/local-direct-path.md`.

- Hub: `worktree.directAccess { worktreeId, hostId }` (`services/direct-access-service.ts`) returns `{ hostId, port, token, expiresAt }` only when the worktree is on that worker, else null. `RemoteHost.direct.issue` mints a `bwd_` token and sends `direct.register` (`packages/link/src/direct.ts`). Tokens last 10 minutes (`BAND_DIRECT_TOKEN_TTL_MS`, read on every token), counted by the worker on its own clock and capped at 1 hour; `direct.register` carries `ttlMs` and the worker answers with `expiresAt`. The hub stores none. The procedure is left out of the MCP endpoint and the relay.
- Worker: `apps/worker/src/direct.ts` is a loopback listener separate from the relay, started on the first registration. It keeps token hashes with their scope, checks `Host` (421), `Origin` (`app://h-<hex>` only, 403), the token (401) and the worktree (403). Calls run `@band-app/worktree-ops` over a worker whose calls go through `Registrar.invoke`, the same handlers and path policy as a link call. The terminal socket serves `attachSession` from `@band-app/worktree-ops/terminal-socket` and waits up to 5 s for a PTY the hub is spawning, then closes with `4100`. The hello lists the `direct` capability.
- `packages/worktree-ops` holds `FilesService`, `DiffService`, `SearchService`, their input schemas, `directOps` (one definition per direct procedure, used by the hub's router and the worker) and the terminal WebSocket protocol (`terminal-socket.ts`, `output-flow.ts`, `strip-queries.ts`). The hub's `services/files-service.ts`, `diff-service.ts` and `search-service.ts` only build them over `worktreeService.resolve`. `WorktreeNotFoundError` lives in `worktree-ops/resolver.ts` and `errors.ts` re-exports it.
- Desktop: `worker_local_id` returns the installed service's `BAND_WORKER_ID` when it serves the current hub. The CSP's `connect-src` allows `http://127.0.0.1:*` and `ws://127.0.0.1:*` for a remote hub's pages only (not `app://local`).
- Web: `directWorkerLink` (`lib/direct-worker.ts`) sits in front of the hub link in both tRPC clients, and `terminal-cache.ts` asks `directTerminalTarget` before each connect. Fallback to the hub on a connect error, a timeout, 401 or any refusal, then 15 s before the direct path is tried again.
- Tests: `apps/hub/tests/direct-path.test.ts` (real hub and worker), `apps/web/e2e-desktop/desktop-direct-path.spec.ts` (real desktop app with this Mac as a worker). Not done yet: chat and agent events (part 2), LSP, file watch and the formatter.

## Architecture: worker provisioning

An admin gets a one-line command for a blank Linux or macOS machine (guide: `docs/provisioning.md`): `curl -fsSL <hub>/api/provision/<code>/script | sh`. Settings > Workers > Add a worker (`ProvisionHostRow.tsx`) shows it with the expiry, a "Copy as cloud-init" variant, the live status and the log. Manual install stays below it.

- State: `services/provisioning-service.ts` and the `host_provisions` table (`infra/db/queries/provisions.ts`). The code (`bpc_`) and the run token (`bpr_`) are stored as SHA-256 hashes. A row holds the pinned commit, the worker id the exchange created, the state (`pending`, `running`, `failed`, `done`), the exit code and the scrubbed log (last 256 KiB). The status the UI sees is derived: `online` when the worker row is online, else `failed`, `provisioning` (spent), `expired` or `waiting`. The service is on the exempt list of the machine-access Biome override, because it runs `git` and `tar` on the hub's machine and keeps bundle files under `<BAND_HOME>/provisioning/<id>/`.
- Endpoints (`api/provisioning/handler.ts`, answered in `start-server.ts` before the device-token check): `GET /api/provision/<code>/script` (no secret, spends nothing, rendered by `services/_utils/provision-script.ts`), `POST /api/provision/exchange` (spends the code with a guarded SQL update, calls `tokenService.issueWorkerBootstrap`, answers `key=value` lines because the script has no JSON parser), `GET /api/provision/<code>/bundle` and `POST /api/provision/<code>/log[?exit=N]` (both need the run token as a Bearer header). A refusal is one generic 401. The bootstrap token cannot authorize the bundle or log, because the worker spends it before the script finishes.
- `provisioning.createCommand | status | settings | updateSettings` use `adminProcedure`, are left out of the MCP endpoint and refused by the relay (`NEVER_FOR_AGENTS`). The repo is `settings.provisioning { repoUrl, branch, command }`, admin only to read or write. The hub URL must be https, or http on loopback.
- The provisioning repo is fetched when the command is created (`git clone --depth 1` on the local worker, the vault's git credential passed as `GIT_CONFIG_*` `http.extraHeader` in the child's environment only), so a bad URL fails there. The commit is pinned and the files are packed without `.git`.
- With a provisioning repo, `custom_install` runs the start command, then the same steps as `default_install` (`install_worker` pinned to `WORKER_VERSION`, `install-service`, `root_steps`), so the repo owns the machine and Band owns the worker. The start command gets `BAND_WORKER_VERSION` beside the other `BAND_*` variables. If a service file naming this worker id exists and `band-worker status` (from `BAND_WORKER_CMD`, `PATH` or `~/.band/npm`) reports it running when the start command exits, Band skips its own install and service steps, logs that it did, and still runs the root steps (enable-linger, `doctor` fixes).
- The script runs as the normal user and uses `sudo -n` for root steps. `BAND_WORKER_CMD` replaces the installed `band-worker`, `BAND_PROVISION_ROOT_STEPS=off` skips root steps, `BAND_PROVISION_HOME` moves the unpack directory, and `BAND_PROVISION_TTL_MS` (hub, read on every command) changes the one hour life. `BAND_PROVISION_TIMEOUT_MS` (hub, read on every check, default 30 minutes) fails a run whose worker has not said hello since the exchange (`ProvisioningService.settle`, run when a command is read). Production settings read at run time, beyond TEST-1's carve-outs, because the tests cannot install a launchd or systemd unit or touch swap.
- Tests: `apps/hub/tests/provisioning.test.ts` (real hub, the real script under `sh`, the real `band-worker`; a wrapper given as `BAND_WORKER_CMD` starts the worker as a background process in place of a service manager), `apps/web/e2e/settings-hosts-provision.spec.ts`. The script passes `shellcheck`.

## Architecture: version updates

Workers show their Band version, the hub tells when a newer release exists, and an admin can update a worker with one click (guide: `docs/install.md#updating`).

- Versions (`packages/shared/src/versions.ts`, pure and tested in `packages/shared/tests/versions.test.ts`): `compatibilityProblem` is the link rule (same major, middle number within 1; version 0.x), `updateTargetFor`/`describeHostVersion` (`services/_utils/host-version.ts`) work out what `workers.list` returns per worker (`workerVersion`, `versionState` current|behind|ahead|unknown|refused, `updateRequired`, `serviceManager`, `updateTarget`, `canUpdate`, `manualCommand`, `update`), and `isStrictSemver` is the only thing allowed to reach npm. The hub's own version is `apps/hub/package.json`, imported into the bundle (`services/_utils/hub-version.ts`), so the Docker build sets it from the `BAND_VERSION` build arg before `pnpm build:web`. A hub that still reports the unreleased default `0.1.0` (run from source) skips the compatibility check, logs that it did, and accepts every worker. `BAND_HUB_VERSION` (plain MAJOR.MINOR.PATCH) replaces the bundled version; `worker-versions.test.ts` uses it to test refusal at a released version, `worker-versions-dev-hub.test.ts` covers the default.
- Link: `Hello.version` and `Hello.serviceManager` (`launchd` | `systemd`) are optional, `Rejected.code` is optional, so old and new peers still talk (no `PROTOCOL_VERSION` bump). A worker without `version` is read from `buildId` (`band-worker@<v>`), else its version is unknown and it is accepted. `WorkerLinkService.authenticate` checks the credential first, then the version; a refusal carries `code: "version-incompatible"` and is stored in `workers.info.updateRequired` (only for a worker that holds a valid credential). `LinkClient.connect` rejects with `LinkRejectedError`, and the worker waits `BAND_WORKER_VERSION_RETRY_MS` (5 min) before it exits, so a service manager does not make it redial every few seconds.
- Release check (`services/release-check-service.ts`): `GET <BAND_GITHUB_API_URL>/repos/band-app/band/releases/latest` at startup and every 24 h (`BAND_UPDATE_CHECK_INTERVAL_MS`), `BAND_UPDATE_CHECK=off` disables it. The answer stays in memory, a failure is logged once and costs nothing in the UI. `workers.updateStatus` (any device token) returns the hub version, `latest`, `updateAvailable`, `installMethod` and `hubCommand` (`hubUpdateCommand`, from `BAND_INSTALL_METHOD`: `compose`, `helm`, `k8s`, `docker`; set in `deploy/compose/compose.yml`, `deploy/k8s/hub.yaml` and `docker/Dockerfile`).
- Update (`services/worker-update-service.ts`): `workers.update { hostId }` (admin) computes the target itself and answers at once (a proxy in front of the hub would time out on a request held open for an npm install); in the background it sends `worker.update` over the link, and the worker (`apps/worker/src/update.ts`) validates the version, runs the npm beside its own node (`BAND_NPM_BIN` overrides; node's directory goes first on the child's PATH) as `npm i -g --prefix <prefix> @band-app/worker@<v>` with the prefix taken from where the worker runs (`installPrefix`; a worker outside an npm global layout sends `updateBlocked` in its hello, so `workers.list` has `canUpdate: false` and `updateBlockedReason`), fixes node-pty's `spawn-helper` mode, answers, and 500 ms later restarts through `launchctl kickstart -k gui/$UID/app.band.worker` or `systemctl --user restart band-worker` (`BAND_LAUNCHCTL_BIN`, `BAND_SYSTEMCTL_BIN`). The service manager comes from the environment (`XPC_SERVICE_NAME=app.band.worker`, `INVOCATION_ID`). The worker row's `update` (`installing`, `restarting`, `failed` with the error) is the progress, pushed as `host-status-changed`. A failed install is an RPC error kept there, an update that does not reconnect on the target within 3 minutes (`BAND_WORKER_UPDATE_RESTART_TIMEOUT_MS`) fails too; state is in memory. `workers.interruptions` (admin) lists the agents the restart ends, for the confirm dialog. `hosts.*` is left out of the MCP endpoint and the worker relay.
- UI: `UpdateAvailableBadge.tsx` in the sidebar footer, `UpdatePanelDialog.tsx`, `WorkerUpdateButton.tsx` (confirm dialog) and `settings/HostVersionLine.tsx` on Settings > Workers. CLI: `band workers list` has a VERSION column.
- Tests: `apps/hub/tests/release-check.test.ts`, `worker-versions.test.ts` (real hub, real worker and `LinkClient` stand-ins), `apps/worker/tests/update.test.ts` (fake npm, launchctl and systemctl), `apps/web/e2e/update-available.spec.ts` (`hub/tests/helpers/stand-in-worker.ts`, `fixtures/github-releases-stub.ts`). The real update of a live worker restarts it, so it is checked by hand.
- Hub update (`services/hub-update-service.ts`, `settings.hubUpdate.command`, admin only to read or write): `workers.updateHub` (admin) runs the command with `sh -c`, detached (`detached`, `unref`), with a minimal env plus `BAND_HUB_TARGET_VERSION` and the user-session bus variables, output in `<BAND_HOME>/hub-update.log`. The run lives in `<BAND_HOME>/hub-update.json` because the restart ends the process. `workers.updateStatus` returns `hubUpdate { configured, state idle|updating|failed, target, error }` (the log tail only for an admin): the target version reached means done, a non-zero exit, a restart on another version or `BAND_HUB_UPDATE_TIMEOUT_MS` (10 minutes, read on every call) means failed. `workers.dismissHubUpdate` clears a failure. `workers.hubInterruptions` (admin) lists every live agent on the hub (held ones included, because only the hub has their ACP state) with a `busy` flag, and `workers.updateHub { confirmInterruptions }` answers 409 naming the busy worktrees unless it is true. `HubUpdateControls.tsx` checks first, starts at once with no busy turn, and otherwise opens a confirm dialog. The documented `update.sh` (`docs/install.md`) defers while `tasks.list` shows turns younger than `BAND_HUB_UPDATE_MAX_TASK_AGE_MIN` (180), up to `BAND_HUB_UPDATE_MAX_DEFER_H` (6) hours. `workers.updateAll { confirmInterruptions }` (admin) updates every online worker that is behind one after the other (`WorkerUpdateService.updateAll`), skips one with running agents unless confirmed, and `updateStatus.updateAll` lists the result per worker. `updateHub`, `hubInterruptions`, `dismissHubUpdate` and `updateAll` are in `NEVER_FOR_AGENTS`, and the service is on the machine-access exempt list in `biome.json`. `BAND_INSTALL_METHOD=npm` gives `npm i -g @band-app/server@<v> && systemctl --user restart band-hub`. UI: `HubUpdateControls.tsx` and `UpdateAllWorkers.tsx` in the update panel. Tests: `apps/hub/tests/hub-update.test.ts`, the probes in `remote-relay.test.ts`, `apps/web/e2e/update-hub.spec.ts`, `apps/web/e2e/update-hub-interruptions.spec.ts`.

## Architecture: desktop workers

A worker can offer a virtual desktop (plan step 7.1). The `band-worker-desktop` image (`docker/worker-desktop.Dockerfile`, entrypoint `docker/desktop-entrypoint.sh`) is the worker image plus Xvfb on `:99` (`BAND_DESKTOP_RESOLUTION`, default 1280x800x24), fluxbox, x11vnc, Chromium and common GUI libraries. The entrypoint exports `DISPLAY` before it execs `band-worker`, so agents, terminals and headed Playwright runs draw on that display. x11vnc runs with `-localhost -nopw`: it listens on loopback only and has no password, because the worker's link is the auth boundary. Never drop `-localhost`.

- A worker reports `desktop` in its capabilities when `DISPLAY` is set and `x11vnc` is on its PATH (`desktopUnavailableReason`, `packages/host-local/src/desktop/desktop.ts`, read on every `host.info`). `Host.desktop.open()` connects to `127.0.0.1:$BAND_DESKTOP_VNC_PORT` (default 5900) and rejects with `This worker has no desktop: <reason>` naming the missing display, the missing x11vnc or the failed connect. The worker method `desktop.open` (`methods-streams.ts`) opens a `desktop` link channel carrying the RFB bytes, and `RemoteHost` wraps it as a `Duplex`.
- The hub bridges it at `GET /api/hosts/<id>/desktop` (`infra/host/desktop-proxy.ts`, wired in `start-server.ts`). It takes any device token like the other WebSocket routes. Binary frames go both ways unchanged, and the `binary` subprotocol noVNC offers is accepted. A worker with no desktop, an offline worker and an unknown worker close with code 4001 and the reason. A second viewer on one worker closes with 4409. Every session starts view-only (step 7.2, `rfb-client-filter.ts`): the bridge splits the viewer's bytes into RFB messages and drops KeyEvent, PointerEvent and ClientCutText, so only SetPixelFormat, SetEncodings and FramebufferUpdateRequest reach x11vnc. It follows RFB 3.7 and 3.8 with security type None (x11vnc `-nopw`) and closes with code 1008 on anything else, including a message type it cannot size. The pane switches mode with a text frame `{"type":"control","enabled":true}`. A binary frame never changes the mode, and the hub sends no text frames because noVNC cannot read them. A new connection is view-only again. The route is for a person's device token only: the worker relay lists no desktop route, so an agent on a worker gets 403 (`remote-relay.test.ts`).
- A runner with `desktop: true` gets `BAND_DESKTOP=1` in its hook environment. The `docker` hook then runs `BAND_DOCKER_DESKTOP_IMAGE` (default `band-worker-desktop`), with `--shm-size 1g`, instead of the repo or worker image.
- Tests: `apps/worker/tests/desktop.test.ts`, `apps/hub/tests/desktop-host.test.ts` (real hub and workers, a stand-in RFB server on the loopback port) and `apps/hub/tests/desktop-docker.test.ts` (the real image, run by the CI `docker` job, skipped without `BAND_DOCKER_TEST_DESKTOP_IMAGE`). The viewer is a dialog (`DesktopViewerDialog.tsx`, `DesktopViewer.tsx`, noVNC loaded with a dynamic import because it reads `window` at load) opened from Settings > Workers ("Open desktop") and from the center group header (`DesktopHeaderButton.tsx`) when the worktree's worker is online with the `desktop` capability. The dialog is a large overlay (96vw by 94vh, no padding), not a center tab, because Settings > Workers opens it too and a worker's desktop belongs to no worktree. Its header shows worker, resolution and mode, with Fit / 1:1, Take control / Release, Fullscreen and Close. Fit scales a desktop larger than the area down at its aspect ratio and draws a smaller one 1:1, never scaled up. 1:1 draws it at its own size and the area scrolls. noVNC measures the area with `getBoundingClientRect`, so the viewer applies the scale again when the dialog's open animation ends. Fullscreen puts the viewer itself in fullscreen. Escape leaves fullscreen first, and in control mode it goes to the remote desktop instead of closing the dialog. The canvas takes keyboard focus only in control mode. It reconnects up to three times after a drop. Take control sends the mode request first, then enables noVNC input, and paste goes to the remote only in control mode. There is no "match my window" resize: the filter does not follow SetDesktopSize (type 251) and would close the session. The filter reads a ClientCutText length as signed, because noVNC answers x11vnc's ExtendedClipboard offer with a negative-length one; read as unsigned it held every later message, so no key or click reached a real x11vnc. Tests: `apps/web/e2e/desktop-viewer.spec.ts` (a stand-in RFB server in `fixtures/rfb-stub.ts` that records keys, its size set per test, with layout, fit, 1:1 and fullscreen cases), `apps/web/e2e/desktop-viewer-x11vnc.spec.ts` (a real Xvfb and x11vnc from `fixtures/x11-desktop.ts`, natively when they are on PATH, which the CI e2e job installs, or in the image named by `BAND_E2E_DESKTOP_IMAGE`; an `xev` window logs the clicks and keys that reach the display), the view-only cases in `desktop-host.test.ts`, and the real framebuffer through the bridge in `desktop-docker.test.ts`. ## Architecture: agent environments

A repo declares its environment in `.band/environment.json` (format and relation to devcontainer and `config.json`: `docs/agent-environments.md`). `packages/environment` (`@band-app/environment`) holds the zod schema, the parser (`parseEnvironment`, `validateEnvironment`), the `requires` range matcher (`satisfies`, `unmetRequirements`) and `scriptFor`. It touches no file system. Unknown keys are errors with the key path, and a `build.devcontainer` or `build.dockerfile` path must stay inside the repo and exist.

- `HostScripts.environment` reads and validates the file on the worktree's worker (worktree first, then the repo checkout) and never rejects. `HostScripts.command` asks it first: a valid file's `install` then `start` is the setup command and its `teardown` is the teardown command, otherwise `.band/config.json` answers. A file with problems is logged and skipped. `WorktreeScriptService.startSetup` opens the file's `terminals` once setup exits 0. Remote worktrees go through the worker's `scripts.environment` call.
- `HostInfo.tools` (`node`, `python`, `go`, `pnpm`, `uv`, `docker`, `git`, from `process/tools.ts`, cached 60 s) comes back in `worker.info` and in the worker's hello (`Hello.tools`, optional). The hub stores it in `workers.info`, and `workers.list` returns it as `tools`.
- `environment.forRepo` and `environment.validate` (`api/environment/router.ts`, `services/environment-service.ts`) back the Environment section of a repo's page in Settings > Repos (`RepoEnvironment.tsx`) and `band env validate`. They read on the hub's machine. `validate` takes a path, so the MCP endpoint leaves it out, and the relay refuses both because they are not in `RELAY_PROCEDURES`.
- Not done yet: placement by the repo's own `requires` (placement takes `requires` from the create call), and using `services` and `secrets`. The `docker` runner hook uses `isolation` and `resources` (see Architecture: runners).
- Images (`services/environment-build-service.ts`, `environment_builds` table, `environment.imageStatus` / `environment.build`, `band env build | status`, the Image in the Environment section of a repo's page in Settings > Repos; how they are built and cached: `docs/agent-environments.md`). The key is `imageKey` in `packages/environment/src/image.ts`, a SHA-256 over git object hashes at `origin/<default branch>` (the environment file, the Dockerfile or devcontainer and its directory, root lockfiles) and the worker base image ID. The build exports the commit with `git read-tree` and `checkout-index` (no worktree is registered), builds layer 2, adds layer 1 with a generated Dockerfile, runs `install` in a created container with `docker cp` and `docker commit`, and pushes when `environmentBuilder.registry` is set. A ready row for the key whose image still exists on the builder worker is a cache hit. The newest ready row is the repo's current image, and a failed build never replaces it. `environmentBuilder.hostId | registry | workerImage` in settings pick the builder worker (default `local`). Every command runs through `Worker.exec` with credential-like and `BAND_*` variables blanked (`scrubEnv`). `BAND_DOCKER_BIN` and `BAND_DEVCONTAINER_BIN` override the binaries on the local worker and are read on every call, which is how tests run `apps/hub/tests/fixtures/docker-stub-bin.mjs`. `environment.build` is admin only, left out of the MCP endpoint and refused by the relay. The auto trigger (`BAND_ENVIRONMENT_BUILD_POLL_MS`, default 60 s) rebuilds only repos that have a build already. Not done yet: snapshots, a settings page for `environmentBuilder`, and pruning old images.
- Tests: `packages/environment/tests` (node:test, pure functions with no state to fake, which is why they are not integration tests), `apps/hub/tests/environment-build.test.ts`, `environment-build-auto.test.ts` (docker stub) and `environment-build-docker.test.ts` (real Docker, skipped with no daemon), `apps/web/e2e/settings-repo-environment-image.spec.ts`, the `env_build_*` tests in `apps/cli/tests/integration.rs`, the contract suite in `packages/worker-api/src/contract.ts` against local and remote workers, `apps/hub/tests/environment.test.ts` and `environment-remote.test.ts` (real worker), the `env_validate_*` tests in `apps/cli/tests/integration.rs`, and `apps/web/e2e/settings-repo-environment.spec.ts`.

## Architecture: placement and worker requests

`worktrees.create` takes `placement: { labels?, requires?, environment? }` instead of `hostId` (passing both is an error). `PlacementService` (`services/placement-service.ts`) picks the least loaded online worker (fewest worktrees) whose `k=v` labels include every requested label and whose facts (`versions`, `os`, `arch` from `host.info`) satisfy `requires` (`>=24`, `>`, `<=`, `<`, `=`, or a plain `24` prefix). The local worker is a candidate when it is enabled. Version constraints use the environment package's range matcher (`>=24`, `^3.12`, `24.x`, `>=20 <23`), and a non-version value such as `os=linux` must match exactly. Facts include the worker's `tools`.

- With no match, the hub inserts a `host_requests` row (`pending`, with the create call in `input`) and `worktrees.create` answers `{ path: "", provisioning: { requestId } }`. Asking again for the same worktree returns the open request. No worktree exists yet; the UI lists `hostRequests.list` as provisioning cards under the repo (`ProvisioningWorktreeCard`).
- Runner side, admin token only: `hostRequests.lease { runnerId, filter: { labels }, ttlMs }` takes the oldest leasable request whose labels are all in the filter (a request without a filter is taken whatever its labels). A guarded SQL `UPDATE` makes the lease atomic, and a lease past `lease_expires_at` is leasable again (the 1 s sweep also returns it to `pending`). `renew` and `fulfil` need the holder's `runnerId`, else 409. `fulfil { requestId, runnerId, hostId, hostRepoPath? }` records the worker; once that worker is online (the worker's hello, or the sweep) the hub replays the stored create call on it and sets `completed_at`. A failed replay fails the request with the error.
- `BAND_PLACEMENT_TIMEOUT_MS` (default 10 minutes, read on every sweep) fails a request that is not completed in time: "No worker matched the placement within Ns", or "Worker X did not connect within Ns" after a fulfil. `hostRequests.cancel` cancels a waiting request or dismisses a failed one; a worktree created while the cancel raced is removed again. `hostRequests.*` is left out of the MCP endpoint and the worker relay.
- CLI: `band worktrees create ... --labels k=v,k=v --requires node=>=24 --any-worker --worker-repo-path <path>`; a provisioning result prints the request id. Tests: `apps/hub/tests/placement.test.ts`, `placement-timeout.test.ts`, `apps/web/e2e/provisioning-worktree.spec.ts`.
- Not done yet: a placement picker in the New Worktree dialog. The runner service (3.4) is below.

## Architecture: runners

`RunnerService` (`services/runner-service.ts`) fulfils worker requests by running the `runners` entries of `~/.band/settings.json` (`services/_utils/runner-config.ts` validates them; `settings.update` refuses a bad list, the service skips a bad entry and `runners.list` reports it). The guide is `docs/runner-hooks.md`.

- Every second each runner with a free `maxConcurrent` slot calls `placementService.lease` with its `labels` (and `provides`, which lets a request's `requires` be checked), so the lease's guarded SQL update is what keeps two runners off one request. The service issues a worker bootstrap token (`issueWorkerBootstrap`, which creates the worker row), runs `spawn` with the contract environment, renews the lease every 10 s, polls for that worker to be `online`, and calls `fulfil` (with the `BAND_WORKER_REPO_PATH=` line the hook may print). A non-zero exit, a `spawn` still running at `timeoutSec` or no hello in time fails the attempt: `destroy` runs, the worker row is removed, and one more attempt starts with a new worker. The second failure fails the request with the reason and the last 20 log lines. A cancelled request or a lost lease stops the run and runs `destroy`.
- Hooks get a minimal environment (`PATH`, `HOME`, `LANG`, `LC_ALL`, `TMPDIR`, `USER`, `SHELL`, `SSH_AUTH_SOCK`, the runner's `env`, then the contract variables). The bootstrap token is in the environment only. Hook output goes to `BAND_HOME/runners/logs/<request id>.log` with the token and anything shaped like a Band token replaced by `[redacted]`. `runners.list` and `runners.log` read them (Settings > Runners, `band runners list | log`). `runners.*` is left out of the MCP endpoint and the worker relay.
- `runners/local` starts an ephemeral `band-worker` with its own HOME and `BAND_HOME` under `$BAND_RUNNER_DIR/<worker id>`. `runners/ssh` sends a script to `ssh $BAND_SSH_TARGET 'sh -s'` on stdin. `runner-service.ts` and `runner-config.ts` are on the exempt list of the machine-access Biome override in `biome.json`: the hooks run on the hub's own machine by design, and the logs are hub state.
- Tests: `apps/hub/tests/runners.test.ts` (real `local` hook and worker, the `ssh` hook against a fake `ssh` that runs the script locally because sshd is not on every CI runner, failing and hanging hooks, concurrency, token scrubbing) and `apps/web/e2e/settings-runners.spec.ts`.
- Machines and the reaper (`services/runner-reaper-service.ts`, `runner_machines` table, `infra/db/queries/runner-machines.ts`, step 3.7; guide: `docs/runner-hooks.md#the-reaper`). `RunnerService` records the machine of every attempt (`spawning` until the hello, then `running`) with the handle `spawn` prints as `BAND_MACHINE_HANDLE=<id>`, and passes it to `destroy` as `BAND_MACHINE_HANDLE`. A runner may also set `status` (a hook that prints its live handles), `maxLifetimeSec` and `lifetimeGraceSec` (default 600). The reaper sweeps every `BAND_REAPER_INTERVAL_MS` (default 30 s) and destroys a spawn no attempt owns that got no hello within `timeoutSec` + `BAND_REAPER_HELLO_GRACE_MS`, a machine whose worker row is gone or whose worker was offline for `BAND_REAPER_OFFLINE_MS`, a handle `status` lists that no live row has, and a machine past `maxLifetimeSec`. For the last it sends the worker `lifecycle.sleep` (`packages/link/src/relay.ts`), which runs the same hand-off as an idle worker, and runs `destroy` only after the worker exited with every worktree stored. Until the hard deadline (`maxLifetimeSec` + `lifetimeGraceSec`) a machine with unstored worktrees is kept. After it the machine is destroyed anyway and the hub logs an error naming the worktrees. A failing `destroy` is retried on later sweeps, and the third failure marks the machine `lost`. `runners.machines` and `runners.destroyMachine` are admin only (the latter refuses unstored worktrees without `force`), and Settings > Runners lists the "Workers started". Tests: `apps/hub/tests/runner-reaper.test.ts` (fake hooks, then the real `local` hook and worker) and `apps/web/e2e/settings-runners.spec.ts`.
- `runners/docker` starts the worker image with `docker run --detach --rm`, ported from Bunny's hardening: uid 65532, `--cap-drop ALL`, `no-new-privileges`, a read-only root with a `/tmp` tmpfs and an anonymous `/work` volume, pids, memory and cpu limits (from `environment.resources`), `band.runner`, `band.request` and `band.worker` labels, and no mounts, so never the docker socket. The container clones the repository itself. The hub passes the repo's current environment image as `BAND_REPO_IMAGE` (`RunnerService.repoImage`) and the hook runs it when its docker daemon has or can pull it, else the worker base image. `destroy` runs `docker rm --force --volumes`. `BAND_DOCKER_*` and `DOCKER_HOST` in the runner's `env` configure it (`docs/runner-hooks.md`).
- Isolation levels (`services/_utils/isolation.ts`): a request's level is `placement.environment.isolation` (default `worktree`), a runner's is its `isolation` setting (`process` is `worktree`). `placementService.lease` skips a request whose level is above the runner's `filter.isolation`, and `RunnerService.tick` passes it. `place()` never reuses a worker for `container` or `vm`, and a worker the hub starts for one carries the label `band.isolation=<level>`, which `place()` skips for `worktree` requests too. `band worktrees create --isolation worktree|container|vm` sets the level. `placeWorktree` throws `No runner offers isolation <level>` at once when no runner in settings offers it, instead of waiting out the placement timeout.
- Tests also cover isolation: `apps/hub/tests/runner-isolation.test.ts` (the `local` hook as a runner that declares a level) and `apps/hub/tests/runner-docker.test.ts` (real docker, skipped without `BAND_DOCKER_TEST_IMAGE`, run by the CI `docker` job).
- `runners/k8s` starts a worker as a Pod (or Job, or agent-sandbox Sandbox) with `kubectl`: `render.mjs` builds the manifests, `spawn.sh` creates the workload, then a token Secret owned by it (the token is only on kubectl's stdin), and prints `BAND_MACHINE_HANDLE=<ns>/<name>`. `destroy.sh` and `status.sh` go by the `band.worker` label. The hardening matches the docker hook (uid 65532, drop ALL, read-only root with emptyDir `/tmp` and `/work`, RuntimeDefault seccomp, no service account token), and `isolation: vm` needs `BAND_K8S_RUNTIME_CLASS`. Examples in `deploy/k8s/` (namespace, RBAC with no Secret read, hub Deployment, `check-rbac.sh`). A worker takes plain http only for loopback, so Pods need an https hub URL. `BAND_K8S_CA_CONFIGMAP` mounts a private CA for the hub. Tests: `apps/hub/tests/runner-k8s.test.ts` (stub `kubectl` through `BAND_KUBECTL_BIN`) and `runner-k8s-kind.test.ts` (real cluster, run by the CI job `k8s (kind)`, skipped without `BAND_K8S_TEST_IMAGE` and `BAND_K8S_TEST_KUBECONFIG`). Not done yet: the reaper (3.7). The idle and ephemeral lifecycle is below.
- `runners/hetzner` and `runners/contabo` (`spawn`, `destroy`, `status`, plan step 3.8) create a VM per request. Both render one cloud-init (`runners/_shared/cloud-init.mjs`) that starts `band-worker --ephemeral` under systemd with `ExecStopPost=+poweroff`, and print `BAND_MACHINE_HANDLE`. Contabo is monthly, so its default is a reuse pool (reinstall an idle instance). Provider credentials come from the runner's own env. Tests: `apps/hub/tests/runner-vm-hooks.test.ts` against Express stubs of both APIs (`HCLOUD_API_URL`, `CONTABO_AUTH_URL`, `CONTABO_API_URL`). Guide: `docs/runner-hooks.md`.
- Snapshots (plan step 3.10, `docs/runner-hooks.md#snapshots`). A runner with `snapshot` and `restore` hooks (plus `snapshotDelete`, `snapshotKeep`, `snapshotTtlSec`, `snapshotTimeoutSec`) gets a machine snapshot on every sleep, after the git and session state is stored, which stays the fallback. `RunnerService.snapshotHost` runs `snapshot` with `BAND_MACHINE_HANDLE` and `BAND_WORKTREE_IDS` and reads `BAND_SNAPSHOT_ID` (and `BAND_SNAPSHOT_SIZE`) from its output into `runner_snapshots`, `RunnerService.destroyMachine` (the reaper's call) runs `destroy` once the worker is gone, and the machine, its runner and its handle come from the `runner_machines` row of the worker id, which the snapshot row points to with `machine_id`. A wake leased by the same runner runs `restore` instead of `spawn`; a failing `restore` runs `destroy` and then `spawn` in the same attempt. After a restore says hello the snapshot row has `restored_at`, and `EphemeralLifecycleService.restore` skips the git checkout for a worktree whose worktree is at its stored `baseSha`, writing only the agent sessions. The hub deletes a snapshot through `snapshot-delete` when a wake used it, a newer one replaced it, it expired or it is beyond `snapshotKeep` (`sweepSnapshots`, `BAND_SNAPSHOT_SWEEP_MS`, default 60 s). `runners.snapshots` lists them. The docker hook snapshots `/work` into an image `band-snapshot:<worker>-<time>` (a helper container, because `docker commit` skips volumes) and restores by filling a new container's `/work` volume from it. The hetzner hook uses `create_image` and creates a server from the image. The restore hooks must delete the saved `session-token`, because a worker prefers it to the bootstrap token. Tests: `apps/hub/tests/runner-snapshots.test.ts` (fake runner wrapping the `local` hook), `runner-docker-snapshot.test.ts` (real docker, skipped without `BAND_DOCKER_TEST_IMAGE`, run by the CI `docker` job) and the snapshot cases in `runner-vm-hooks.test.ts`.

## Architecture: checkpoints

The hub keeps recent checkpoints of every worktree on a static worker (`services/checkpoint-service.ts`, `worktree_checkpoints` table, guide: `docs/checkpoints.md`). A checkpoint reuses the sleep snapshot (`packages/host-api/src/snapshot-git.ts`, a commit of the working tree built in a temporary index; the worker uses it too, for the fence snapshot) and lives on the hub only, never on origin: `<BAND_HOME>/checkpoints/<worktree id>/<checkpoint id>/bundle.pack` (a bundle of what the worker's remotes lack, absent when every remote has the snapshot) and `sessions.json` (the agent session files).

- Triggers: `onTurnEnded` (`_utils/turn-events.ts`, emitted by `finishTask`), a sweep every `BAND_CHECKPOINT_POLL_MS` (60 s) that takes one once the files' fingerprint (head, `git status`, `git diff --numstat`) stayed unchanged for `BAND_CHECKPOINT_QUIET_MS` (3 min) and differs from the last checkpoint, the worker's `lifecycle.shutdown` request (sent by `Worker.shutdown` before the link closes, 30 s at most), `move`, and `checkpoints.take`. A checkpoint is skipped when base sha, tree sha and agent session hash match the newest one. Ephemeral workers and the hub's own machine are never checkpointed.
- Retention: `BAND_CHECKPOINT_KEEP` (5) and `BAND_CHECKPOINT_MAX_BYTES` (200 MB per worktree). A checkpoint above the limit is skipped and `checkpoints.list` returns the warning.
- The per-repo setting is `repos.checkpoints_enabled` (null for the default, `checkpointsEnabledFor` in `@band-app/shared/repo-hosts`: on for a repo with no allowed-worker list, off for a limited repo). Written only by `RepoQueries.setCheckpointsEnabled` (`repos.update { checkpointsEnabled }`, admin), kept by `saveAll`. Off means nothing is stored, including by `take`; `move` still takes a transient checkpoint and deletes it.
- Offline views (`changes`, `diff`, `files`, `file`) run git on a bare repo the hub builds under `view.git` from the bundles, after fetching history from the hub's checkout or the remote URL. The chat log is on the hub already.
- Restore (`checkpoints.restore`) checks that the target is online and allowed (`addHost` adds it, admin; `RepoHostNotAllowedError` otherwise), makes the repo available there (`WorktreeService.ensureCheckoutOn`, `hostRepoPath` for a repo with no remote), fetches the bundle, `checkoutSnapshot`, builds a snapshot of the result and compares its tree with the checkpoint's, imports the agent sessions, then adds the worktree row, calls `RepoQueries.setSupersededBy` on the old one (`worktrees.superseded_by`, kept by `saveAll`, keyed by repo, name and worker), `rekeyWorktreeRows` (panel states, tasks, agent sessions, cron jobs, subscriptions, browser history, usage, client state, origin links) and `ChatService.reassignWorktree`. Nothing is deleted on the old worker. A superseded copy gets no checkpoints, is ignored by the one-worker-per-branch rule and is removed only by a person (`worktrees.remove`).
- `move` takes a fresh checkpoint, restores, and removes the source with `worktreeService.remove` only after the restore verified the tree. `evacuate` (admin) does it for each worktree of a worker, one after the other, never for a repo's own clone. An offline source worker restores instead.
- Sessions follow the worktree: `restoreSessions` (checkpoints and the ephemeral wake) passes `fromCwd` and `toCwd` to `lifecycle.importSessions`, and the worker (`apps/worker/src/methods-lifecycle.ts`) moves Claude's file under `claudeProjectSlug(toCwd)` (`@band-app/shared/claude-session`, also used by `claude-resume.ts`) and rewrites `cwd` in Claude and Codex lines. Restoring a default-branch worktree sets the target as the repo's primary worker, and `listedMainHostOf` skips superseded copies while a live one exists. Dockview leaves take the worktree id from `PanelVisibilityContext`, not their saved params.
- Owner only: `CheckpointService.assertOwner` runs at the start of a take and again before the row is written, and rejects a superseded worktree, one that lives on another worker, or one whose link session changed meanwhile. Restore replaces what the target holds (an older superseded copy, a branch with extra commits, or for the default branch the repo's own checkout) after saving it under `refs/band/backup/<new worktree id>/<time>[-branch]` (`RestoreResult.backupRefs`); the default-branch worktree goes through `resetCheckoutToSnapshot` and `move` takes it too while its worker is up, refusing when it has a running agent, queued message or terminal. The source clone stays, superseded, and is never removed.
- `checkpoints.*` is left out of the MCP endpoint and the worker relay. CLI: `band worktrees move | restore | checkpoints`, `band workers evacuate`, `band repos set --checkpoints`. UI: Settings > Repos switch, `WorktreeCard` (offline icon with a tooltip, faded row, one "Open on another worker…" item that opens `MoveWorktreeDialog` while the worker is online and `ContinueOnHostDialog` while it is offline, disabled with its reason when there is no checkpoint or the repo is limited to the worker), `OfflineWorktreeNotice` above an offline worktree (worker, last seen, checkpoint age, the Open on another worker button, or the `follow.offer` block reason) with the read-only `CheckpointSidepanel` behind "View checkpoint", `EvacuateHostDialog` in Settings > Workers.
- Tests: `apps/hub/tests/checkpoints.test.ts` (two real workers, scripted ACP stub; S1 to S6), `checkpoints-retention.test.ts`, `apps/web/e2e/checkpoints-offline.spec.ts`, `apps/web/e2e/settings-repo-checkpoints.spec.ts`, `repos_set_checkpoints_*` in `apps/cli/tests/integration.rs`.
- Not done yet: restoring on the hub's own machine, checkpoints of worktrees on the hub's machine, ignored files, and a settings field for the limits (they are environment variables).

## Architecture: follow the work

When a worktree's worker is offline, an action that needs a live worker continues the worktree on another allowed worker from its latest checkpoint (`services/follow-service.ts`, guide: `docs/follow-the-work.md`).

- The gate. `followService.gate(worktreeId, { chatId?, agentId? })` runs before a chat message (`api/chat-submit.ts`, answers 409 with a `HostOfflineAnswer`), `terminals.create` and `agentSessions.launch` (tRPC PRECONDITION_FAILED, the answer in the error's `data.hostOffline`, put there by the `errorFormatter` in `api/trpc.ts`). It is a no-op for a worktree whose worker is online, on the hub's own machine, asleep (ephemeral lifecycle) or superseded. Reading (checkpoint views, chat history) never calls it.
- The offer (`follow.offer`, `FollowService.offer`) checks in this order: the repo is limited to the offline worker, checkpoints are off, no checkpoint exists, no allowed online worker, the chat's agent is unavailable on every candidate (capability report plus `modelRefreshService.launchProblemOn`). Each gives a `blocked.reason` and a message. Otherwise the targets are sorted by agent ready, has a clone, fewest worktrees, and the first agent-ready one is `recommended`. Types are in `packages/shared/src/continuation.ts`.
- The lease (issue #901, `services/worker-lease-service.ts`, `apps/worker/src/lease.ts`, link method `lease.renew`). The hub renews each non-ephemeral worker's lease (`BAND_WORKER_LEASE_MS`, default 5 minutes, read on every call) every fifth of it, writes `workers.last_seen_at` on each acknowledgement and sends the folders of superseded copies as `blockedPaths`. The hub also sends that list at once, as the same renewal, whenever a superseded mark is set or cleared or a superseded copy is removed (`pushBlockedPaths`, called by `CheckpointService.restoreFrom`, `FollowService` and `WorktreeService.remove`), so a move, restore or discard takes effect on the worker in about a second. Requests for one worker that overlap share one follow-up renewal, and an offline worker is skipped. A worker whose lease runs out (hub down or network down) kills its agents, terminals, MCP processes, browsers, language servers and script plans, then snapshots each worktree locally (`refs/band/fenced/<folder>`, `<state dir>/fenced.json`, never uploaded, never a checkpoint), and refuses `acp.spawn`, `pty.spawn`, `scripts.prepare` and `scripts.runHidden` until the next renewal (`LeaseGuard.assertMayRun`). `follow.offer` answers `lease-active` with `leaseExpiresAt` while `workerLeaseService.remainingMs(host)` is positive for an offline worker (the UI counts down on the button), and `CheckpointService.restoreFrom` refuses an offline source the same way, so `continue`, auto-continue, `restore` and `evacuate` all wait. An old worker that answers "method not found" is never held back. Tests: `apps/worker/tests/fencing.test.ts`, `apps/hub/tests/worker-lease.test.ts`, `checkpoint-wins.test.ts` (test hubs set `BAND_WORKER_LEASE_MS` to 1.5 s and `killWorker` waits it out).
- Automatic continuation needs `repos.auto_continue` (`RepoQueries.setAutoContinue`, `repos.update { autoContinue }` admin, `band repos set --auto-continue`) and a checkpoint younger than `BAND_AUTO_CONTINUE_MAX_AGE_MS` (default 30 minutes, read on every call). Older checkpoints always prompt.
- `follow.continue` / `FollowService.continueOn` calls `CheckpointService.restore`, then records `ContinuedFrom` on the new copy (`worktrees.continued_from`, written only by `RepoQueries.setContinuedFrom`, kept by `saveAll`), starts the repo's setup there and broadcasts a notice to the chats. One continuation per worktree runs at a time. The old copy stays superseded and is never deleted by it.
- Divergence. When a worker connects, `WorkerLinkService.onConnected` calls `followService.onHostReturned`, which builds a snapshot of each superseded copy on that worker and compares its tree with the checkpoint's (`worktrees.divergence`, `RepoQueries.setDivergence`). `follow.divergence` and `follow.divergenceDiff` read it, `follow.bringOver` applies the difference as a patch on the new copy (`git apply --check` first, so a conflict changes nothing), and `follow.discardOld` removes the old copy only with `confirm: true`, and a diverged copy also needs `discardChanges: true` (a `resolved` verdict holds while the copy's tree equals `Divergence.treeSha`). For the default-branch worktree it resets the branch to its remote's latest and clears the superseded mark instead of removing the folder.
- `follow.*` is left out of the MCP endpoint and the worker relay. CLI: `band worktrees continue <id> [--to <worker>]`, `band repos set --auto-continue on|off`.
- Tests: `apps/hub/tests/follow-the-work.test.ts` (two real workers plus one without the scripted agent, scripted ACP stub), `apps/web/e2e/follow-the-work.spec.ts`, `repos_set_auto_continue_*` and `worktrees_continue_*` in `apps/cli/tests/integration.rs`.
- Not done yet: continuing on the hub's own machine, a placement-style retry when the chosen target fails, and a settings field for the age limit.

## Architecture: ephemeral lifecycle

Worktrees on an ephemeral worker sleep when it idles and wake on the next use (`services/ephemeral-lifecycle-service.ts`, `worktree_sleep` table, guide: `docs/ephemeral-workers.md`).

- Sleep. An ephemeral worker that was idle for its idle time sends `lifecycle.idle` (`packages/link/src/relay.ts`) and exits with code 0 only on `exit: true`. The hub refuses while a turn, a request waiting on the user, background agent work, queued messages or a terminal exist for a worktree on that worker. Otherwise it stores every worktree through calls on the worker's link: a snapshot commit built in a temporary index (`GIT_INDEX_FILE`) on top of the branch head, pushed to `refs/heads/band/wip/<worktree id>` on `origin` or, when that is not writable, kept as a git bundle in `<BAND_HOME>/sleep/<worktree id>/`; plus the agent session files (`lifecycle.exportSessions`, `sessions.json`). A worker stores all of its worktrees or none. A failure keeps the worker alive and shows as `sleepError` in `workers.list`. The hub's `BAND_EPHEMERAL_IDLE_TIMEOUT_MS` is sent to the worker as `lifecycle.policy`.
- Idle clock. RPCs the hub makes on its own schedule (`host.info`, `worktree.list`, `git.exec`, `git.gh`, read-only `fs.*`, `search.listFiles`) hold the worker while they run but do not restart the idle clock (`PASSIVE_METHODS` in `apps/worker/src/context.ts`). A channel the hub opens counts until both sides end it.
- Wake. `ensureAwake(worktreeId)` is called by a chat prompt (`AgentSessionService.ensureSession`), `TerminalService.spawn` and the file calls of `FilesService`. Pollers do not call it, so they do not wake anything. It records a wake worker request (`input.wake`, hidden from `hostRequests.list`) with the labels and environment of the request that made the worker. `RunnerService` starts a worker with the same worker id (`TokenService.issueWorkerBootstrapFor`, the worker row is kept when an attempt fails). When it says hello, `PlacementService.finish` calls `restoreHost`: fetch the snapshot, `git worktree add -B`, `git read-tree -u --reset` plus `git reset` for the uncommitted changes, and `lifecycle.importSessions` for the agent files. The chat then reattaches with `session/resume` or `session/load`.
- `PlacementService` never offers an ephemeral worker to a new worktree (the claim). `repos.list` marks each worktree `lifecycle: "sleeping" | "waking"`, and `WorktreeCard` shows it. `runners/local/spawn.sh` starts a woken worker id from an empty directory.
- Limits: ignored files, running processes and terminals do not survive. The snapshot upload needs a writable origin or a usable `<BAND_HOME>/sleep`.
- Tests: `apps/hub/tests/ephemeral-lifecycle.test.ts` (real hub, real `local` hook and worker, scripted ACP agent), `apps/worker/tests/lifecycle.test.ts`, `apps/web/e2e/sleeping-worktree.spec.ts`.

## Architecture: distribution

`release.yml` publishes the DMGs, the Homebrew cask, `@band-app/server` and `@band-app/worker` on npm, and then calls `images.yml`, which builds `docker/Dockerfile` and `docker/worker.Dockerfile` as `ghcr.io/band-app/band-hub` and `band-worker` (amd64 on `ubuntu-latest`, arm64 on `ubuntu-24.04-arm`, pushed by digest and merged into a manifest tagged `<version>` and `latest`). The same workflow runs on a pull request that touches `docker/`, `deploy/compose/` or the release workflows, with nothing pushed. `deploy/compose/compose.yml` pulls `ghcr.io/band-app/band-hub:${BAND_VERSION:-latest}` (`BAND_IMAGE` overrides the whole name), and `compose.build.yml` is the override that builds from the checkout. The `mobile` job runs after `publish` (`apps/mobile/scripts/release.mjs`, tested by `apps/mobile/tests/release.test.ts`): the `mobile` input (`auto`, `always`, `skip`) decides, `auto` shipping only when `apps/mobile`, `packages/client`, `packages/shared` or `pnpm-lock.yaml` changed since the previous `v*` tag. It writes the release version into `app.json`, runs `eas build` for iOS (production, auto-submit to TestFlight) and Android (preview) with `EXPO_TOKEN`, and links the builds in the summary and release notes. The EAS workflow `apps/mobile/.eas/workflows/build.yml` has no push trigger. Tests: `apps/worker/tests/service.test.ts` (the real binary against stub `systemctl`, `loginctl` and `launchctl` on PATH) and `apps/web/e2e/settings-hosts.spec.ts` for the install tabs of Add worker. The guide is `docs/install.md`.

The hub's own `band` CLI (`findCliBinaryAt`, `packages/host-local/src/process/cli-binary.ts`) comes from `BAND_CLI_PATH`, a cargo build, the desktop sidecar, the `@band-app/worker-cli-<platform>-<arch>` package beside the bundle (an optional dependency of `@band-app/server`, pinned by `apps/worker/scripts/cli-packages.mjs --pin` in the release, which publishes the CLI packages first), then PATH. `cli.check` answers `{ status, applicable }`: `applicable` is false on a hub with `BAND_LOCAL_WORKER=off` or for a non-admin token, and the dashboard shows no "Install band CLI" banner then. `cli.install` is admin only. A link whose real path is the binary the hub resolved counts as `Installed`. The hook checks again when the window regains focus, and an install the hub cannot write says "On the hub's server, run: sudo ln -sf ...". The desktop admin dialog runs only for a hub on this Mac. Tests: `apps/hub/tests/cli-check.test.ts`, `cli-sidecar-path.test.ts`, `apps/web/e2e/cli-banner.spec.ts`.

## Architecture: headless hub deploy

`deploy/compose/compose.yml` runs the hub image with a `band-data` volume for BAND_HOME, a healthcheck that reads the token from `settings.json`, and an optional Caddy `tls` profile. The guide is `docs/run-the-hub-on-a-server.md`, and the CI `docker` job runs the compose file.

- `BAND_ADMIN_TOKEN` sets the shared admin token (`SettingsQueries.resolveAdminToken`) and replaces a stored secret that differs. With none set, the first boot mints one and, when `BAND_PRINT_ADMIN_TOKEN` is true (the Docker entrypoint sets it), prints it once in `start-server.ts`. `BAND_ACCESS_TOKEN` is the entrypoint's older name for `BAND_ADMIN_TOKEN`. The image bakes in no token.
- `BAND_SERVE_UI=false` skips sirv and the shell, so every non-API path answers 404 and a missing UI build doesn't stop the boot. Dev mode ignores it.
- `BAND_ALLOWED_ORIGINS` adds to `BAND_CORS_ORIGINS` and `corsAllowedOrigins`, for both CORS and the WebSocket origin check.
- Tests: `apps/hub/tests/headless-hub.test.ts`.

## Architecture: machine access lives in host-local

Code that touches a machine (git and `gh`, the exec worker, ripgrep, the LSP manager, ACP launch and spawn, the terminal pool and daemon backend, setup scripts, the Claude environment readers and installers) lives in `packages/host-local` (`@band-app/host-local`). `LocalHost` implements the `Host` interface from `packages/host-api`. The hub imports it through `HostRegistry` (`apps/hub/src/server/infra/host/registry.ts`) and a few helpers by subpath (`@band-app/host-local/git/git-client`). The package has its own worker contract test and its own dependencies (node-pty, ripgrep, xterm, the ACP adapters, typescript-language-server). `apps/hub` still lists node-pty, ripgrep, the adapters and the language server, because its build script copies them into `dist/`.

Services may import from `@band-app/host-local` only the pure helpers and hub-side wiring listed in the `patterns` group in `biome.json` (`getRepoInfo`, `git-refusals`, `process/path`, the terminal backends). `gitRunner`, `ghRunner` and `CommandRun` live in `@band-app/host-api`. A service that reads a worktree's checkout calls `worktree.host` (`host.git.exec`, `host.fs.stat`, `host.fs.readFile`), never `node:fs` on `worktree.path`, because the worktree is on the worker's disk. The remote-loopback test job enforces this: `apps/hub/tests/helpers/worker-fs-guard.mjs` fails the hub on any fs or child process access under a worker's worktree, and `apps/hub/tests/remote-git-routing.test.ts` covers changes, diff, graph, branch status and sync for a remote worktree. `subscription-source-service` keeps `execGh` on the hub: it lends the GitHub plugin's subscription source a `gh` (webhook registration, check runs, comments and the authenticated user) that uses only the GitHub API and the hub's own `gh` login, and needs no checkout.

A Biome `style/noRestrictedImports` override in `biome.json` bans `node:fs`, `node:fs/promises`, `node:child_process`, `node-pty`, the exec worker and `execGit`/`execGh` in `apps/hub/src/server/services/**`, `apps/hub/src/server/api/**` and `packages/worktree-ops/src/**`. A second override lists the files exempt from it: hub state (CLI install, avatar cache, uploads, tasks, the PWA manifest, worktree prompt files) and `repo-service`, which still probes the hub's own repo directories with `existsSync`. A third override lets the GitHub webhook and poll services keep calling `execGit` and `execGh`, while still banning `node:fs`, `node:child_process` and `node-pty`. A new service that needs a machine goes through `host.*`. Adding it to the exempt list needs a reason.

## Architecture: Hub vs Desktop App

The hub (`apps/hub`) handles **data, state, and background processes** only. It must never invoke macOS-only shell helpers (folder pickers, Finder reveal, opening apps, installing the CLI symlink with administrator privileges). Those bridges live in the Electron desktop app (`apps/desktop/src/main/ipc/macos-shell.ts`) and are invoked from the React webview via the IPC bridge in `apps/web/src/lib/desktop-ipc.ts`, which talks to the preload script at `apps/desktop/src/preload/index.cts`.

## Architecture: this computer as a worker

A desktop app connected to a remote hub can make its Mac a worker (`apps/desktop/src/main/services/this-computer-worker.ts`, `ipc/worker.ts`, IPC `worker_status | worker_add | worker_remove | worker_switch_bundled | worker_dismiss_prompt`). Docs: `docs/install.md` (This Mac, from the desktop app).

- The worker ships in the app as `Resources/worker` (`apps/worker/scripts/build-desktop.mjs` writes `apps/worker/dist-desktop`, an `extraResources` entry in `electron-builder.yml`): the worker and terminal daemon bundles with every pure-JS dependency inlined, the ACP adapters in `agents/`, and `node_modules` with only node-pty and ripgrep. `after-pack.mjs` deep-signs it like `Resources/web`. The service runs it with the app's executable and `ELECTRON_RUN_AS_NODE=1`, the way the hub already runs, so no Node install is needed and an app update replaces it.
- The launchd label, plist and 0600 token handling are the worker's own: main runs the bundled `band-worker install-service | uninstall-service` with the token in the child's environment only, so the npm and desktop paths write one layout. `install-service` adds `ELECTRON_RUN_AS_NODE=1` to the plist when it runs under Electron. `BAND_LAUNCHCTL_BIN` replaces `launchctl` for the worker's service code and for main (tests point it at `apps/web/e2e-desktop/fixtures/fake-launchctl.mjs`).
- Main asks the hub for the bootstrap token (`tokens.issueWorkerBootstrap` with the admin token it holds for the remote hub), installs, and polls `workers.list` until the worker is online (60 s). A failure uninstalls and removes the worker row again, so Retry starts clean. Remove uninstalls, waits for the worker to go offline, then `workers.remove`.
- The prompt shows only for a remote hub with no service installed and no answer saved in `~/.band/desktop-worker.json` (`answered` per hub URL). A service installed by npm is detected by its plist not pointing into `Resources/worker`, and Switch reinstalls it from the bundle with the same worker id, name, labels, roots and state dir. On the first start after an update main runs `launchctl kickstart -k` (the file's `serviceVersion`).
- Tests: `apps/desktop/tests/this-computer-worker.test.ts` and `apps/web/e2e-desktop/desktop-this-computer-worker.spec.ts` (real app, real hub, real bundled worker, fake launchctl; the packaged job also checks the plist points into the app bundle). `launchDesktop({ answeredWorkerPrompt })` marks hubs as answered for specs that are not about the prompt. Not done yet: LSP servers in the bundled worker, Linux and Windows.

## Architecture: desktop hub picker

The desktop window loads the bundled UI from `app://<host>/` (`apps/desktop/src/main/app-protocol.ts`, a standard, secure, `supportFetchAPI` scheme; a path with no extension and no file gets `_shell.html`, so reloads and deep links keep their route). The UI build comes from `resources/web/dist/client` when packaged and `apps/web/dist/client` in a repo build (`services/ui-paths.ts`); with no build the window falls back to loading the hub's own URL. With `BAND_DEV_WEB_URL` set in an unpackaged run, local mode still loads the dev server.

- The hub is `local` (default: Electron spawns `apps/hub`) or `remote` (a URL and token, nothing spawned). The choice lives in `~/.band/desktop-hub.json` (mode 0600, `services/hub-choice.ts`). A remote `http:` URL is accepted only for loopback, because the secure `app://` page can't make plain `http:`/`ws:` requests to other hosts.
- Each hub has its own host, so its own origin and localStorage (drafts, tabs, last worktree): `app://local` for the bundled hub, `app://h-<12 hex of sha256(hub origin)>` for a remote one. The handler serves only the host the window is loaded under.
- Every `app://` response carries a CSP (`buildCsp`): `connect-src` is `'self'` plus the current hub's http and ws origins, `frame-src` and `media-src` allow the hub, `object-src 'none'`. Inline scripts are allowed because the SPA shell has inline bootstrap scripts. A new origin the UI must reach (another API host) needs adding there.
- The main window can't leave its `app://` host: `will-navigate` and `will-redirect` open web links in the browser and drop everything else, and `window.open` never creates a window (`navigation-guard.ts`). A hub switch loads programmatically, so it is unaffected.
- The preload reads `{ url, token }` with a synchronous IPC (`band_hub_config`, answered only to the bundled UI's frames, `ipc/hub.ts`) and exposes it as `window.__BAND_HUB__`, which `apps/web/src/lib/hub-config.ts` already reads. The renderer never gets the saved remote token back: `hub_get_choice` returns only `hasToken`. The hub IPC handlers also require the main window's top frame on a trusted origin.
- The hub's CORS allows only `app://local`, `app://h-<12 hex>` and the configured origins (`corsAllowedOrigins`, `BAND_CORS_ORIGINS`). Other `app://` hosts and `file://` are refused. `Origin: null` is allowed only when `null` is in the configured list.
- `registerIpc` wraps every channel with the sender check (`ipc/sender-guard.ts`): the main window's top frame on a bundled `app://` origin, never a `<webview>` or subframe. A new channel registered through its `handle` gets the check automatically.
- With a saved remote hub that does not answer at launch, the window shows a Retry / Use local page (`hub-unreachable.ts`, a `data:` URL whose links are `band-action://` URLs handled in `window.ts`). Use local runs the bundled hub for that run and keeps the saved remote choice. A hub switch started while another runs is refused with an error in the picker.
- Settings > Hub (`HubSettings.tsx`, desktop only) calls `hub_set_choice`. The main process checks the remote hub with `GET /api/health` and the Bearer token, then `switchHub` in `index.ts` stops or starts the local hub and reloads the window.
- The PWA manifest is `apps/web/public/manifest.webmanifest`. The hub still answers it before auth, for iOS.
- `apps/web/e2e-desktop/` drives the real unpackaged Electron app with Playwright's `_electron` (`pnpm --filter @band-app/web test:e2e:desktop`, CI job `desktop-macos`). It needs `pnpm build:web` and `pnpm --filter @band-app/desktop build` first, and runs against a throwaway HOME with a random `webServerPort`: the app kills whatever listens on that port, so never point it at 3456. With `BAND_DESKTOP_EXECUTABLE` set to a packaged `Band` binary (`pnpm --filter @band-app/desktop package:dir --mac --arm64`, output in `apps/desktop/dist-builder/mac-arm64/Band.app/Contents/MacOS/Band`) the same specs run against the electron-builder output, in the CI job `desktop-packaged-macos`. A packaged run has no scripted ACP agent, because the hub starts it as `process.execPath <script>`, which in a packaged app launches a second Band that frees the hub's port. The chat-reply step skips there. The folder picker is tested by stubbing `dialog.showOpenDialog` in the main process and calling the `pick_folder` IPC; the native sheet itself stays untested.

## Architecture: browser profiles

A browser profile is a separate cookie jar for browser-pane tabs: one Electron session partition per profile (`persist:band-browser-profile-<id>`, see `apps/desktop/src/browser/profiles.ts`). The built-in Default profile is `null` everywhere and keeps the original `persist:band-browser` partition.

- The web server stores only metadata: the `browser_profiles` table, each repo's default profile (`repo_browser_profiles`), and each tab's `profileId` in its `panel_states` blob. `browsers.create` without a `profileId` uses the repo default. `browsers.setProfile` switches a tab and makes that profile the repo default.
- Chrome import reads Chrome data only in the desktop app (`apps/desktop/src/browser/chrome-import/`). The import dialog (`ChromeImportDialog.tsx`, "Import from browser…" in the pane's profile menu) lists Chrome's profile names from `Local State` and shows a "close Chrome" hint while Chrome's `SingletonLock` points at a live process. The user toggles cookies and browsing history and clicks Import. The desktop then reads every selected DB from a private copy (`snapshot.ts`) before writing anything; a copy that SQLite reports as busy, locked or malformed fails the whole import with `ChromeDataLockedError`. Cookies are decrypted with the "Chrome Safe Storage" key (`security find-generic-password`, the macOS Keychain prompt) and written into the Band profile's partition; their values never cross IPC, reach the web server, or get logged. History entries (the most recent 5,000 http(s) URLs) go back to the renderer, which stores them in the tab's worktree history with `history.import`, merging with rows already there. Saved passwords aren't imported, because Band's browser has no password store or autofill. Importing a Chrome profile again re-imports its cookies into the Band profile with the same name (`<Chrome name> (Chrome)`) instead of creating another one, and `browserProfiles.create` refuses a name that is already taken, ignoring case (409).
- A pane's `<webview>` sets its `partition` from the tab's profile (`partitionForProfile` in `apps/web/src/lib/browser-webview.ts`, mirrored in `apps/desktop/src/browser/profiles.ts`). `guest-policy.ts` admits only the Default and profile partitions, and the guest manager prepares each session (`band-action://` handler, no `file:`) when its first guest attaches.

## Architecture: plugins

GitHub features live in a bundled, in-process plugin (`plugins/github/`), following the plugin architecture plan in `docs/architecture/plugins.md`. Band loads no third-party code.

- `packages/plugin-api` holds the contract: the `band-plugin.json` schema (`manifest.ts`), the provider interfaces the core owns (`providers.ts`: `ReviewProvider`, `ChecksProvider`, `ReviewAction`, `WorktreeReview`), the server API (`server.ts`, `definePlugin`, `workers.call`, `tools.register`), the worker API (`worker.ts`, `defineWorkerPlugin`) and the client contributions (`client.tsx`, `defineClientPlugin`, `ClientPluginHost`). A Biome override (`plugins/**` in `biome.json`) lets a plugin import only `@band-app/plugin-api`, `@band-app/ui` and its own dependencies, never `apps/*` or another `@band-app/*` package.
- The server half is listed in `apps/hub/src/server/services/bundled-plugins.ts` and run by `PluginHost` (`plugin-host-service.ts`). It activates a plugin on `onStartup` or on the first provider lookup for a matching `onRepoRemote:<host glob>`, skips ids in `plugins.disabled` in `~/.band/settings.json`, and contains a plugin that throws. `ReviewService` resolves a worktree and asks the matching provider. The tRPC surface is `reviews.forWorktree`, `reviews.provider` (the provider for a worktree, no forge command), `reviews.runAction`, the wrappers `reviews.merge` and `reviews.rerunChecks` (kept for the mobile app), and `plugins.list`.
- Providers return plain JSON and the core draws it. The Checks tab is the core's (`apps/web/src/components/review`, listed by `useWorktreeSideTabs` in `plugins/use-plugin-slot.ts`): it shows when `reviews.provider` finds a provider for the worktree, keeps the test id slug `github-pull-request`, and takes the forge's name and the Fix prompt's `fixHint` from the provider. A review lists `actions` (id, label, icon from a fixed set, placement `header` or `check`, args, confirm text, disabled reason). The core draws them and calls `reviews.runAction`. GitHub offers `merge` (one action per method, group `merge`), `rerun-job`, `rerun-failed` and `ready` (`gh pr ready`), and `gh` subcommands must be on the allowlist in `_utils/worktree-gh.ts`. The `worktree.sideTabs` slot and `ClientPluginHost` stay for client halves, and no bundled plugin has one.
- The GitHub plugin's review data is the branch's pull request with the checks on its head commit, or the CI jobs on the branch head when there is no PR. It gets both from one `gh api graphql` query (`plugins/github/src/server/checks-query.ts`). `BAND_GH_BIN` overrides the `gh` binary and is read on every call; tests point it at `apps/hub/tests/fixtures/gh-stub-bin.mjs`, which forwards to the Express stub in `gh-stub.ts`. A fake `gh` on `PATH` would not work, because `/opt/homebrew/bin` and `/usr/local/bin` are always prepended.
- Change signal. `BandServerApi.reviews.changed({ repo, branch?, number? })` (`packages/plugin-api/src/server.ts`) tells the core a review changed on the forge. `ReviewSignalService` (`services/review-signal-service.ts`) maps it to the worktrees whose repo `remoteKey` is `host/owner/repo` and whose branch matches (all of the repo's worktrees when no branch is given) and sends one `review-changed { worktreeIds }` status event, coalesced over 1 s. The GitHub plugin's subscription source fires it (`plugins/github/src/server/subscriptions.ts`): from `parseDelivery` after the signature check, for `pull_request`, `pull_request_review`, `pull_request_review_comment`, `issue_comment`, `check_run`, `check_suite` and `workflow_run` whether or not a subscription exists (`reviewTargetOf`), and from `poll` when it sees a new comment or a new CI verdict. `ReviewService.runAction` fires it after an action succeeds. `useWorktreeReview` refetches on the event for its worktree, and `PullRequestPanel` polls every 30 s while checks run and every 180 s otherwise, as a fallback for a hub with no webhook. Mobile keeps its own polling. Tests: `apps/hub/tests/review-changed-signal.test.ts`, `apps/web/e2e/pr-checks-review-signal.spec.ts`.
- The worktree card's PR badge (`dashboard/components/PullRequestBadge.tsx`) is stored by `branch-status-poller.ts` in the core. The batched query also returns each branch's PR (open first, then the latest merged, then the latest closed; on the default branch only an open one), stored in `branch_statuses.ci_pr`. The badge is the PR number colored by CI state: red failing, yellow pending or running, green passed, gray with no checks or only cancelled ones, violet merged, struck-through gray closed. A branch without a PR shows the older CI icon, or nothing without checks. Hovering or keyboard focus opens a popover with the title, status, "Open on GitHub" and "Copy link"; a click opens the Checks tab (`dashboard/lib/checks-tab.ts`). The poller queries on its first tick too. It asks `pluginHost.branchStatusProviderFor(repo)` for one `getBranchStatuses` call per repo and checkout (a `BranchStatusProvider` in `plugin-api`), and the GitHub plugin's batched GraphQL query (`plugins/github/src/server/branch-query.ts`) runs `gh` through the core's `ghRunner`, which honors `BAND_GH_BIN`. With the GitHub plugin in `plugins.disabled` the poller never runs `gh`, so rows show neither the PR badge nor the CI icon. Step 1 of the plan's migration (the badge in the plugin) is done; the poller keeps the cadence, battery rules and the once-per-failure log throttle.

## Architecture: plugin worker half and the simulator

## Architecture: worktree groups

A group is a hub entity that collects worktrees across repos and hosts (`worktree_groups { id, name, color, sort_order, created_at }`, `infra/db/queries/worktree-groups.ts`, `services/worktree-group-service.ts`). A worktree is in at most one group, named by `worktrees.group_id`. It replaced the repo labels: `repos.label` and `settings.labels` are gone.

- Writes. Only `RepoQueries.setGroup` writes `group_id`, like the `origin_*` columns: `saveAll` copies it from the rows it replaces, and `repos.list` carries it through the rebuilt worktree list. `CheckpointService.restoreFrom` sets it on the restored copy, so a move, restore or continuation keeps the group. Deleting a group nulls the column for its worktrees and never touches the rows.
- Default group for a new worktree (`WorktreeService.create`): an explicit `groupId` (null means none), else the origin worktree's group, else none. The web sends the group the sidebar is filtered to. A replayed placement request keeps the settled `groupId`.
- API: `groups.list | create | update | remove | reorder`, `worktrees.setGroup { worktreeId, groupId | null, withChildren? }` (`withChildren` moves the whole origin subtree) and `groupId` on `worktrees.create`. `repos.list` returns `groups` and a `groupId` per worktree. Mutations emit `worktree-origin-changed`, which refreshes the sidebar.
- Agents. The relay allows `groups.list` and `worktrees.setGroup` for a worktree on the caller's host, and refuses `withChildren` (it would move worktrees the relay never checked). `groups.create | update | remove | reorder` are refused by the relay and left out of the MCP endpoint, so an agent assigns worktrees but does not change groups.
- Migration `worktree_groups`: copies each repo's label id into its worktrees' `group_id`, drops `repos.label` and renames the client-state keys (`band.repos-list.group-filter`, `collapsed-groups`, `group-last-worktree`, `band.mobile.group-filter`). `WorktreeGroupService.convertLegacyLabels` runs first in `runFirstTimeSetup`: it creates a group for each entry of `settings.labels` with the same id, name, color and order, clears ids that name no group and removes the `labels` key. It is idempotent.
- Titles. `worktrees.title` (null for none) is written only by `RepoQueries.setTitle`, and `saveAll` and `CheckpointService.restoreFrom` carry it like `group_id`. `worktrees.setTitle { worktreeId, title | null }` trims, treats blank as null, rejects more than 100 characters with 400 and emits `worktree-origin-changed`. The relay allows it for a worktree on the caller's host and the MCP endpoint lists it. `repos.list` returns `title` per worktree. The web card shows `title ?? name` with "Rename…" and double-click, `worktreeDisplay` uses it for headers and dialogs, and the mobile row menu has Rename…. CLI: `band worktrees rename <id> <title> | --clear`. Tests: `apps/web/e2e/worktree-rename.spec.ts`, `trpc.test.ts`, `worktree-groups-relay.test.ts`, `worktrees_rename_*` in `apps/cli/tests/integration.rs`, `apps/mobile/tests/renaming.test.ts`.
- UI: the sidebar's default view is Groups (a section per group with its origin tree, then Ungrouped), with drag onto a header, the header menu and the group filter. Settings > Groups manages them. CLI: `band groups list | create | rename | remove`, `band worktrees set-group`, `band worktrees create --group`.
- Tests: `apps/hub/tests/worktree-groups-migration.test.ts`, `worktree-groups-relay.test.ts` (real worker), the group cases in `checkpoints.test.ts` and `trpc.test.ts`, `apps/web/e2e/sidebar-groups.spec.ts`, `settings-groups.spec.ts`, `groups_*` in `apps/cli/tests/integration.rs`.
- Not done yet: several groups per worktree, nested groups, and group management in the mobile app.

## Architecture: origin links

A worktree records where it was started from (plan section 15, guide: `docs/origin-links.md`). `worktrees.origin_worktree_id`, `origin_chat_id` and `origin_terminal_id` hold plain ids. `RepoQueries.saveAll` rewrites both tables and so copies these columns from the rows it replaces, ignoring its snapshot. ## Architecture: agent sessions

An agent session is one run of a coding agent (issue #682). Its mode is how it is displayed: `gui` runs in a chat pane over ACP, `tui` runs the agent's CLI in a terminal. A session keeps its mode for its whole life.

- Rows live in the `agent_sessions` table. `services/agent-session-registry-service.ts` owns them and emits `agent-session-created`, `agent-session-updated` and `agent-session-ended`. A chat's `activeSessionId` is its session's `providerSessionId`. A session ends when its chat or terminal is removed. `services/agent-session-service.ts` is a different thing: it runs the ACP process behind a chat.
- A chat's ACP process is never stopped for being idle, so the agent's own timers (`ScheduleWakeup`, `CronCreate`, `Monitor`, background shells) fire as they do in a terminal. It ends when the chat is stopped or removed, its worktree is removed, the agent exits, or the hub or worker shuts down. `BAND_AGENT_IDLE_TIMEOUT_MS` is an opt-in: with a positive value, a process that sends nothing for that long is stopped and the next prompt reattaches its session. Every update restarts the countdown, and work that lives in the process holds the stop off (`services/_utils/agent-pending-work.ts`): AIR `async_task_*` updates for background Bash, Monitor and workflows (Band lists the `asyncTasks` capability and takes those updates off the stream before the SDK's validator, in `acp-agent-process.ts`), and `ScheduleWakeup` and `CronCreate` tool calls. Each hold lapses after at most 8 hours.
- `services/agent-launch-service.ts` starts agents (`agentSessions.launch`, `worktrees.create` with a prompt). The CLI reaches it through `band agents launch` and `band agents list`. An agent with no TUI invocation (cursor-cli) falls back to `gui`, and the response carries a `notice`.
- Each browser stores its own mode in localStorage (`band.agent-mode`, `dashboard/lib/agent-mode.ts`) and sends it on every launch. With no mode sent, the server uses `agents.defaultMode` from `~/.band/settings.json`. Boot copies the older `cli.defaultVia` into it once and leaves the old key, because the CLI still reads it.

## Architecture: chat ownership

A worker started with `--own-chats` (`BAND_WORKER_OWN_CHATS=1`, the hello capability `chatOwnership`; the desktop app's bundled worker installs with it) runs the chats of its own worktrees and replicates them to the hub (ADR `docs/architecture/chat-ownership.md`, guide `docs/chat-ownership.md`). `chats.ownerHostId` (in the chat's `panel_states` JSON, written only by `ChatService.setOwner`) names the owner; undefined is the hub.

- Shared pieces live in `packages/chat-runtime`: the `chat_events` table (`log-schema.ts`, re-exported by the hub's schema), `ChatEventQueries` over any drizzle db (`log.ts`, with `insertRows`, `readChat`, `readIdRange` and `reserveIdBlock`), `rowsToEvents`, `AcpAgentProcess`, `PendingWork`, the SSE writer, `turnUsage` and the session state read from a log. The hub's `infra/db/queries/chat-events.ts` binds the queries to its db.
- Worker (`apps/worker/src/chats/`): `store.ts` (`<state dir>/chats.db` on `node:sqlite`, loaded lazily), `runtime.ts` (one chat's ACP session, a smaller port of `agent-session-service.ts`), `turns.ts` (turns and the queue, a port of `task-service.ts`), `owner.ts` (link methods, seeding, replication, forwards) and `local-http.ts` (the chat routes, the hub's wire format, served by the direct listener in `direct.ts` on its token). The web side is `apps/web/src/lib/direct-chat.ts`: a `HubFetch` for the chat hook's stream, sends and history that tries the worker first. A change to turn handling goes in both runtimes.
- Link (`packages/link/src/chats.ts`): hub to worker `chat.own | forward | release | setConfigOption | listSessions`; worker to hub `chat.replicate | idBlock | history | launch | sessionState` and the notifications `chat.live.changed | chat.transient | chat.activity`. Large row batches go over a channel (`payload.ts`).
- Hub (`services/chat-ownership-service.ts`): `ownerFor` hands a chat over at a clean point (no task, `agentSessionService.isActive` false, empty hub queue) after stopping the hub's process; `taskService.submitTask | submitOrQueueTask | abortTask | cancelTask | getTask | hasRunningTask`, `agentSessionService.ensureSession` (never runs an owned chat), the answers, `setConfigOption`, `listSessions`, the pending and work checks, the queue router and `api/chat-events.ts` consult it. Forwards go through the `chat_forwards` outbox (delivered in order on connect, rerouted when the chat moved). Replicated rows are inserted by id and only new ones act (`ingest`: tasks, status, summary, `emitTurnEnded`). Rows for a chat the worker no longer owns go to `chat_event_holds`. `chat-submit` skips the follow-the-work gate for an owned chat, so a message to an offline owner waits.
- Every worker registers `lifecycle.exportSessions | importSessions` (before this only ephemeral ones did), so checkpoints carry agent session files on static workers too.
- Tests: `apps/hub/tests/chat-ownership.test.ts` (real hub, an owning and a plain `band-worker`, scripted ACP stub; S2 to S6, S9), `chat-ownership-direct.test.ts` (the direct send and stream, token scope, a cut link within the lease through `helpers/cuttable-proxy.ts`), the chat step of `apps/web/e2e-desktop/desktop-direct-path.spec.ts` (the real app sends and streams on 127.0.0.1; the fake launchd passes `BAND_TEST_ACP_*` to the worker), `apps/worker/tests/service.test.ts` (`--own-chats` in the service file).
- A worker whose hub lease ran out (#905) starts no agent for an owned chat either (`assertMayRun`). Whether owned chats should keep running while fenced is an open decision.
- Not done yet: the restore guard and the diverged copy shown in the UI (the second half), and moving an existing desktop install to `--own-chats` without adding This Mac again.

## Architecture: subscriptions

`subscriptions.create | list | remove | events` (`apps/hub/src/server/api/subscriptions/router.ts`) are tRPC procedures, so the MCP endpoint lists them as `band_subscriptions_*`. A call carrying `x-band-chat-id` and `x-band-worktree-id` headers (an agent's `BAND_CHAT_ID` and `BAND_WORKTREE_ID`) can omit both ids. ACP chat agents get both variables; terminals get only `BAND_WORKTREE_ID`, since a terminal has no chat.

- Webhook source: `create` with `source: "webhook"` returns a token once and stores only its SHA-256 (`subscriptions.config`). `POST /api/hooks/:id` is answered before the server's auth check, takes the token in `X-Band-Webhook-Token` or `Authorization: Bearer`, and compares hashes in constant time. 404 for an unknown id, 401 for a bad token, 202 otherwise.
- Timer source: `source: "timer"` with `at` (epoch ms, one-off, forced to `maxWakeups: 1` so it removes itself after delivery) or `cron` (croner syntax, optional seconds field; it ends after `maxWakeups` fires, default 50, or at the 180-day cap). Timers are re-armed from the database in `SubscriptionService.start()`.
- GitHub source (the plugin's `SubscriptionSourceProvider` in `plugins/github/src/server/subscriptions.ts`, `webhook.ts` and `check-runs.ts`, driven by `services/subscription-source-service.ts` in the core): `create` with `source: "github"`, `repo` and exactly one of `pr` (comments, reviews, review comments, lifecycle; key `github:pr:owner/repo#N`) or `branch` (CI; key `github:ci:owner/repo@branch`, kinds `["ci"]`). `POST /api/hooks/github` is answered before auth. The core reads the secret in `BAND_GITHUB_WEBHOOK_SECRET` or `~/.band/github-webhook-secret` (`infra/subscriptions/webhook-secret.ts`, generated on the first registration, mode 0600) and the provider checks `X-Hub-Signature-256` against it in constant time, because the scheme is GitHub's; 401 for a bad or missing signature, 202 otherwise, and 404 when `github` is in `plugins.disabled`. The plugin fires `reviews.changed` for each verified delivery. Repeated `X-GitHub-Delivery` ids are dropped. A completed `check_run`, `check_suite` or `workflow_run` makes the hub fetch the commit's check runs with `gh api` (`BAND_GH_BIN`); it pages through them 100 at a time and delivers one event per commit and verdict only when no check is pending. A failure names the failed checks; with no failure, a cancelled run is reported as its own `cancelled` outcome. The first subscription for a repo registers the webhook with `gh api repos/{o}/{r}/hooks --input -` (the body, secret included, goes over stdin, never argv) when `BAND_PUBLIC_URL` or the running tunnel gives a public origin (the tunnel's `?token=` is dropped); otherwise `webhook.status` is `waiting-for-url`.
- Guards (`SubscriptionService.ingest`, `services/pushed-sha-service.ts`): without `maxWakeups` a CI subscription gets 10 and any other 50, and every subscription expires within 180 days. After a successful `worktree.gitPush` or `worktrees.gitPush`, Band records the branch head in `pushed_shas`. A `push` or PR `synchronize` event whose commit is in that table is flagged `self` and recorded with `dropped_reason = "self"`, not delivered, so an agent's own push does not wake it. A CI failure on a commit in the table is delivered as a fix trigger. A CI failure on any other commit carries `fix: false`, and the message says the commit is not Band's and must not be fixed. Comments, reviews and review comments are delivered only from `config.allowedSenders` (`create` takes `allowedSenders` with `pr`; the default is the repo owner plus the authenticated `gh api user` login, and a list replaces it, ignoring case). Other senders' events are recorded with `dropped_reason = "sender"`.

- Polling fallback (`services/subscription-poll-service.ts`, with the GraphQL query and parsing in `plugins/github/src/server/pr-activity.ts`): the branch-status poller calls `poll()` on its CI ticks, so it follows the activity cadence and needs the GitHub plugin enabled. It serves GitHub subscriptions whose repo has no registered webhook (`webhook.status` is `waiting-for-url` or `failed`). When the hub has a public URL by then, it first tries to register the webhook, and a repo with any `registered` subscription is no longer polled. A PR subscription reads new comments, reviews and review comments with one GraphQL query per repo, from a cursor in `subscription_cursors` (the newest `createdAt` seen, starting at the subscription's creation time). A branch subscription reads the head commit's check runs and delivers through the same `aggregateChecks` as the webhook path. The provider splits a repo's subscriptions into units (`pollUnits`) and reads one (`poll`) from each subscription's cursor; the core keeps the cursors, the budget and the backoff. One poll makes at most 6 `gh` calls (a branch whose check pages exceed what is left waits for the next poll), taking turns across repos and branches, and a source that fails is skipped for 2, 4, 8 and then 16 polls.

## Architecture: cronjobs

A cronjob belongs to one worktree (`cronjobs.worktree_id`, also its `file_key`), never to a repo. For a repo's main branch the job names the default-branch worktree. `services/cronjob-service.ts` owns the scheduler and the dispatch, `infra/db/queries/cronjobs.ts` the rows.

- Fields. `worktreeId` is required on `cronjobs.create` (a repo `scope` or a missing worktree answers 400, and the worktree must exist). Optional `agent` is a `settings.codingAgents[].id` (unknown ids are refused) and `sessionId` is the agent's provider session id, a chat's `activeSessionId`. A `sessionId` with `via: "terminal"` is refused, and so is an `agent` that differs from the agent of the chat that already has the session. `cronjobs.update` takes the same fields (`null` clears `agent` and `sessionId`) and `worktreeId` moves the job. `lastRunMessage` holds the reason of a failed run or of a job the boot migration disabled.
- Dispatch (`dispatchToChat`). Without a `sessionId` the prompt goes to the job's `band:cronId` chat, created with the job's `agent`. With one it goes to the chat in the worktree whose `activeSessionId` matches, whatever its labels. With none, a chat is created with the `band:cronId` label and that active session, and `agentSessionService.ensureSession(chatId, "prompt", { strictSession: true })` attaches it with `session/resume` or `session/load`. Strict mode makes `attach` throw instead of falling back to a fresh session. On failure the run is recorded `failed` with the reason (`CronjobDispatchError`, 412 from `cronjobs.trigger`), a chat created for this fire is removed, and the next fire tries again. A chat that is mid-turn queues the prompt (`submitOrQueueTask`), so a fire is no longer recorded `skipped` for a busy chat. A terminal job that is still running still is.
- Boot migration (`CronjobService.migrateRepoJobs`, called from `runFirstTimeSetup` after the worktree sync and before `cronjobService.start`). Each job still scoped to a repo moves to `toWorktreeId(repo, defaultBranch, listedMainHostOf(repo))` keeping its id, schedule, prompt, `via`, enabled flag and chat. With no listed default-branch worktree, or no repo, it is disabled with `lastRunMessage` set. Nothing is deleted, and a second run changes nothing. The `scope` column stays and reads `worktree` for every job. `rekeyWorktreeRows` moves `file_key` along with `worktree_id`. `removeForRepo` clears the jobs of a repo's worktrees when the repo is removed.
- Surfaces. `band cronjobs create --worktree <id> [--agent] [--session-id]`, `update <key> <id> [--worktree] [--agent] [--session-id | --clear-session]` (`--repo` and `--scope` fail with a message). The UI form is `CronjobsPageContent.tsx` (repo, then worktree with the default branch first, agent, session id).
- Tests: `apps/hub/tests/cronjobs-sessions.test.ts` (ACP stub, request log), `cronjobs-worktree-migration.test.ts` (seeded pre-change DB, then a real boot), `cronjobs.test.ts`, `apps/web/e2e/cronjobs-worktree.spec.ts`, `cronjobs_*` in `apps/cli/tests/integration.rs`.

## Architecture: battery saver

On battery, or with the window blurred or hidden, Band slows its polling and stops continuous repaint work. Plugged in and focused, nothing changes.

- Client power state (`apps/web/src/lib/power-state.ts`): battery comes from Electron's `powerMonitor` (IPC `get_power_state` and the `power-state-changed` event) or, in a plain browser, the Battery Status API. It sets `data-power="saver"` (battery, blurred or hidden) and `data-on-battery` on `<html>`. Under `data-power="saver"`, and under `prefers-reduced-motion`, `globals.css` pauses the infinite animations (`animate-spin`, `animate-pulse`, `animate-status-pulse*`, `tool-shimmer`, the browser loading bar). On battery the desktop window drops its vibrancy (`applyPowerToWindow`, `services/window-power.ts`) and the sidebar paints solid. A focused terminal's cursor stops blinking, a parked terminal drops its output instead of draining it (the snapshot replays on show), and hidden terminals stay warm for 10 s / 1 min instead of 30 s / 5 min. `usePollInterval` pauses the changes, diff and `workers.list` polls while blurred and slows them on battery.
- Activity (`activity-reporter.ts`, `services/client-activity-service.ts`): every UI, in the desktop app or a browser, reports `active | idle | background` with its own client id through `services.setActivity` on change and every minute (`releaseActivity` on page hide). The hub keeps the most active live client, drops one that is silent for 3 minutes (`BAND_ACTIVITY_TTL_MS`), and uses `idle` with no live client (`BAND_ACTIVITY_DEFAULT` overrides that level). The branch-status poller and the terminal title poller follow it. The desktop main process no longer reports; the old `activity-monitor.ts` only worked for a local hub.
- Worker power (`packages/host-local/src/process/power.ts`): `host.info` carries `onBattery` (`pmset -g batt` on macOS, `/sys/class/power_supply` on Linux, unknown elsewhere, cached 60 s, `BAND_POWER_STATE=battery|ac` pins it). The poller reads it once a minute per worker. A worktree on a battery worker is polled every 60 s whatever the clients report, never `git fetch`ed, and queried for CI every 10 minutes.
- `host.fs.watch` takes `ignore` (single path segments); the hub passes its ignore list so `node_modules`, `.git` and build output never cross a worker's link.
- Tests: `apps/hub/tests/client-activity.test.ts`, `host-battery-polling.test.ts` (two real workers), `packages/host-local/tests/power.test.ts` and `watch-ignore.test.ts`, `apps/desktop/tests/window-power.test.ts`, `apps/web/e2e/power-saver.spec.ts`, `apps/web/tests/power-policy.test.ts` (pure functions, no state to fake). `BAND_ACTIVITY_DEFAULT` and `BAND_POWER_STATE` are production settings read on every call; the hub vitest config sets them to `active` and `ac` so servers with no UI keep their 5 s poll and a fixed power state, beyond TEST-1's carve-outs.
- Exceptions: `packages/host-local/tests/power.test.ts` and `watch-ignore.test.ts` call `parsePmset`, `readLinuxPower`, `isOnBattery` and `LocalHost.fs.watch` directly against temp dirs, because a worker's real power source and its link are not reachable from a test (the hub test covers the whole path with `BAND_POWER_STATE`). `apps/desktop/tests/window-power.test.ts` covers only `applyPowerToWindow`; the `on-ac` and `on-battery` forwarding in `main/index.ts` and the `get_power_state` handler need the Electron runtime and stay untested, as with `window-state.test.ts`.
- Not done yet: Windows power detection, event-driven git status.

## Architecture: agent status states

A worktree's agent status is one of `working`, `monitoring`, `question`, `done`, `failed` and `idle` (`AgentHookStatus`, `packages/coding-agent/src/types.ts`). `worktree_statuses.agent_status` is derived from the rows of `worktree_status_sources` (`chat:<id>`, `hook:<session>`, `manual`) with priority question > failed > working > monitoring > done > idle (`state.ts`). Hub boot makes everything but `done` and `failed` idle. `statuses.clearNeedsAttention` turns `done` and `failed` sources into `idle` and never clears a `question`.

- Chats: `services/chat-status-service.ts` sets the status. `task-service` calls `beginBandTurn` and `endBandTurn` (`end_turn` is `done`, or `monitoring` while the chat's `PendingWork` has holds, `refusal`, `max_tokens`, `max_turn_requests` and a thrown prompt are `failed`, a stopped turn is `idle`). A permission or form request is `question` and its answer `working`. The Claude adapter sends no marker when a turn it started itself ends (a cron, `ScheduleWakeup`, a task notification), so updates outside a Band turn show `working` and the chat settles after `BAND_AGENT_QUIET_MS` (default 10 s) of silence. A background task ending (an AIR `async_task_state_update`) or the soonest hold lapsing moves `monitoring` to `done`.
- Hooks: `packages/coding-agent/src/hook-status.ts` maps each Claude Code event (`mapClaudeCodeHookStatus`, `foldSubagents` for subagents that outlive the main `Stop`). `band notify` never fails: it prints nothing, exits 0 and returns within one second. A hook matches a worktree by worker and cwd (`resolveWorktreeIdByCwd(cwd, hostId)`); the worker relay writes the worker's id into `statuses.notify`.

## Architecture: account usage

The footer's usage popover (`AccountUsagePopover.tsx`) shows the Claude and Codex limits of every account logged in on an online worker. Each worker reads its own logins, so no token leaves it.

- Readers (`packages/host-local/src/usage/`): `claude-usage.ts` takes the token from `$CLAUDE_CONFIG_DIR/.credentials.json` or `~/.claude/.credentials.json`, then on macOS from the Keychain item `Claude Code-credentials` (this can prompt), and calls `api.anthropic.com/api/oauth/usage`. `codex-usage.ts` takes `tokens.access_token` from `$CODEX_HOME/auth.json` and calls `chatgpt.com/backend-api/wham/usage`. The identity is the email from `~/.claude.json` or the Codex `id_token`, the plan comes from the credentials or the response. `BAND_CLAUDE_USAGE_URL`, `BAND_CODEX_USAGE_URL` and `BAND_USAGE_KEYCHAIN=off` are read on every call and let tests point at a stub. A worker caches an answer for 3 minutes (30 s for no login, 1 minute for an error, 5 minutes after a 429) and shares one request between concurrent calls.
- `Host.agentEnv.accountUsage({ refresh })` returns one `AccountUsage` per provider and never rejects. The worker method is `agentEnv.accountUsage` (passive for the idle clock).
- Hub: `accountUsage.list { refresh? }` (`services/account-usage-service.ts`) asks every online worker, merges rows of the same account (case-insensitive email) into one that names its workers, and groups failures into `problems` ("Not logged in on contabo"). The MCP endpoint and the relay leave it out.
- Tests: `packages/host-local/tests/account-usage-mapping.test.ts`, `apps/hub/tests/account-usage.test.ts` (real hub and four workers, `fixtures/usage-stub.ts`), `apps/web/e2e/account-usage.spec.ts`. Not done yet: `band usage`, other providers.

## Architecture: center layout

The center area of a worktree and the split panes of a terminal tab run on Band's own layout code in `apps/web/src/components/layout/`. It replaced the dockview library.

- `serialized.ts` types and parses the saved shape. `model.ts` is the pure model (`LayoutApi`, `LayoutGroup`, `LayoutPanel`): a tree of splits whose leaves are groups of tabbed panels, with add, remove, move, split, resize, maximize, `toJSON` and `fromJSON`. It has no DOM, and `apps/web/tests/layout-model.test.ts` drives it directly. `LayoutView.tsx` renders it: tab strips, drag with `@dnd-kit/core`, sashes, drop zones. `saved-layout.ts` holds the pure fixes applied to a saved blob before loading it (legacy edge groups, unknown panel kinds).
- The saved shape is the JSON dockview's `toJSON()` wrote, so layouts users already have keep opening, and an older Band build on the same device opens what this one writes. It is stored under `band:dockview-layout-v9:<worktreeId>` (plus Band's `maximizedGroup`) and, for a terminal tab's panes, `band:term-split:<worktreeId>:<leafId>`. The parser ignores fields it does not know. `band:center-tabs:<worktreeId>` is Band's own tab list and did not change. Fixtures in `apps/web/tests/fixtures/layouts/` were captured from dockview 6.0.6.
- Sizes are weights per child. The browser lays groups out in percent from the weights (`computeGeometry`), and `toJSON` writes pixels of the last container size. A group never moves in the DOM when the tree restructures, because groups are siblings under the root and keyed by id.
- A panel's content renders into `panel.element` through a portal, and the element moves with the panel between groups. The selected panel's element is in its group's content area. An `always` panel (terminals, browsers) stays attached and gets `display: none` while unselected, so a webview keeps its guest. Every other unselected panel is detached, with its React tree still mounted.
- Tabs sit in a plain flex list with native `overflow-x: auto` and `overscroll-behavior-x: contain`. Only a mostly vertical wheel is turned sideways. A mouse or pen press selects a tab at once. A touch selects on click, so a swipe scrolls without switching tabs. Tabs are `role="tab"` in a `tablist` with arrow-key navigation.
- A sash drag sets `data-band-layout-resizing` on `<html>` (`lib/layout-resizing.ts`). `terminal-cache.ts` skips its refit while it is set and fits once when the drag ends, so a PTY gets one resize, not one per pixel.
- Test hooks are `data-testid`s: `layout-root` (with `data-layout-kind="center"` or `"split"`), `layout-group`, `layout-header`, `layout-tab-list`, `layout-tab` (`data-selected`, `data-panel-id`), `layout-header-void`, `layout-sash`, `layout-drop-indicator`. `apps/web/e2e/pages/CenterLayout.ts` and `CenterTabStrip.ts` wrap them.
- Styles are `components/layout/layout.css`, with theme tokens only.
- Not built: floating groups, popouts and an overflow tab list. Dockview had them and Band never used them.

## Architecture: client state

Small UI state (center tabs, drafts, panel widths, collapsed repos) lives on the web server so the phone and the desktop show the same thing. localStorage stays the synchronous read cache.

- The server keeps rows in `client_state`, keyed by `(key, scope)`. It accepts only the keys listed in `shared/client-state-keys.ts`, takes a key's worktree from the key, and refuses writes for a worktree that no longer exists. Scope `all` is one value for every device; `desktop` and `mobile` hold one value per device type (viewport of at least 1024 px, or the desktop app, counts as desktop). `services/client-state-service.ts` and the `clientState.*` router own them. A write names the version it was based on, and a stale one is refused and answered with the current row. A delete leaves a tombstone, which `list` doesn't return. Accepted writes go out as `client-state-changed` on the status stream. Deleting a worktree removes its rows.
- The dashboard writes through `clientStorage` (`lib/client-state.ts`), which writes localStorage and pushes the key 500 ms later. `shared/client-state-keys.ts` lists the synced keys and their scope; any other key stays on the device (for example `band.agent-mode`, per device on purpose). A synced key can split into several entries: `band-tab-state:<ws>` shares view mode and language and keeps scroll per device type.
- Unsaved file edits and untitled buffers are shared too, one key per file (`band-unsaved:<ws>:<path>`). Last save wins. When another device's copy of a file arrives while this device has edits of its own, the file leaf shows a banner offering to load theirs or keep its own; with no local edits the leaf just loads the new copy. Untitled numbers start above every `untitled:N` in the shared tab list, so two devices don't share a buffer by accident.
- Hydration runs before first read: `ClientStateGate` in `__root.tsx` waits for the global keys, and the center layout's data query waits for its worktree's keys (both give up after 1.5 s so an offline load still renders). A local value the server doesn't have is uploaded, which migrates existing localStorage.
- The center layout shares only which tabs are open, their order and the active tab (`band:center-tabs:<ws>`, `lib/center-tabs.ts`). Its full layout, with splits and sizes, is per device type. While a worktree is on screen, another device's change only opens and closes tabs; order and active tab apply the next time it is shown.
- A load on `/` (every desktop launch, a phone's home-screen icon) reopens the worktree this device type last showed (`band:last-worktree`, `lib/last-worktree.ts`). `ClientStateGate` picks it after hydration and before the shell renders, skips a worktree that no longer exists, and prefers the selected group's last worktree when the two disagree. The desktop window's bounds and maximized / full-screen state live in `~/.band/desktop-window.json` (`apps/desktop/src/main/services/window-state.ts`).
- e2e specs whose tests share one server call `resetClientState(tmpHome)` in `beforeEach`, because UI state no longer resets with each new browser context.

## Architecture: agent daemon

A worker holds the ACP agent process of each hub-run chat in a second detached process, the agent daemon, so a worker update does not stop a running agent (ADR `docs/architecture/agent-daemon.md`). Chats a worker owns (`--own-chats`) and agents on the hub's own machine (the `local` worker) are not covered: their agents stay children of the process that starts them.

- Daemon (`packages/host-local/src/agents/daemon/`, entry `apps/worker/src/agent-daemon.ts` bundled to `dist/agent-daemon.mjs`, started by `apps/worker/src/agents.ts`): built on the daemon kit, run dir `<state dir>/run/agents/` (0700, socket 0600), its own `PROTOCOL_VERSION`, no node-pty. Requests `spawn | attach | ack | write | kill | list | forget`; events `out` (base64 with the byte offset) and `exit`. It keeps every stdout and stderr byte after the last acknowledged offset (`OutputRing`) and stops reading an agent past `BAND_AGENT_BUFFER_BYTES` (8 MiB, read on every chunk), so the agent blocks and nothing is dropped. An exited agent stays for `BAND_AGENT_EXIT_KEEP_MS` (10 minutes) until the hub `forget`s it. `BAND_AGENT_DAEMON=0` turns it off. `AgentHolder` (`holder.ts`) is the worker's connection, with the same build and supersede rules as the terminal backend, and `HeldAgentProcess` is the `AgentStdio` it hands out.
- Worker (`apps/worker/src/methods-agents.ts`): `acp.spawn` replies `held: true` and opens the two channels as before. A channel reset detaches and leaves the agent running. `acp.reattach {agentId, stdout, stderr}` opens fresh channels from the hub's offsets and answers with the daemon's stdin offset. `acp.ack` releases output, `acp.forget`, and `acp.reconcile {keep}` kills held agents the hub does not know that nobody is attached to. The fence, a `blockedPaths` folder (`LeaseGuard.onBlocked`) and a rejected hello (`Worker.killAgents`) kill held agents, `acp.spawn` is refused while fenced, and `uninstall-service` ends the daemon (`stopAgentDaemons`).
- Hub: `RemoteAgent` (`packages/host-remote/src/agent.ts`) wraps a held agent. When the link session is destroyed it detaches instead of exiting: its stdout and stderr iterables wait, stdin is kept, and `WorkerLinkService.onConnected` calls `RemoteHost.reattachAgents()`, which reattaches each agent and then reconciles. The hub acks what it received (250 ms debounce, at once above 1 MiB) and resends stdin past the offset the worker reports. `BAND_AGENT_REATTACH_TIMEOUT_MS` (2 minutes, read on every loss) gives up with exit signal `link-lost`, which is today's fallback (the next prompt starts a process and loads the session). Both 2 minutes and 8 MiB are estimates, not measurements.
- Restart at a clean point: `launchSpecHash` (`packages/chat-runtime/src/acp-agent-process.ts`) hashes command, args, adapter version (`adapter-version.ts`: package version, else file size and mtime), the ACP protocol version and client capabilities, unset names, and each env name with a hash of its value. The relay grant and chat ids are not in it. The hub stores it with the agent. After a reattach `Runtime.checkLaunch` is set, and the next prompt (`restartIfLaunchChanged` in `agent-session-service.ts`, never mid-turn) resolves the launch again and restarts the process when the hash differs.
- Kill at once: `credential-events.ts` carries "login removed, secret replaced or re-chosen" and "vault git credential changed" from the login and vault services to `agent-session-service.ts`, which stops the runtimes that hold the old login (`Runtime.loginId`) or a `GH_TOKEN` (`AgentStdio.ghToken`). Stop, chat removal and worktree removal already stop the runtime.
- When the hub stops, held agents stop too, because only the hub holds their ACP state. Shutdown calls `RemoteHost.stopAgents()` before the worker links close (`start-server.ts`), and the daemon kills an agent no worker watches for `BAND_AGENT_REATTACH_TIMEOUT_MS` plus 2 seconds (a worker restart or a worker with its hub link down, reported with the daemon request `hub`), so a hub crash cannot leave agents running. The daemon also enforces the lease (`lease {ttlMs}` on each renewal).
- Stalled turns (issue #1039). `AgentSessionService.prompt` runs a watchdog: a turn with no agent update for `BAND_TURN_STALL_MS` (5 minutes, read on every turn) while its process exited or its held agent has no link to the worker (`AgentStdio.detached`) ends as failed and closes the process, and `finishTask` then starts the next queued message. 5 minutes is longer than the 2 minute reattach window, so the watchdog only fires for a turn that path did not end, and a live agent in a quiet tool call is never cut off. `RemoteAgent` also asks for a reattach as soon as its output ends without an exit: `LinkSession.notify` drops a message while the socket is down, so an `acp.exit` sent during a cut is lost and no later connect would ask. `finishTask` drains the queue after a stopped or failed turn too, so a message sent while a Stop is still settling starts a turn. Messages queued before the Stop stay paused (`pausedQueues` in `task-service.ts`); only later ones start on their own. Test: `apps/hub/tests/chat-stalls.test.ts`.
- `workers.interruptions` (`AgentSessionService.liveAgents`) lists only agents the restart will end: held agents are left out. `WorkerUpdateButton.tsx` words the dialog accordingly, and "Update all" skips only workers with such agents.
- Not covered: a versioned copy of the adapter before spawn (npm replaces the files in place, #1008), worker-owned chats, the hub's own machine, Windows.
- Tests: `apps/worker/tests/agent-persistence.test.ts` (real `band-worker` killed and restarted, `cat` and shell agents, the cap, reconcile, fence, `blockedPaths`), `apps/hub/tests/agent-daemon.test.ts` (real hub and worker, the ACP stub: S1 to S6 and S8), `apps/web/e2e/update-agents.spec.ts` (stand-in workers that run the stub agent, `held` or not; the dialog and Update all).

## Architecture: Web Server vs Terminal Daemon

Terminal PTYs do not live in the web server. They live in the **terminal daemon** (`apps/hub/terminal-daemon.ts`, bundled to `dist/terminal-daemon.mjs`), a detached process the server launches on the first terminal spawn, so shells survive a server restart (desktop relaunch, auto-update, `pnpm dev` reload, crash). The restarted server reattaches to the same shells, and the browser replays their screens over the unchanged `/terminal` WebSocket.

- `TerminalService` talks to a `TerminalBackend` (`packages/host-local/src/terminals/terminal-backend.ts`). `DaemonTerminalBackend` is the default. `InProcessTerminalBackend` is used on Windows, when `BAND_TERMINAL_DAEMON=0`, and as a fallback when the daemon cannot start; its terminals die with the server. Nothing outside `packages/host-local/src/terminals/` touches node-pty.
- The daemon knows nothing about worktrees, layouts or events. It runs a `TerminalPool` behind a Unix socket (NDJSON, token hello, separate control and stream connections). The wire protocol is in `packages/host-local/src/terminals/daemon/protocol.ts`; bump `PROTOCOL_VERSION` on any change to it that an older peer would misread. A new `ControlNotify` that is safe to ignore (like `hold` / `release`) is the one exception, because a daemon drops notifies it doesn't know and new sessions only start on a daemon of the server's own build.
- Runtime files live in `~/.band/run/` (mode 0700): `terminal-daemon-v3.sock`, `.token`, `.pid`, and `terminal-daemon.log`. If the socket path would exceed the 104-byte `sun_path` limit, the socket moves to `/tmp/band-<uid>/`, named by a hash of the run dir.
- Socket publishing follows orca's endpoint-ownership rules (see the header of `daemon/endpoint.ts`): never unlink a socket you did not create, only a refused or missing connect proves a daemon dead, and a daemon never removes its endpoint on shutdown.
- Output to a server shares one stream socket per server. When that socket holds more than 128 KB, the daemon pauses the PTY of each session that has sent over 4,096 characters since the socket was last empty, and resumes them on `drain`. Floods stop at the shell instead of burying other terminals' echo, and a server is only dropped (at 64 MB unread) when it stops reading entirely.
- Output to a browser is parse-acknowledged (ported from orca). The browser attaches with `flow: true` and sends `{ type: "ack", bytes }` once xterm has parsed output; `packages/worktree-ops/src/output-flow.ts` holds the PTY while more than 256 KB is unacknowledged and releases it below 32 KB, through `TerminalAttachment.setOutputHeld` (in-process: `TerminalPool.holdOutput`; daemon: the `hold` / `release` notifies, one per server). A client that never opted in is paced on `ws.bufferedAmount`, one that acknowledges nothing for 5 s is written off, and a terminal nobody can see (parked, or in a hidden page) acknowledges on receipt so it never pauses a PTY another device is watching. In the browser, `terminal-output-queue.ts` drains visible output in 16 KB slices with at most 128 KB unparsed in xterm. It writes visible output up to the last DEC 2026 end marker and holds only an unfinished frame's tail until its end arrives (or 100 ms, or 64 KB): xterm skips any render while a frame is open, so a TUI redrawing back to back, whose frames arrive as several 1 KB messages, otherwise painted only on xterm's 1 s timeout. Panes get `CLAUDE_CODE_FORCE_SYNC_OUTPUT=1`, without which Claude Code, not recognising the terminal from `TERM_PROGRAM`, repaints the whole screen on every wheel tick instead of scrolling a DECSTBM region.
- Daemon kit (`packages/host-local/src/daemon-kit/`): the parts of a daemon that host nothing in particular. `endpoint.ts` (endpoint ownership), `protocol.ts` (NDJSON framing, hello, run-dir file names, exit codes), `private-files.ts`, `connection.ts` (client sockets, handshake, `retireDaemon`), `launch.ts` and `exit-records.ts`. The terminal daemon passes its own name, `PROTOCOL_VERSION` and exit-code text. A Biome rule bans node-pty, xterm and `terminals/` imports in the kit.
- Server shutdown only disconnects. A session ends when its tab is closed, its worktree is deleted (or found deleted at boot), or its shell exits.
- The daemon exits on its own, following orca's daemon: when it has no shells, no spawn in flight and no connection, the moment its last server disconnects (or 2 minutes after launch if none ever connects). If its socket is replaced or removed, it drains: no new sessions, existing shells keep working over already-open connections, and it exits when the last one ends. If `~/.band/run` disappears, it kills its shells and exits.
- New sessions only start on a daemon of the server's own build (issue #652). The build ID is the size and mtime of the daemon entry file. When the endpoint is served by a daemon of another build, or by one whose entry file (recorded in its pid file) no longer exists, the server's first spawn launches a daemon of its own build with `--supersede <dev>:<ino>`. That daemon hardlinks the old socket to a private retired name (`.r<tag>` beside the socket, plus `terminal-daemon-v3.retired-<tag>.token` and `.pid` in the run dir), then renames itself over the endpoint. The old daemon sees its endpoint lost and drains. Servers keep reattaching its shells, including after a restart, through the retired name. It exits when its last shell ends, and the daemon that created the retired names removes them then. A daemon stays alive while it holds retired names.
- **Node-pty loads eagerly at daemon startup**, before the socket binds (`preloadNodePty()` in `packages/host-local/src/terminals/node-pty-loader.ts`, called from `runDaemon`). Node's ESM loader caches a failed CommonJS evaluation for the life of the process, so a daemon that served spawn requests after a failed load would fail every one of them forever, even once the underlying problem is gone — failing fast instead (exit code `EXIT_NODE_PTY_UNAVAILABLE`, `protocol.ts`) means the next spawn launches a fresh process with a fresh module cache. `DaemonTerminalBackend.openConnection` retries a failed launch once before giving up and falling back to `InProcessTerminalBackend` (`TerminalService.spawn`'s existing behavior, unchanged). A `pty.spawn` failure during a normal spawn (missing native module, resource exhaustion) is turned into a short human message by `packages/host-local/src/terminals/pty-error-hints.ts` before it reaches the pane; the raw error stays in the daemon log.
- **"Restart the terminal service"** (Settings > Terminal, `band terminals restart-daemon`, `terminal.restartDaemon`) SIGTERMs the current-build daemon directly and lets its own shutdown path (kill every PTY, exit) do the work — no new wire message. Losing the connection already makes `DaemonTerminalBackend.handleDisconnect` report every session as exited, the same path a crash takes, so panes show "exited" and can be reopened. Only ever signals the current-build daemon; a daemon of another build, or one already draining after being superseded, is untouched and keeps its shells.
- **Cold restore**: each daemon-hosted terminal periodically checkpoints its scrollback (serialized ANSI, via the existing headless-mirror/`serialize()` machinery) and cwd to `~/.band/terminal-history/<encoded terminalId>/` (`packages/host-local/src/terminals/terminal-history.ts`), bounded in size and pruned only by an explicit `kill` / `killWorktree` (the tab or worktree is actually closed or deleted). Any other way a PTY goes away — a natural shell exit, a daemon crash, or the `killAll` a restart triggers — leaves the checkpoint in place, so the next `spawn()` for that terminalId writes it into the fresh session's scrollback/cwd before the client's first snapshot. If the checkpoint's saved command was a plain `claude` invocation, `packages/host-local/src/terminals/claude-resume.ts` looks for the newest Claude Code session transcript under `~/.claude/projects/<cwd slug>/` and relaunches with `--resume <id>` instead of just restoring scrollback; other agents/commands are not auto-relaunched.
- Tests: the server helpers' `close()` stops the home's daemon (`tests/helpers/terminal-daemon.ts`), because it is detached and escapes the process-group kill. Pass `{ keepTerminalDaemon: true }`, or use the e2e fixture's `restart()`, to model a restart.

## Band CLI Skills

The Band CLI ships **seven domain-specific skills**, each authored directly as `apps/cli/skills/<name>/SKILL.md` — that file is the single source of truth and is baked into the Rust binary via `include_str!`:

- `band/SKILL.md` — worktrees, repos, agents, cronjobs, tunnel, settings, schema, notify, skills install.
- `band-chat/SKILL.md` — chat panes (`band chats ...`).
- `band-terminal/SKILL.md` — terminal sessions (`band terminals ...`).
- `band-browser/SKILL.md` — browser tabs (`band browsers ...`).
- `band-start/SKILL.md` — kickoff flow: create a worktree and submit the first agent task (`band worktrees create --prompt ...`) with Jira/GitHub ticket auto-detection and branch-name generation.
- `band-loop/SKILL.md` — schedule a recurring agent prompt against a worktree via `band cronjobs`, with an optional self-deleting "stop when criteria is met" wrapper. Native answer for users who would otherwise reach for Claude Code's `/loop`.
- `band-subscribe/SKILL.md` — wait for events instead of polling (`band subscriptions ...`): when to subscribe (after opening a PR, after asking a question), how to call the CLI or the MCP tool, and to unsubscribe when the wait is over.

Each `SKILL.md` is self-contained: the per-skill `## Commands` reference is written out in the file itself, not rendered from the CLI schema. (Earlier these were generated from the live schema by a `band generate-skills` command via a `<!-- COMMANDS -->` placeholder + `commands:` frontmatter; that command and the whole rendering pipeline were removed in favour of authoring the files directly — issue #331.) The split into one skill per task type improves trigger precision and keeps each SKILL.md scoped to one domain. When you change the CLI surface, update the affected skill's `## Commands` section by hand so it stays accurate.

### Installed skill layout (shared + symlinks)

Skills are installed once into a canonical, agent-agnostic location and then linked into each detected coding-agent's skills directory:

```
~/.agents/skills/<name>/SKILL.md          ← canonical content (one copy)
~/.claude/skills/<name>            → ~/.agents/skills/<name>     (symlink)
~/.codex/skills/<name>             → ~/.agents/skills/<name>     (symlink)
~/.gemini/skills/<name>            → ~/.agents/skills/<name>     (symlink)
~/.config/opencode/skills/<name>   → ~/.agents/skills/<name>     (symlink)
```

The symlinks are created with **absolute** targets (`symlinkSync(target, link, "dir")` in TS / `std::os::unix::fs::symlink` in Rust, both fed the canonical `~/.agents/skills/<name>` path). That keeps the link valid regardless of where it lives in the agent's directory tree, at the cost of breaking if the home directory ever moves — acceptable since each user only installs into their own `$HOME`.

Editing a `SKILL.md` in `~/.agents/skills/` is reflected in every linked agent without re-running the installer.

**Supported coding agents** (Band creates a symlink for each one whose config dir is present on the worker):

| Agent type     | Detected via         | Skills dir                       |
| -------------- | -------------------- | -------------------------------- |
| `claude-code`  | `~/.claude/` exists  | `~/.claude/skills/`              |
| `codex`        | `~/.codex/` exists (`$CODEX_HOME` honored) | `~/.codex/skills/` |
| `gemini-cli`   | `~/.gemini/` exists  | `~/.gemini/skills/`              |
| `opencode`     | `~/.config/opencode/` exists | `~/.config/opencode/skills/` |

`cursor-cli` is deliberately excluded — Cursor has no documented user-scope skills directory.

The list of supported agents lives in `packages/coding-agent/src/install-skills.ts::SUPPORTED_AGENT_TYPES` (a single place to update when a new agent adds skills support). The write/symlink logic lives in the Rust CLI (`apps/cli/src/skills.rs::install_skills`); the web server's `apps/hub/src/server/services/cli-skills-service.ts::installSkills` shells out to `band skills install` on every boot from `runFirstTimeSetup`. It's idempotent: an existing symlink pointing at the right shared dir is left alone, an existing symlink pointing elsewhere (or a real directory occupying the path) is reported as a conflict rather than overwritten.

### Install

- `band skills install` — write the seven embedded SKILL.md files into `~/.agents/skills/`, then symlink each detected coding agent's skills directory. Idempotent. Useful for users running the CLI outside the Band dashboard, or for forcing a re-sync without rebooting the web server. The Band web server invokes this same subcommand on every boot from `runFirstTimeSetup`, so most users never need to call it directly.

To change a skill's content, edit `apps/cli/skills/<name>/SKILL.md` directly and rebuild the CLI — there is no generation step.

Optional flags on `band skills install`:

- `--home <path>` — override the destination home dir (mostly for tests).
- `--filter <substr>` — only install skills whose name contains the substring (e.g. `--filter chat`).
