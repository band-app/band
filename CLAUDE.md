# Band

IDE-agnostic agent orchestrator.

## Testing Strategy

This project uses **integration tests** as the primary testing approach. Do not write unit tests with mocked dependencies.

> **When writing, adding, or modifying tests — backend OR frontend — invoke the [`write-integration-test`](.claude/skills/write-integration-test/SKILL.md) skill FIRST.** It is the canonical reference for this repository: real-server boot, Express stubs for external services, no tRPC mocking, no `page.route()` on own routes, Page Object Model for Playwright, locator priority, the universal checklist, and worked examples for both layers. The rules below are the summary; the skill is the source of truth.

### Why Integration Tests

Unit tests with heavy mocking verify that your mocks work, not that your system works. Integration tests exercise the real system through its public interfaces — the same way a client or user would interact with it.

### Rules

- **Never modify production code to make a test pass.** No test-only branches, no exporting internals, no `NODE_ENV` checks in business logic.
- **Black-box testing only.** Test through public interfaces: HTTP endpoints, CLI commands, file system outputs, the rendered DOM (frontend).
- **Real infrastructure.** For databases use test containers, not mocks. For file-based state use temporary directories. Start real servers on random ports.
- **External-only stubs at the network boundary.** Mock only services your process calls *out* to (third-party APIs, agent binaries, GitHub, etc.) using an **Express stub on a random port + env-var override** read at request time. Do NOT use MSW (it misses subprocess-originated traffic, and the env-var indirection is what forces the production code into a testable shape). Do NOT use `page.route()` to intercept your own backend routes from a Playwright test. Do NOT add a tRPC mock layer.
- **Coding agents are stubbed at the ACP boundary.** Chats talk to agents over the Agent Client Protocol; tests set `BAND_TEST_ACP_AGENT` to the scripted stub agent `apps/hub/tests/fixtures/acp-stub-agent.mjs` (scenario, capabilities and request log are env-configured — see its header and `apps/hub/tests/helpers/acp-chat.ts`). Don't mock the ACP SDK or the agent-session service.
- **Test framework: match the package.** `node:test` with `node:assert/strict` is the default for new code. The web app (`apps/web`) and the hub (`apps/hub`) are the exception: they already standardised on **vitest** before this convention was written down (the existing test suites use `describe`/`it`/`expect`/`beforeAll` from `vitest`), so new tests under `apps/hub/tests/` and `apps/web/tests/` should use vitest too rather than mix runners in one package. Don't add test framework dependencies elsewhere unless already present.

See the `write-integration-test` skill (`.claude/skills/write-integration-test/SKILL.md`) for the full doctrine — backend + frontend integration tests, Express-stub patterns, page-object conventions, the universal checklist, and worked examples.

### Frontend tests (web app)

**Frontend tests follow the same integration doctrine as backend tests** — they boot the real server (the production `dist/start-server.mjs` bundle), drive it through a real Chromium via Playwright, and assert on the real rendered DOM / `localStorage` / URL state. Read [`docs/integration-testing.md`](docs/integration-testing.md) and the `write-integration-test` skill (`.claude/skills/write-integration-test/`) before authoring frontend tests.

The non-negotiables for any new frontend test:

- **Boot the real server** with `apps/web/e2e/helpers/server.ts` (`startServer` + `createTmpHome` + `seedState` + `seedSettings`). No in-process React mounting. No shallow renders. No `jsdom` + `renderHook` for behaviour that's user-observable.
- **No tRPC mocking.** No `createTrpcMock`. No `page.route('**/trpc/**', …)`. The existing `apps/web/e2e/helpers/trpc-mock.ts` and the two `workspace-switch-*.spec.ts` files that use it are technical debt to be migrated, not a pattern to copy.
- **Page Object Model.** Locators (`getByRole`, `getByTestId`) live on a page object class under `apps/web/e2e/pages/`. The test body never calls `page.goto()`, `page.getByRole()`, `page.getByTestId()` directly — only methods like `workspacePage.maximizePanel()`.
- **Locator priority for elements your code owns:** `getByRole({ name })` when the ARIA name is system-controlled; otherwise `getByTestId("page__element")` (BEM convention). Banned: CSS selectors, element IDs, `getByText` for localisable copy.
- **External services get Express stubs** under `apps/web/e2e/fixtures/` (or `apps/hub/tests/fixtures/` if shared with backend tests). One stub per env var. Subprocess-originated traffic (`codex`, `claude-code`, `git`) is exactly the case where MSW would silently fail — Express stubs cover it.
- **Production code reads outbound URLs from env vars at request time**, not at module load (`axios.create({ baseURL })` at module top is wrong). Refactoring that pattern is the only allowed production-code change a test may introduce, alongside `data-testid` attributes on JSX.
- **Wait properly.** `expect(locator).toBeVisible()` and `expect.poll(() => …)` auto-retry. Never `page.waitForTimeout(N)`.

Look at `apps/web/e2e/workspace-maximize-state.spec.ts` and `apps/web/e2e/pages/WorkspacePage.ts` as the model — they follow the doctrine end-to-end. Run frontend tests with `pnpm --filter @band-app/web test:e2e`; backend integration tests with `pnpm --filter @band-app/server test`.

### Running the hub suite locally

`pnpm install`, then `pnpm --filter @band-app/server test`. The `pretest` script builds the web app and the hub bundle first. Use Node 24 (`.nvmrc`); the default Node on some machines is newer and breaks other suites.

- The band CLI: `apps/hub/tests/global-setup.ts` runs `cargo build --manifest-path apps/cli/Cargo.toml` once when no CLI newer than `apps/cli/src`, `skills` and `Cargo.*` exists, after which tests find it under `apps/cli/target`. It needs Rust. Without it the run stops with one message saying how to build the CLI. Set `BAND_CLI_PATH` to use a binary you built yourself.
- pnpm under a temp HOME: `vitest.config.ts` sets `COREPACK_HOME` to the cache of your real HOME (`~/.cache/node/corepack`, or `XDG_CACHE_HOME`) and turns the download prompt off, so `dev-server` and `plain-projects` find pnpm without the network. Run pnpm once (any `pnpm install`) so the cache holds it.
- Network: after the install and the CLI build, the suite needs none. `runner-docker`, `runner-k8s-kind` and `environment-build-docker` skip without Docker or a cluster.
- Teardown: start servers with `startServer` from `tests/helpers/server.ts`, which waits for the server's process group before the test deletes its temp home, and delete the home with `removeTmpHome` (`tests/helpers/tmp-home.ts`), which lists leftover files when the delete fails with ENOTEMPTY.

## Git Hooks & CI

This repo has a pre-push hook (`.husky/pre-push`) that runs linting, formatting, and clippy checks. **Never bypass git hooks** — do not use `--no-verify` on `git push` or `git commit`. If a hook fails, fix the underlying issue instead of skipping the check.

**Always run `/review-and-apply` before pushing code.** This invokes the `review-and-apply` skill, which runs Band's CI-style PR review locally against the current branch, auto-applies the resulting fixes, and verifies them with lint/clippy/tests. Do the local review *before* `git push` so the same criteria CI uses catch issues while they're still cheap to fix.

## Architecture: Hub and UI packages

`apps/hub` (`@band-app/server`) is the API server: tRPC, the raw HTTP and WebSocket handlers, the MCP endpoint, the database, the terminal daemon and its build (`scripts/build-server.sh`). `apps/web` (`@band-app/web`) is the React UI and its Playwright e2e specs. `packages/shared` (`@band-app/shared`) holds the types and small pure helpers both sides import (`chat-events`, `client-state-keys`, `toWorkspaceId`, …); it was chosen over keeping them in the hub because the UI imports runtime values from it, and the UI may import only `type { AppRouter }` from `@band-app/server` (`apps/web/tests/hub-boundary.test.ts` enforces it).

The hub serves the built UI from `--ui-dir <path>` or `BAND_UI_DIR`. By default it looks for `apps/web/dist/client` in the workspace, then `client/` beside its bundle (the desktop app, the Docker image and the npm tarball ship it there). In dev, `pnpm dev` runs the hub with Vite mounted as middleware over `apps/web` (`BAND_UI_ROOT` overrides the root), so there is still one port with HMR.

## Architecture: hub tokens

The hub authenticates with revocable tokens in the `tokens` table (`services/token-service.ts`, `infra/db/queries/tokens.ts`). Only a SHA-256 of a token is stored, and no log line carries one.

- Device tokens (`bdt_…`) are for UIs and the CLI. The auth middleware and the WebSocket upgrade in `start-server.ts` accept any live device token (not revoked, not expired) as a Bearer header, the `band_token` cookie, a `?token=` link login, or the `band-token.<token>` subprotocol. `settings.tokenSecret` is the device token with id `shared`, re-synced at every boot (a changed secret replaces its hash). `tokens.revoke` refuses it, because the desktop app and the CLI read it from `settings.json`. A device token has an `admin` flag (default false). The shared token is admin, and `tokens.createDevice` / `band tokens create-device --admin` makes others. Every `tokens.*` procedure uses `adminProcedure` (`api/trpc.ts`) and answers 403 to a non-admin token; the token that authenticated a request is resolved in `start-server.ts` (`requestIsAdmin`) for both the HTTP and the WebSocket tRPC handlers, and dev mode, which has no auth, counts as admin. `hosts.list` is readable by any device token. Revoking any other token also destroys the sockets it opened. SSE streams are not tracked and last until the client reconnects. Dev mode still runs with no auth.
- Worker tokens: `tokens.issueWorkerBootstrap` creates a `hosts` row (`h-<12 hex>`, offline) and a one-time bootstrap token (`bwb_…`, 1 hour by default, 7 days at most) whose `host_id` is the worker id. `TokenService.authenticate` has the shape `LinkServer` takes: a live session token (`bws_…`) for the hello's workerId passes as `token` or `sessionToken`, anything else must be a bootstrap token for that workerId, which is exchanged once (the update that spends it is guarded in SQL) for a session token. A wrong workerId doesn't spend the token. Refusals reach the worker as one generic reason. `/api/workers/exchange` and `/api/workers/connect` call it (see Architecture: remote hosts), and `apps/hub/tests/remote-host.test.ts` covers the exchange and `authenticate` through them. Session tokens aren't rotated yet.
- `tokens.*` is left out of the MCP endpoint (`src/mcp/server.ts`), so an agent can't mint or list tokens, and neither is `hosts.*`. The UI is Settings > Hosts (`HostsSettings.tsx`) and the CLI is `band tokens list | create-device | revoke`.

## Architecture: credential vault

The hub stores credentials encrypted in `vault_items` (`services/vault-service.ts`, `infra/db/queries/vault.ts`, `services/_utils/vault-crypto.ts`). Kinds are `api_key`, `env` and `oauth`. Scope is `global` or `project:<name>`, and a name is unique per scope.

- Encryption is AES-256-GCM with a random 12-byte nonce per write and the item id as authenticated data, so a blob copied onto another row fails to decrypt. The key is `BAND_VAULT_KEY` (32 bytes as base64 or 64 hex characters) or, with that unset, `<BAND_HOME>/vault.key` (mode 0600, generated on first use). `band vault rotate-key` (`vault.rotateKey`) re-encrypts every item in one transaction and then replaces the key file. It is refused when the key comes from the environment.
- No API returns a secret. `vault.list` shows metadata (kind, scope, OAuth account, scopes, expiry), and `getSecret` and `getAccessToken` are for hub services only (the MCP proxy and environment `secrets` in later steps). Metadata never holds a secret, and no log line or error message does. `vault.*` uses `adminProcedure`, is left out of the MCP endpoint, and is not in `RELAY_PROCEDURES`, so a worker's agent gets 403.
- OAuth (`services/_utils/oauth-client.ts`): `vault.startOAuth` discovers the server (RFC 9728 protected resource metadata, also from a 401's `resource_metadata`, then RFC 8414 or OpenID metadata), registers a public client with RFC 7591 when the server offers it (otherwise the caller supplies `clientId`), and returns a PKCE (S256) authorization URL with the RFC 8707 `resource`. Endpoints must be https, or http on loopback. The redirect URI is `<redirectBase>/api/oauth/callback`, where `redirectBase` is the origin the UI is served from, `BAND_PUBLIC_URL` or the loopback address.
- `GET /api/oauth/callback` is answered before the device-token check, because the browser that returns may not hold the hub's session. The state is the credential: it is random, held as a SHA-256 in memory, compared in constant time against each pending flow, valid for 10 minutes and used once. A response whose `iss` names another issuer is refused. The UI follows a flow with `vault.oauthStatus`.
- A sweep every `BAND_VAULT_REFRESH_POLL_MS` (default 30 s) refreshes a token that expires within `BAND_VAULT_REFRESH_SKEW_MS` (default 2 minutes), and `getAccessToken` refreshes on demand. Concurrent refreshes of one item share one request. A failed refresh stores `refreshError` in the metadata. Deleting an OAuth item revokes its token at the server (RFC 7009, best effort) before removing the row.
- UI: Settings > Credentials (`CredentialsSettings.tsx`). CLI: `band vault list | put | delete | rotate-key` (`put` reads the value from stdin).
- Tests: `apps/hub/tests/vault.test.ts` (real hub, real local OAuth server in `fixtures/oauth-stub.ts`), the vault probes in `remote-relay.test.ts`, `apps/web/e2e/settings-credentials.spec.ts`, `vault_put_list_delete` in `apps/cli/tests/integration.rs`.
- The MCP proxy that uses these credentials is below (Architecture: MCP proxy). Not done yet: injecting `env` items into environments.

## Architecture: MCP proxy

The hub proxies HTTP MCP servers at `/mcp-proxy/<name>` and adds the credential from the vault, so an agent never holds it (plan step 4.2). The request flow is `api/mcp-proxy/handler.ts`, the state is `services/mcp-proxy-service.ts` (`mcp_servers`, `mcp_proxy_tokens`, `mcp_proxy_audit`), and `services/_utils/mcp-policy.ts` and `mcp-sse.ts` hold the pure filter rules and the SSE rewriting.

- Servers: `mcp.list | add | update | remove` (admin only, `band mcp list | add | remove`). A server has a `url` (https, or http on loopback, no credentials in it), an optional `vaultItemId` (an `api_key` or `oauth` item), `allowTools` (null means every tool), `readOnly`, `readOnlyTools` and `enabled`. An API key goes out as `<headerName>: <headerPrefix><key>` (default `Authorization: Bearer <key>`), an OAuth access token always as `Authorization: Bearer`. Only streamable HTTP upstreams work over a URL. Legacy SSE transport is not proxied.
- Session tokens: `mcpProxyService.issueSessionToken(sessionId, servers, ttlMs)` (also `mcp.issueSessionToken`, admin only, for the agent launcher in step 4.3) returns an `mcp_` token once. Only its SHA-256 is stored. A token names the servers it may use, expires (1 hour by default, 24 at most) and is revoked when `agent-session-ended` or `chat-removed` fires for its session id (`mcp.revokeSession` does it by hand). A missing, unknown, expired or revoked token gets 401, a token that does not name the server gets 403, a disabled server 404. The route is answered before the device-token check, and the hub's own tokens are no credential for it.
- Filters: `tools/list` answers keep only tools in `allowTools` and, with `readOnly`, tools named in `readOnlyTools` or annotated `readOnlyHint`. A `tools/call` for any other tool is answered by the hub with JSON-RPC error -32602 and never reaches the upstream. A read-only call for a tool the proxy has not seen in a `tools/list` makes the proxy list the upstream's tools first, and an unknown tool is refused. A batch with a refused call is answered whole, with one error per request. `resources/*` and `prompts/*` pass through unfiltered.
- Streaming: a request with no `tools/list` or `tools/call` in it streams through unbuffered. When one is in flight, a JSON answer is read whole (up to 8 MiB) and an SSE answer is parsed one event at a time, so progress notifications reach the client while the call runs. Request bodies are capped at 4 MiB, and the client leaving aborts the upstream request.
- Credentials: the client's `Authorization` and every other header except `content-type`, `accept`, `mcp-protocol-version`, `mcp-session-id` and `last-event-id` stay on the hub. An upstream 401 on an OAuth server makes the hub refresh the token (`vaultService.getCredential(id, true)`) and retry once. A second 401, or a refresh that fails, answers the client 502, never 401, so it is not mistaken for a bad proxy token. Redirects from the upstream are refused.
- Audit: one `mcp_proxy_audit` row per `tools/call` (server, tool, session, ok, and `not-allowed`, `upstream-error`, `no-response` or `upstream-<status>` as the error), kept 30 days, read with `mcp.audit`. Arguments and results are never stored, and no token or credential is logged.
- Workers: an agent on a worker calls `<relay>/mcp-proxy/<name>` with `Authorization: Bearer <mcp token>` and its relay token in the `band_token` cookie or `X-Band-Relay-Token`. On this route the worker relay reads its credential from there, forwards the `Authorization` header, and the hub replays the call without its own token. The relay lets any `/mcp-proxy/<name>` call from a workspace on that worker through, and the proxy's token check decides the rest. `mcp.*` is left out of the MCP endpoint and the relay's procedure list.
- Tests: `apps/hub/tests/mcp-proxy.test.ts` (real hub, the SDK's MCP client, real SDK MCP servers in `fixtures/mcp-stub.ts`, the vault's OAuth stub), `mcp-proxy-relay.test.ts` (real worker), `mcp_add_list_remove` in `apps/cli/tests/integration.rs`.
- Stdio servers (step 4.4, `api/mcp-proxy/stdio.ts`, `services/mcp-stdio-service.ts`). `mcp.add` with `transport: "stdio"`, `hostId`, `command`, `args`, `env` and `cwd` (admin only, like every `mcp.*` call) makes a server that runs as a process on that host. The command is an executable, not a shell line, and only an admin sets it. `env` entries hold a literal value or a vault item id (`api_key` or `env` kind). The hub reads the vault plaintext when it opens a process and sends it inside `mcp.stdio.open`, and the worker hands it to the process. No log line, audit row or file holds it, and the worker drops the process's stderr for the same reason. The route and the session tokens are the same as for HTTP servers. The `initialize` POST starts one process and answers with an `Mcp-Session-Id`. A later request must carry that id with the token that started it, or it gets 404. `DELETE`, a revoked token (`mcp.revokeSession`, `agent-session-ended`), a changed or removed server, 15 idle minutes (`BAND_MCP_STDIO_IDLE_MS`, also enforced on the worker) and a lost link all kill the process. The worker method `mcp.stdio.open` (`apps/worker/src/methods-streams.ts`, `HostMcp` in `packages/host-api`) opens one link channel for the process, checks `cwd` against the worker's roots, and kills the process when the hub resets the channel. A host that is offline or unknown answers 503 with its id. Filters and audit run through `api/mcp-proxy/filter.ts`, shared with the HTTP path. Each POST answers with one JSON body. A server message that answers no request goes to the `GET` stream if one is open, and is dropped otherwise. A call that takes longer than `BAND_MCP_STDIO_CALL_TIMEOUT_MS` (10 minutes) answers 504. Test: `apps/hub/tests/mcp-stdio-relay.test.ts` (real worker, `fixtures/mcp-stdio-server.mjs`).
- Sessions (step 4.3): `agent-session-service.ts` (`sessionMcpServers`) puts the servers a chat may use in `mcpServers` of `session/new`, `session/load` and `session/resume`, as `http` entries `<hub URL>/mcp-proxy/<name>` with `Authorization: Bearer <mcp token>`. A server reaches a session when it is enabled and the session's project is in `scopeProjects` and its host id in `scopeHosts` (null means no limit; set with `mcp.add` / `mcp.update`, no CLI flag yet). The token's session id is the chat id, each attach revokes the chat's older tokens and issues a new one, and the agent process exiting also revokes them. An agent on a worker gets the relay URL and an extra `X-Band-Relay-Token` header. An agent whose `initialize` lacks `mcpCapabilities.http` gets no entries and the hub logs "agent does not support HTTP MCP servers". Tests: `apps/hub/tests/mcp-session-servers.test.ts` and `mcp-session-servers-relay.test.ts` (the stub agent's `mcpCall` step calls a tool through the entry Band passed).
- Not done yet: the UI (step 4.5), the CLI flags for a stdio server, and streaming a stdio server's progress notifications into the POST reply.

## Architecture: remote hosts

A worker (`apps/worker`, `band-worker`) is a machine the hub runs workspaces on. It dials the hub, so it needs no inbound port.

- Registering: Settings > Hosts (or `tokens.issueWorkerBootstrap`) creates a `hosts` row and a one-time bootstrap token. `band-worker --hub <url> --token <bootstrap>` calls `POST /api/workers/exchange` (answered before the device-token check, in `services/worker-link-service.ts`). The hub binds the token to the host id it was issued for, answers `{ sessionToken, workerId }`, and the worker adopts that id. A second exchange of the same token gets 401, with one generic message for every reason. The worker then opens `GET /api/workers/connect`, a WebSocket whose `hello` carries the session token. `LinkServer` authenticates it with `TokenService.authenticate`, which accepts worker tokens only. A device token cannot connect as a worker, and a worker session token fails the device-token check on every other endpoint.
- Revoking a worker's session token calls `LinkServer.drop`, which closes its socket and channels. The worker's redial then fails the hello, and it exits with code 1.
- `WorkerLinkService` keeps the `hosts` row current: `online` with the worker's `info` and build on connect, `offline` when the socket closes or the session expires, `lost` after three missed heartbeats. Each change goes out as a `host-status-changed` status event, which Settings > Hosts follows. At boot every non-local `hosts` row becomes a `RemoteHost` in `HostRegistry`, and a hub restart sets `online` rows to `offline` until the worker redials.
- `RemoteHost` (`packages/host-remote`) implements `Host` over the link session, so a service that calls `workspace.host.*` needs no change. A call to an offline host rejects with `HostOfflineError`. `TerminalService` skips an unreachable host when it looks a terminal up, so local terminals keep working.
- A workspace on a remote host has `worktrees.host_id` set. `workspaces.create` takes `hostId` and, the first time a project is used on that host, `hostProjectPath` (the repository on the worker, kept in `project_hosts`). The worktree goes under `<first worker root>/.band-worktrees/<project>/<branch>`. `syncWorktrees` and `projects.list` pass remote worktrees through, since this machine's `git worktree list` cannot see them, and `ProjectQueries.saveAll` keeps the `project_hosts` rows of remote hosts.
- Files the hub keeps for a workspace live on its host. A worker reports `dirs` in `host.info` (`<first root>/.band-uploads` and `.band-shared`). `saveWorkspaceUploads` (`services/_utils/upload-utils.ts`) writes a remote workspace's chat uploads to `<uploads>/<workspaceId>/` through `host.fs`, and the hub keeps no copy. The chat renders them from `/api/uploads/<workspaceId>/<name>`, which streams from the worker. The shared dir (`services/_utils/shared-dir.ts`) is `<shared>/<workspaceId>/` on the worker, listed with `host.fs.list` after each completed tool call and served from `/api/shared/<workspaceId>/<name>`. ACP `additionalDirectories` name these worker paths.
- Worker relay (`apps/worker/src/relay.ts`, `services/worker-relay-service.ts`, `services/relay-scope.ts`). `host.relay.issue({ workspaceId, chatId })` sends `relay.register` with a hub-generated `brt_` token, and the worker answers with its relay URL (`http://127.0.0.1:<port>`, loopback only, started on the first registration). The hub puts `BAND_SERVER_URL` and `BAND_TOKEN` in the env of the agent (`ensureProcess`) and of each terminal on a remote host (`TerminalService.spawn`, never saved in the layout), and revokes the token when the process exits. A call to the relay needs that token as a Bearer header or `band_token` cookie, or it gets 401. The worker forwards it as one `relay.http` request on its link, and the hub checks it (`checkRelayRequest`), replays it against its own HTTP server on loopback, and streams the answer down a channel. The worker's session token and the hub's tokens never reach an agent. Agents may call only the procedures in `RELAY_PROCEDURES` (`services/relay-scope.ts`, an exact list, so a procedure added to a router later stays refused until it is listed), `/mcp` and the chat routes. Every call must name a workspace (or a chat, a browser tab, a terminal or a `cwd`) on that worker's host, and `chats.create` / `browsers.create` refuse a chosen id that already belongs to another workspace. `projects.list` is allowed too, and the hub cuts its answer down to that worker's workspaces (`filterProjectsReply`). Cronjobs are allowed for workspace-scoped jobs only, keyed by a workspace on the host. `workspaces.create` from a worker always creates on that worker (the relay writes `hostId` into the body and refuses another), and `workspaces.remove` is limited to workspaces on it. `projects.add/remove` and `settings` stay refused. `apps/hub/tests/helpers/relay-cli-commands.ts` lists the CLI commands the skills name, and `relay-cli-skills-drift.test.ts` fails when a skill names one that is neither tested through the relay nor listed as refused with a reason. A refused tRPC call answers in tRPC's error shape (code FORBIDDEN, message naming the procedure), so the CLI prints it. Anything else, or a workspace on another host, gets 403. WebSocket routes are not relayed, and a request body is capped at 512 KiB. Hooks work through it unchanged: `band notify` reads `BAND_SERVER_URL` and `BAND_TOKEN` from the agent's env. Tests: `apps/hub/tests/remote-relay.test.ts`.
- `workspaces.remove` of a workspace on an offline worker removes it from the hub at once and records the checkout in `pending_removals`. `WorkspaceService.finishPendingRemovals` deletes it when the worker connects. `system.listWorktrees` also lists each remote host's worktrees (with `hostId`) and `duBytes` runs on that host. `formatFile` reads a remote workspace's JSON Prettier config through `host.fs` and ignores its `plugins`. `killAllLspServers` stops them on every host.
- What a worker offers. `hosts.list` returns `agents`, `roots`, `capabilities` and `home` for each host, filled from the worker's hello and `host.info` (the local host is described live). `models.availability` says per host whether each configured agent can start, and `models.refresh` takes a `hostId`: without one it uses the local host when it can start the agent, else the first online worker that can, so a Docker hub with no agents refreshes on a worker. Settings > Agents has a host picker per agent. A `hostProjectPath` for a remote host may start with `~` (the worker's `home`) and must otherwise be absolute. An error for a missing directory or a path outside the roots names the roots, and the New Workspace dialog lists them under the field.
- `hosts.remove` (admin) deletes a worker host that is offline with no workspaces, after revoking its live tokens. The local host, an online or lost host and a host with workspaces are refused. UI: Remove in Settings > Hosts. CLI: `band hosts remove <id>`.
- The `band` CLI on a worker. On every connect the worker sends `cli.fetch` (platform and arch, plus the SHA-256 it holds) and `WorkerCliService` (`services/worker-cli-service.ts`) answers with the binary down a channel, or `available: false`. The hub reads `$BAND_CLI_BINARIES_DIR/band-<platform>-<arch>` first (for workers of another platform than the hub), then its own CLI when the worker has the hub's platform and arch. The worker saves it as `<state dir>/bin/band` (`apps/worker/src/cli.ts`, replaced when the hash differs), runs `band skills install` with it, and puts that directory first on PATH for every agent (`acp.spawn`) and terminal (`pty.spawn`) it starts. A worker whose platform the hub cannot serve runs without `band`. Tests: `apps/hub/tests/remote-relay.test.ts`.
- Not done yet: cloning a project onto a worker, the usage scanner on remote hosts, relaying WebSocket routes, and the CLI flag for choosing a host.

## Architecture: agent environments

A repo declares its environment in `.band/environment.json` (format and relation to devcontainer and `config.json`: `docs/agent-environments.md`). `packages/environment` (`@band-app/environment`) holds the zod schema, the parser (`parseEnvironment`, `validateEnvironment`), the `requires` range matcher (`satisfies`, `unmetRequirements`) and `scriptFor`. It touches no file system. Unknown keys are errors with the key path, and a `build.devcontainer` or `build.dockerfile` path must stay inside the repo and exist.

- `HostScripts.environment` reads and validates the file on the workspace's host (worktree first, then the project checkout) and never rejects. `HostScripts.command` asks it first: a valid file's `install` then `start` is the setup command and its `teardown` is the teardown command, otherwise `.band/config.json` answers. A file with problems is logged and skipped. `WorkspaceScriptService.startSetup` opens the file's `terminals` once setup exits 0. Remote workspaces go through the worker's `scripts.environment` call.
- `HostInfo.tools` (`node`, `python`, `go`, `pnpm`, `uv`, `docker`, `git`, from `process/tools.ts`, cached 60 s) comes back in `host.info` and in the worker's hello (`Hello.tools`, optional). The hub stores it in `hosts.info`, and `hosts.list` returns it as `tools`.
- `environment.forProject` and `environment.validate` (`api/environment/router.ts`, `services/environment-service.ts`) back Settings > Environment (`EnvironmentSettings.tsx`) and `band env validate`. They read on the hub's machine. `validate` takes a path, so the MCP endpoint leaves it out, and the relay refuses both because they are not in `RELAY_PROCEDURES`.
- Not done yet: placement by the project's own `requires` (placement takes `requires` from the create call), and using `services` and `secrets`. The `docker` runner hook uses `isolation` and `resources` (see Architecture: runners).
- Images (`services/environment-build-service.ts`, `environment_builds` table, `environment.imageStatus` / `environment.build`, `band env build | status`, the Image section of Settings > Environment; how they are built and cached: `docs/agent-environments.md`). The key is `imageKey` in `packages/environment/src/image.ts`, a SHA-256 over git object hashes at `origin/<default branch>` (the environment file, the Dockerfile or devcontainer and its directory, root lockfiles) and the worker base image ID. The build exports the commit with `git read-tree` and `checkout-index` (no worktree is registered), builds layer 2, adds layer 1 with a generated Dockerfile, runs `install` in a created container with `docker cp` and `docker commit`, and pushes when `environmentBuilder.registry` is set. A ready row for the key whose image still exists on the builder host is a cache hit. The newest ready row is the project's current image, and a failed build never replaces it. `environmentBuilder.hostId | registry | workerImage` in settings pick the builder host (default `local`). Every command runs through `Host.exec` with credential-like and `BAND_*` variables blanked (`scrubEnv`). `BAND_DOCKER_BIN` and `BAND_DEVCONTAINER_BIN` override the binaries on the local host and are read on every call, which is how tests run `apps/hub/tests/fixtures/docker-stub-bin.mjs`. `environment.build` is admin only, left out of the MCP endpoint and refused by the relay. The auto trigger (`BAND_ENVIRONMENT_BUILD_POLL_MS`, default 60 s) rebuilds only projects that have a build already. Not done yet: snapshots, a settings page for `environmentBuilder`, and pruning old images.
- Tests: `packages/environment/tests` (node:test, pure functions with no state to fake, which is why they are not integration tests), `apps/hub/tests/environment-build.test.ts`, `environment-build-auto.test.ts` (docker stub) and `environment-build-docker.test.ts` (real Docker, skipped with no daemon), `apps/web/e2e/settings-environment-image.spec.ts`, the `env_build_*` tests in `apps/cli/tests/integration.rs`, the contract suite in `packages/host-api/src/contract.ts` against local and remote hosts, `apps/hub/tests/environment.test.ts` and `environment-remote.test.ts` (real worker), the `env_validate_*` tests in `apps/cli/tests/integration.rs`, and `apps/web/e2e/settings-environment.spec.ts`.

## Architecture: placement and host requests

`workspaces.create` takes `placement: { labels?, requires?, environment? }` instead of `hostId` (passing both is an error). `PlacementService` (`services/placement-service.ts`) picks the least loaded online host (fewest worktrees) whose `k=v` labels include every requested label and whose facts (`versions`, `os`, `arch` from `host.info`) satisfy `requires` (`>=24`, `>`, `<=`, `<`, `=`, or a plain `24` prefix). The local host is a candidate when it is enabled. Version constraints use the environment package's range matcher (`>=24`, `^3.12`, `24.x`, `>=20 <23`), and a non-version value such as `os=linux` must match exactly. Facts include the host's `tools`.

- With no match, the hub inserts a `host_requests` row (`pending`, with the create call in `input`) and `workspaces.create` answers `{ path: "", provisioning: { requestId } }`. Asking again for the same workspace returns the open request. No worktree exists yet; the UI lists `hostRequests.list` as provisioning cards under the project (`ProvisioningWorkspaceCard`).
- Runner side, admin token only: `hostRequests.lease { runnerId, filter: { labels }, ttlMs }` takes the oldest leasable request whose labels are all in the filter (a request without a filter is taken whatever its labels). A guarded SQL `UPDATE` makes the lease atomic, and a lease past `lease_expires_at` is leasable again (the 1 s sweep also returns it to `pending`). `renew` and `fulfil` need the holder's `runnerId`, else 409. `fulfil { requestId, runnerId, hostId, hostProjectPath? }` records the host; once that host is online (the worker's hello, or the sweep) the hub replays the stored create call on it and sets `completed_at`. A failed replay fails the request with the error.
- `BAND_PLACEMENT_TIMEOUT_MS` (default 10 minutes, read on every sweep) fails a request that is not completed in time: "No host matched the placement within Ns", or "Host X did not connect within Ns" after a fulfil. `hostRequests.cancel` cancels a waiting request or dismisses a failed one; a workspace created while the cancel raced is removed again. `hostRequests.*` is left out of the MCP endpoint and the worker relay.
- CLI: `band workspaces create ... --labels k=v,k=v --requires node=>=24 --any-host --host-project-path <path>`; a provisioning result prints the request id. Tests: `apps/hub/tests/placement.test.ts`, `placement-timeout.test.ts`, `apps/web/e2e/provisioning-workspace.spec.ts`.
- Not done yet: a placement picker in the New Workspace dialog. The runner service (3.4) is below.

## Architecture: runners

`RunnerService` (`services/runner-service.ts`) fulfils host requests by running the `runners` entries of `~/.band/settings.json` (`services/_utils/runner-config.ts` validates them; `settings.update` refuses a bad list, the service skips a bad entry and `runners.list` reports it). The guide is `docs/runner-hooks.md`.

- Every second each runner with a free `maxConcurrent` slot calls `placementService.lease` with its `labels` (and `provides`, which lets a request's `requires` be checked), so the lease's guarded SQL update is what keeps two runners off one request. The service issues a worker bootstrap token (`issueWorkerBootstrap`, which creates the host row), runs `spawn` with the contract environment, renews the lease every 10 s, polls for that host to be `online`, and calls `fulfil` (with the `BAND_HOST_PROJECT_PATH=` line the hook may print). A non-zero exit, a `spawn` still running at `timeoutSec` or no hello in time fails the attempt: `destroy` runs, the host row is removed, and one more attempt starts with a new host. The second failure fails the request with the reason and the last 20 log lines. A cancelled request or a lost lease stops the run and runs `destroy`.
- Hooks get a minimal environment (`PATH`, `HOME`, `LANG`, `LC_ALL`, `TMPDIR`, `USER`, `SHELL`, `SSH_AUTH_SOCK`, the runner's `env`, then the contract variables). The bootstrap token is in the environment only. Hook output goes to `BAND_HOME/runners/logs/<request id>.log` with the token and anything shaped like a Band token replaced by `[redacted]`. `runners.list` and `runners.log` read them (Settings > Runners, `band runners list | log`). `runners.*` is left out of the MCP endpoint and the worker relay.
- `runners/local` starts an ephemeral `band-worker` with its own HOME and `BAND_HOME` under `$BAND_RUNNER_DIR/<worker id>`. `runners/ssh` sends a script to `ssh $BAND_SSH_TARGET 'sh -s'` on stdin. `runner-service.ts` and `runner-config.ts` are on the exempt list of the machine-access Biome override in `biome.json`: the hooks run on the hub's own machine by design, and the logs are hub state.
- Tests: `apps/hub/tests/runners.test.ts` (real `local` hook and worker, the `ssh` hook against a fake `ssh` that runs the script locally because sshd is not on every CI runner, failing and hanging hooks, concurrency, token scrubbing) and `apps/web/e2e/settings-runners.spec.ts`.
- Machines and the reaper (`services/runner-reaper-service.ts`, `runner_machines` table, `infra/db/queries/runner-machines.ts`, step 3.7; guide: `docs/runner-hooks.md#the-reaper`). `RunnerService` records the machine of every attempt (`spawning` until the hello, then `running`) with the handle `spawn` prints as `BAND_MACHINE_HANDLE=<id>`, and passes it to `destroy` as `BAND_MACHINE_HANDLE`. A runner may also set `status` (a hook that prints its live handles), `maxLifetimeSec` and `lifetimeGraceSec` (default 600). The reaper sweeps every `BAND_REAPER_INTERVAL_MS` (default 30 s) and destroys a spawn no attempt owns that got no hello within `timeoutSec` + `BAND_REAPER_HELLO_GRACE_MS`, a machine whose host row is gone or whose worker was offline for `BAND_REAPER_OFFLINE_MS`, a handle `status` lists that no live row has, and a machine past `maxLifetimeSec`. For the last it sends the worker `lifecycle.sleep` (`packages/link/src/relay.ts`), which runs the same hand-off as an idle worker, and runs `destroy` only after the worker exited with every workspace stored. Until the hard deadline (`maxLifetimeSec` + `lifetimeGraceSec`) a machine with unstored workspaces is kept. After it the machine is destroyed anyway and the hub logs an error naming the workspaces. A failing `destroy` is retried on later sweeps, and the third failure marks the machine `lost`. `runners.machines` and `runners.destroyMachine` are admin only (the latter refuses unstored workspaces without `force`), and Settings > Runners lists the machines. Tests: `apps/hub/tests/runner-reaper.test.ts` (fake hooks, then the real `local` hook and worker) and `apps/web/e2e/settings-runners.spec.ts`.
- `runners/docker` starts the worker image with `docker run --detach --rm`, ported from Bunny's hardening: uid 65532, `--cap-drop ALL`, `no-new-privileges`, a read-only root with a `/tmp` tmpfs and an anonymous `/work` volume, pids, memory and cpu limits (from `environment.resources`), `band.runner`, `band.request` and `band.worker` labels, and no mounts, so never the docker socket. The container clones the repository itself. The hub passes the project's current environment image as `BAND_PROJECT_IMAGE` (`RunnerService.projectImage`) and the hook runs it when its docker daemon has or can pull it, else the worker base image. `destroy` runs `docker rm --force --volumes`. `BAND_DOCKER_*` and `DOCKER_HOST` in the runner's `env` configure it (`docs/runner-hooks.md`).
- Isolation levels (`services/_utils/isolation.ts`): a request's level is `placement.environment.isolation` (default `worktree`), a runner's is its `isolation` setting (`process` is `worktree`). `placementService.lease` skips a request whose level is above the runner's `filter.isolation`, and `RunnerService.tick` passes it. `place()` never reuses a host for `container` or `vm`, and a worker the hub starts for one carries the label `band.isolation=<level>`, which `place()` skips for `worktree` requests too. `band workspaces create --isolation worktree|container|vm` sets the level. `placeWorkspace` throws `No runner offers isolation <level>` at once when no runner in settings offers it, instead of waiting out the placement timeout.
- Tests also cover isolation: `apps/hub/tests/runner-isolation.test.ts` (the `local` hook as a runner that declares a level) and `apps/hub/tests/runner-docker.test.ts` (real docker, skipped without `BAND_DOCKER_TEST_IMAGE`, run by the CI `docker` job).
- `runners/k8s` starts a worker as a Pod (or Job, or agent-sandbox Sandbox) with `kubectl`: `render.mjs` builds the manifests, `spawn.sh` creates the workload, then a token Secret owned by it (the token is only on kubectl's stdin), and prints `BAND_MACHINE_HANDLE=<ns>/<name>`. `destroy.sh` and `status.sh` go by the `band.worker` label. The hardening matches the docker hook (uid 65532, drop ALL, read-only root with emptyDir `/tmp` and `/work`, RuntimeDefault seccomp, no service account token), and `isolation: vm` needs `BAND_K8S_RUNTIME_CLASS`. Examples in `deploy/k8s/` (namespace, RBAC with no Secret read, hub Deployment, `check-rbac.sh`). A worker takes plain http only for loopback, so Pods need an https hub URL. `BAND_K8S_CA_CONFIGMAP` mounts a private CA for the hub. Tests: `apps/hub/tests/runner-k8s.test.ts` (stub `kubectl` through `BAND_KUBECTL_BIN`) and `runner-k8s-kind.test.ts` (real cluster, run by the CI job `k8s (kind)`, skipped without `BAND_K8S_TEST_IMAGE` and `BAND_K8S_TEST_KUBECONFIG`). Not done yet: the reaper (3.7). The idle and ephemeral lifecycle is below.
- `runners/hetzner` and `runners/contabo` (`spawn`, `destroy`, `status`, plan step 3.8) create a VM per request. Both render one cloud-init (`runners/_shared/cloud-init.mjs`) that starts `band-worker --ephemeral` under systemd with `ExecStopPost=+poweroff`, and print `BAND_MACHINE_HANDLE`. Contabo is monthly, so its default is a reuse pool (reinstall an idle instance). Provider credentials come from the runner's own env. Tests: `apps/hub/tests/runner-vm-hooks.test.ts` against Express stubs of both APIs (`HCLOUD_API_URL`, `CONTABO_AUTH_URL`, `CONTABO_API_URL`). Guide: `docs/runner-hooks.md`.
- Snapshots (plan step 3.10, `docs/runner-hooks.md#snapshots`). A runner with `snapshot` and `restore` hooks (plus `snapshotDelete`, `snapshotKeep`, `snapshotTtlSec`, `snapshotTimeoutSec`) gets a machine snapshot on every sleep, after the git and session state is stored, which stays the fallback. `RunnerService.snapshotHost` runs `snapshot` with `BAND_MACHINE_HANDLE` and `BAND_WORKSPACE_IDS` and reads `BAND_SNAPSHOT_ID` (and `BAND_SNAPSHOT_SIZE`) from its output into `runner_snapshots`, `RunnerService.destroyMachine` (the reaper's call) runs `destroy` once the worker is gone, and the machine, its runner and its handle come from the `runner_machines` row of the worker id, which the snapshot row points to with `machine_id`. A wake leased by the same runner runs `restore` instead of `spawn`; a failing `restore` runs `destroy` and then `spawn` in the same attempt. After a restore says hello the snapshot row has `restored_at`, and `EphemeralLifecycleService.restore` skips the git checkout for a workspace whose worktree is at its stored `baseSha`, writing only the agent sessions. The hub deletes a snapshot through `snapshot-delete` when a wake used it, a newer one replaced it, it expired or it is beyond `snapshotKeep` (`sweepSnapshots`, `BAND_SNAPSHOT_SWEEP_MS`, default 60 s). `runners.snapshots` lists them. The docker hook snapshots `/work` into an image `band-snapshot:<worker>-<time>` (a helper container, because `docker commit` skips volumes) and restores by filling a new container's `/work` volume from it. The hetzner hook uses `create_image` and creates a server from the image. The restore hooks must delete the saved `session-token`, because a worker prefers it to the bootstrap token. Tests: `apps/hub/tests/runner-snapshots.test.ts` (fake runner wrapping the `local` hook), `runner-docker-snapshot.test.ts` (real docker, skipped without `BAND_DOCKER_TEST_IMAGE`, run by the CI `docker` job) and the snapshot cases in `runner-vm-hooks.test.ts`.

## Architecture: ephemeral lifecycle

Workspaces on an ephemeral worker sleep when it idles and wake on the next use (`services/ephemeral-lifecycle-service.ts`, `workspace_sleep` table, guide: `docs/ephemeral-workers.md`).

- Sleep. An ephemeral worker that was idle for its idle time sends `lifecycle.idle` (`packages/link/src/relay.ts`) and exits with code 0 only on `exit: true`. The hub refuses while a turn, a request waiting on the user, background agent work, queued messages or a terminal exist for a workspace on that worker. Otherwise it stores every workspace through calls on the worker's link: a snapshot commit built in a temporary index (`GIT_INDEX_FILE`) on top of the branch head, pushed to `refs/heads/band/wip/<workspace id>` on `origin` or, when that is not writable, kept as a git bundle in `<BAND_HOME>/sleep/<workspace id>/`; plus the agent session files (`lifecycle.exportSessions`, `sessions.json`). A host stores all of its workspaces or none. A failure keeps the worker alive and shows as `sleepError` in `hosts.list`. The hub's `BAND_EPHEMERAL_IDLE_TIMEOUT_MS` is sent to the worker as `lifecycle.policy`.
- Idle clock. RPCs the hub makes on its own schedule (`host.info`, `worktree.list`, `git.exec`, `git.gh`, read-only `fs.*`, `search.listFiles`) hold the worker while they run but do not restart the idle clock (`PASSIVE_METHODS` in `apps/worker/src/context.ts`). A channel the hub opens counts until both sides end it, so the hub reads the worker's end marker of `cli.body` (`worker-cli-service.ts`).
- Wake. `ensureAwake(workspaceId)` is called by a chat prompt (`AgentSessionService.ensureSession`), `TerminalService.spawn` and the file calls of `FilesService`. Pollers do not call it, so they do not wake anything. It records a wake host request (`input.wake`, hidden from `hostRequests.list`) with the labels and environment of the request that made the host. `RunnerService` starts a worker with the same host id (`TokenService.issueWorkerBootstrapFor`, the host row is kept when an attempt fails). When it says hello, `PlacementService.finish` calls `restoreHost`: fetch the snapshot, `git worktree add -B`, `git read-tree -u --reset` plus `git reset` for the uncommitted changes, and `lifecycle.importSessions` for the agent files. The chat then reattaches with `session/resume` or `session/load`.
- `PlacementService` never offers an ephemeral host to a new workspace (the claim). `projects.list` marks each workspace `lifecycle: "sleeping" | "waking"`, and `WorkspaceCard` shows it. `runners/local/spawn.sh` starts a woken worker id from an empty directory.
- Limits: ignored files, running processes and terminals do not survive. The snapshot upload needs a writable origin or a usable `<BAND_HOME>/sleep`.
- Tests: `apps/hub/tests/ephemeral-lifecycle.test.ts` (real hub, real `local` hook and worker, scripted ACP agent), `apps/worker/tests/lifecycle.test.ts`, `apps/web/e2e/sleeping-workspace.spec.ts`.

## Architecture: headless hub deploy

`deploy/compose/compose.yml` runs the hub image with a `band-data` volume for BAND_HOME, a healthcheck that reads the token from `settings.json`, and an optional Caddy `tls` profile. The guide is `docs/run-the-hub-on-a-server.md`, and the CI `docker` job runs the compose file.

- `BAND_ADMIN_TOKEN` sets the shared admin token (`SettingsQueries.resolveAdminToken`) and replaces a stored secret that differs. With none set, the first boot mints one and, when `BAND_PRINT_ADMIN_TOKEN` is true (the Docker entrypoint sets it), prints it once in `start-server.ts`. `BAND_ACCESS_TOKEN` is the entrypoint's older name for `BAND_ADMIN_TOKEN`. The image bakes in no token.
- `BAND_SERVE_UI=false` skips sirv and the shell, so every non-API path answers 404 and a missing UI build doesn't stop the boot. Dev mode ignores it.
- `BAND_ALLOWED_ORIGINS` adds to `BAND_CORS_ORIGINS` and `corsAllowedOrigins`, for both CORS and the WebSocket origin check.
- Tests: `apps/hub/tests/headless-hub.test.ts`.

## Architecture: machine access lives in host-local

Code that touches a machine (git and `gh`, the exec worker, ripgrep, the LSP manager, ACP launch and spawn, the terminal pool and daemon backend, setup scripts, the Claude environment readers and installers) lives in `packages/host-local` (`@band-app/host-local`). `LocalHost` implements the `Host` interface from `packages/host-api`. The hub imports it through `HostRegistry` (`apps/hub/src/server/infra/host/registry.ts`) and a few helpers by subpath (`@band-app/host-local/git/git-client`). The package has its own host contract test and its own dependencies (node-pty, ripgrep, xterm, the ACP adapters, typescript-language-server). `apps/hub` still lists node-pty, ripgrep, the adapters and the language server, because its build script copies them into `dist/`.

Services may import from `@band-app/host-local` only the pure helpers and hub-side wiring listed in the `patterns` group in `biome.json` (`getRepoInfo`, `git-refusals`, `process/path`, the terminal backends). `gitRunner`, `ghRunner` and `CommandRun` live in `@band-app/host-api`. A service that reads a workspace's checkout calls `workspace.host` (`host.git.exec`, `host.fs.stat`, `host.fs.readFile`), never `node:fs` on `worktree.path`, because the worktree is on the host's disk. The remote-loopback test job enforces this: `apps/hub/tests/helpers/worker-fs-guard.mjs` fails the hub on any fs or child process access under a worker's worktree, and `apps/hub/tests/remote-git-routing.test.ts` covers changes, diff, graph, branch status and sync for a remote workspace. The two GitHub services (`github-poll-service`, `github-webhook-service`) keep `execGh` on the hub: their calls (`gh api` for webhooks, check runs, comments and the authenticated user) use only the GitHub API and the hub's own `gh` login, and need no checkout.

A Biome `style/noRestrictedImports` override in `biome.json` bans `node:fs`, `node:fs/promises`, `node:child_process`, `node-pty`, the exec worker and `execGit`/`execGh` in `apps/hub/src/server/services/**` and `apps/hub/src/server/api/**`. A second override lists the files exempt from it: hub state (CLI install, avatar cache, uploads, tasks, the PWA manifest, workspace prompt files) and `project-service`, which still probes the hub's own project directories with `existsSync`. A third override lets the GitHub webhook and poll services keep calling `execGit` and `execGh`, while still banning `node:fs`, `node:child_process` and `node-pty`. A new service that needs a machine goes through `host.*`. Adding it to the exempt list needs a reason.

## Architecture: Hub vs Desktop App

The hub (`apps/hub`) handles **data, state, and background processes** only. It must never invoke macOS-only shell helpers (folder pickers, Finder reveal, opening apps, installing the CLI symlink with administrator privileges). Those bridges live in the Electron desktop app (`apps/desktop/src/main/ipc/macos-shell.ts`) and are invoked from the React webview via the IPC bridge in `apps/web/src/lib/desktop-ipc.ts`, which talks to the preload script at `apps/desktop/src/preload/index.cts`.

## Architecture: desktop hub picker

The desktop window loads the bundled UI from `app://<host>/` (`apps/desktop/src/main/app-protocol.ts`, a standard, secure, `supportFetchAPI` scheme; a path with no extension and no file gets `_shell.html`, so reloads and deep links keep their route). The UI build comes from `resources/web/dist/client` when packaged and `apps/web/dist/client` in a repo build (`services/ui-paths.ts`); with no build the window falls back to loading the hub's own URL. With `BAND_DEV_WEB_URL` set in an unpackaged run, local mode still loads the dev server.

- The hub is `local` (default: Electron spawns `apps/hub`) or `remote` (a URL and token, nothing spawned). The choice lives in `~/.band/desktop-hub.json` (mode 0600, `services/hub-choice.ts`). A remote `http:` URL is accepted only for loopback, because the secure `app://` page can't make plain `http:`/`ws:` requests to other hosts.
- Each hub has its own host, so its own origin and localStorage (drafts, tabs, last workspace): `app://local` for the bundled hub, `app://h-<12 hex of sha256(hub origin)>` for a remote one. The handler serves only the host the window is loaded under.
- Every `app://` response carries a CSP (`buildCsp`): `connect-src` is `'self'` plus the current hub's http and ws origins, `frame-src` and `media-src` allow the hub, `object-src 'none'`. Inline scripts are allowed because the SPA shell has inline bootstrap scripts. A new origin the UI must reach (another API host) needs adding there.
- The main window can't leave its `app://` host: `will-navigate` and `will-redirect` open web links in the browser and drop everything else, and `window.open` never creates a window (`navigation-guard.ts`). A hub switch loads programmatically, so it is unaffected.
- The preload reads `{ url, token }` with a synchronous IPC (`band_hub_config`, answered only to the bundled UI's frames, `ipc/hub.ts`) and exposes it as `window.__BAND_HUB__`, which `apps/web/src/lib/hub-config.ts` already reads. The renderer never gets the saved remote token back: `hub_get_choice` returns only `hasToken`. The hub IPC handlers also require the main window's top frame on a trusted origin.
- The hub's CORS allows only `app://local`, `app://h-<12 hex>` and the configured origins (`corsAllowedOrigins`, `BAND_CORS_ORIGINS`). Other `app://` hosts and `file://` are refused. `Origin: null` is allowed only when `null` is in the configured list.
- `registerIpc` wraps every channel with the sender check (`ipc/sender-guard.ts`): the main window's top frame on a bundled `app://` origin, never a `<webview>` or subframe. A new channel registered through its `handle` gets the check automatically.
- With a saved remote hub that does not answer at launch, the window shows a Retry / Use local page (`hub-unreachable.ts`, a `data:` URL whose links are `band-action://` URLs handled in `window.ts`). Use local runs the bundled hub for that run and keeps the saved remote choice. A hub switch started while another runs is refused with an error in the picker.
- Settings > Hub (`HubSettings.tsx`, desktop only) calls `hub_set_choice`. The main process checks the remote hub with `GET /api/health` and the Bearer token, then `switchHub` in `index.ts` stops or starts the local hub and reloads the window.
- The PWA manifest is `apps/web/public/manifest.webmanifest`. The hub still answers it before auth, for iOS.
- `apps/web/e2e-desktop/` drives the real unpackaged Electron app with Playwright's `_electron` (`pnpm --filter @band-app/web test:e2e:desktop`, CI job `desktop-macos`). It needs `pnpm build:web` and `pnpm --filter @band-app/desktop build` first, and runs against a throwaway HOME with a random `webServerPort`: the app kills whatever listens on that port, so never point it at 3456. With `BAND_DESKTOP_EXECUTABLE` set to a packaged `Band` binary (`pnpm --filter @band-app/desktop package:dir --mac --arm64`, output in `apps/desktop/dist-builder/mac-arm64/Band.app/Contents/MacOS/Band`) the same specs run against the electron-builder output, in the CI job `desktop-packaged-macos`. A packaged run has no scripted ACP agent, because the hub starts it as `process.execPath <script>`, which in a packaged app launches a second Band that frees the hub's port. The chat-reply step skips there. The folder picker is tested by stubbing `dialog.showOpenDialog` in the main process and calling the `pick_folder` IPC; the native sheet itself stays untested.

## Architecture: browser profiles

A browser profile is a separate cookie jar for browser-pane tabs: one Electron session partition per profile (`persist:band-browser-profile-<id>`, see `apps/desktop/src/browser/profiles.ts`). The built-in Default profile is `null` everywhere and keeps the original `persist:band-browser` partition.

- The web server stores only metadata: the `browser_profiles` table, each project's default profile (`project_browser_profiles`), and each tab's `profileId` in its `panel_states` blob. `browsers.create` without a `profileId` uses the project default. `browsers.setProfile` switches a tab and makes that profile the project default.
- Chrome import reads Chrome data only in the desktop app (`apps/desktop/src/browser/chrome-import/`). The import dialog (`ChromeImportDialog.tsx`, "Import from browser…" in the pane's profile menu) lists Chrome's profile names from `Local State` and shows a "close Chrome" hint while Chrome's `SingletonLock` points at a live process. The user toggles cookies and browsing history and clicks Import. The desktop then reads every selected DB from a private copy (`snapshot.ts`) before writing anything; a copy that SQLite reports as busy, locked or malformed fails the whole import with `ChromeDataLockedError`. Cookies are decrypted with the "Chrome Safe Storage" key (`security find-generic-password`, the macOS Keychain prompt) and written into the Band profile's partition; their values never cross IPC, reach the web server, or get logged. History entries (the most recent 5,000 http(s) URLs) go back to the renderer, which stores them in the tab's workspace history with `history.import`, merging with rows already there. Saved passwords aren't imported, because Band's browser has no password store or autofill. Importing a Chrome profile again re-imports its cookies into the Band profile with the same name (`<Chrome name> (Chrome)`) instead of creating another one, and `browserProfiles.create` refuses a name that is already taken, ignoring case (409).
- A pane's `<webview>` sets its `partition` from the tab's profile (`partitionForProfile` in `apps/web/src/lib/browser-webview.ts`, mirrored in `apps/desktop/src/browser/profiles.ts`). `guest-policy.ts` admits only the Default and profile partitions, and the guest manager prepares each session (`band-action://` handler, no `file:`) when its first guest attaches.

## Architecture: plugins

GitHub features live in a bundled, in-process plugin (`plugins/github/`), following the plugin architecture plan. Band loads no third-party code.

- `packages/plugin-api` holds the contract: the `band-plugin.json` schema (`manifest.ts`), the provider interfaces the core owns (`providers.ts`: `ReviewProvider`, `ChecksProvider`, `WorkspaceReview`), the server API (`server.ts`, `definePlugin`) and the client contributions (`client.tsx`, `defineClientPlugin`, `ClientPluginHost`). Plugins import only this package, `@band-app/ui` and their own dependencies, never `apps/web/src`.
- The server half is listed in `apps/hub/src/server/services/bundled-plugins.ts` and run by `PluginHost` (`plugin-host-service.ts`). It activates a plugin on `onStartup` or on the first provider lookup for a matching `onProjectRemote:<host glob>`, skips ids in `plugins.disabled` in `~/.band/settings.json`, and contains a plugin that throws. `ReviewService` resolves a workspace and asks the matching provider; `reviews.forWorkspace` / `reviews.merge` and `plugins.list` are the tRPC surface.
- The client half is listed in `apps/web/src/plugins/bundled-client-plugins.ts`. Plugin UI reaches the core only through `ClientPluginHost` (`client-plugin-host.ts`). The one slot so far is `workspace.sideTabs`, rendered after Explorer and Changes in `RightSidepanel.tsx`, each tab inside `PluginErrorBoundary`.
- The GitHub plugin's Checks tab shows the branch's pull request with the checks on its head commit, or the GitHub Actions jobs on the branch head when there is no PR. It gets both from one `gh api graphql` query (`plugins/github/src/server/checks-query.ts`). `BAND_GH_BIN` overrides the `gh` binary and is read on every call; tests point it at `apps/hub/tests/fixtures/gh-stub-bin.mjs`, which forwards to the Express stub in `gh-stub.ts`. A fake `gh` on `PATH` would not work, because `/opt/homebrew/bin` and `/usr/local/bin` are always prepended.
- The workspace card's PR badge (`dashboard/components/PullRequestBadge.tsx`) still comes from `branch-status-poller.ts` in the core. Its batched CI query also returns each branch's PR (open first, then the latest merged, then the latest closed; on the default branch only an open one), stored in `branch_statuses.ci_pr`. The badge is the PR number colored by CI state: red failing, yellow pending or running, green passed, gray with no checks or only cancelled ones, violet merged, struck-through gray closed. A branch without a PR shows the older CI icon, or nothing without checks. Hovering or keyboard focus opens a popover with the title, status, "Open on GitHub" and "Copy link"; a click opens the Checks tab (`dashboard/lib/checks-tab.ts`). The poller queries GitHub on its first tick too, and its `execGh` honors `BAND_GH_BIN`. With the GitHub plugin in `plugins.disabled` the poller never runs `gh`, so rows show neither the PR badge nor the CI icon. Moving the badge into the plugin is step 1 of the plan's migration.

## Architecture: agent sessions

An agent session is one run of a coding agent (issue #682). Its mode is how it is displayed: `gui` runs in a chat pane over ACP, `tui` runs the agent's CLI in a terminal. A session keeps its mode for its whole life.

- Rows live in the `agent_sessions` table. `services/agent-session-registry-service.ts` owns them and emits `agent-session-created`, `agent-session-updated` and `agent-session-ended`. A chat's `activeSessionId` is its session's `providerSessionId`. A session ends when its chat or terminal is removed. `services/agent-session-service.ts` is a different thing: it runs the ACP process behind a chat.
- A chat's ACP process stops after 15 minutes without a turn or an update from the agent (`BAND_AGENT_IDLE_TIMEOUT_MS` overrides it). Every update restarts the countdown, so a turn the agent started itself (a `/loop` wakeup, a task notification) isn't cut off. Work that lives in the process holds the stop off (`services/_utils/agent-pending-work.ts`): AIR `async_task_*` updates for background Bash, Monitor and workflows (Band lists the `asyncTasks` capability and takes those updates off the stream before the SDK's validator, in `acp-agent-process.ts`), and `ScheduleWakeup` and `CronCreate` tool calls. Each hold lapses after at most 8 hours.
- `services/agent-launch-service.ts` starts agents (`agentSessions.launch`, `workspaces.create` with a prompt). The CLI reaches it through `band agents launch` and `band agents list`. An agent with no TUI invocation (cursor-cli) falls back to `gui`, and the response carries a `notice`.
- Each browser stores its own mode in localStorage (`band.agent-mode`, `dashboard/lib/agent-mode.ts`) and sends it on every launch. With no mode sent, the server uses `agents.defaultMode` from `~/.band/settings.json`. Boot copies the older `cli.defaultVia` into it once and leaves the old key, because the CLI still reads it.

## Architecture: subscriptions

`subscriptions.create | list | remove | events` (`apps/hub/src/server/api/subscriptions/router.ts`) are tRPC procedures, so the MCP endpoint lists them as `band_subscriptions_*`. A call carrying `x-band-chat-id` and `x-band-workspace-id` headers (an agent's `BAND_CHAT_ID` and `BAND_WORKSPACE_ID`) can omit both ids. ACP chat agents get both variables; terminals get only `BAND_WORKSPACE_ID`, since a terminal has no chat.

- Webhook source: `create` with `source: "webhook"` returns a token once and stores only its SHA-256 (`subscriptions.config`). `POST /api/hooks/:id` is answered before the server's auth check, takes the token in `X-Band-Webhook-Token` or `Authorization: Bearer`, and compares hashes in constant time. 404 for an unknown id, 401 for a bad token, 202 otherwise.
- Timer source: `source: "timer"` with `at` (epoch ms, one-off, forced to `maxWakeups: 1` so it removes itself after delivery) or `cron` (croner syntax, optional seconds field; it ends after `maxWakeups` fires, default 50, or at the 180-day cap). Timers are re-armed from the database in `SubscriptionService.start()`.
- GitHub source (`services/github-webhook-service.ts`, `infra/subscriptions/github.ts`): `create` with `source: "github"`, `repo` and exactly one of `pr` (comments, reviews, review comments, lifecycle; key `github:pr:owner/repo#N`) or `branch` (CI; key `github:ci:owner/repo@branch`, kinds `["ci"]`). `POST /api/hooks/github` is answered before auth and checks `X-Hub-Signature-256` against the secret in `BAND_GITHUB_WEBHOOK_SECRET` or `~/.band/github-webhook-secret` (generated on the first registration, mode 0600); 401 for a bad or missing signature, 202 otherwise. Repeated `X-GitHub-Delivery` ids are dropped. A completed `check_run`, `check_suite` or `workflow_run` makes the hub fetch the commit's check runs with `gh api` (`BAND_GH_BIN`); it pages through them 100 at a time and delivers one event per commit and verdict only when no check is pending. A failure names the failed checks; with no failure, a cancelled run is reported as its own `cancelled` outcome. The first subscription for a repo registers the webhook with `gh api repos/{o}/{r}/hooks --input -` (the body, secret included, goes over stdin, never argv) when `BAND_PUBLIC_URL` or the running tunnel gives a public origin (the tunnel's `?token=` is dropped); otherwise `webhook.status` is `waiting-for-url`.
- Guards (`SubscriptionService.ingest`, `services/pushed-sha-service.ts`): without `maxWakeups` a CI subscription gets 10 and any other 50, and every subscription expires within 180 days. After a successful `workspace.gitPush` or `workspaces.gitPush`, Band records the branch head in `pushed_shas`. A `push` or PR `synchronize` event whose commit is in that table is flagged `self` and recorded with `dropped_reason = "self"`, not delivered, so an agent's own push does not wake it. A CI failure on a commit in the table is delivered as a fix trigger. A CI failure on any other commit carries `fix: false`, and the message says the commit is not Band's and must not be fixed. Comments, reviews and review comments are delivered only from `config.allowedSenders` (`create` takes `allowedSenders` with `pr`; the default is the repo owner plus the authenticated `gh api user` login, and a list replaces it, ignoring case). Other senders' events are recorded with `dropped_reason = "sender"`.

- Polling fallback (`services/github-poll-service.ts`, `infra/subscriptions/github-poll.ts`): the branch-status poller calls `poll()` on its CI ticks, so it follows the activity cadence and needs the GitHub plugin enabled. It serves GitHub subscriptions whose repo has no registered webhook (`webhook.status` is `waiting-for-url` or `failed`). When the hub has a public URL by then, it first tries to register the webhook, and a repo with any `registered` subscription is no longer polled. A PR subscription reads new comments, reviews and review comments with one GraphQL query per repo, from a cursor in `subscription_cursors` (the newest `createdAt` seen, starting at the subscription's creation time). A branch subscription reads the head commit's check runs and delivers through the same `aggregateChecks` as the webhook path. One poll makes at most 6 `gh` calls (a branch whose check pages exceed what is left waits for the next poll), taking turns across repos and branches, and a source that fails is skipped for 2, 4, 8 and then 16 polls.

## Architecture: client state

Small UI state (center tabs, drafts, panel widths, collapsed projects) lives on the web server so the phone and the desktop show the same thing. localStorage stays the synchronous read cache.

- The server keeps rows in `client_state`, keyed by `(key, scope)`. It accepts only the keys listed in `shared/client-state-keys.ts`, takes a key's workspace from the key, and refuses writes for a workspace that no longer exists. Scope `all` is one value for every device; `desktop` and `mobile` hold one value per device type (viewport of at least 1024 px, or the desktop app, counts as desktop). `services/client-state-service.ts` and the `clientState.*` router own them. A write names the version it was based on, and a stale one is refused and answered with the current row. A delete leaves a tombstone, which `list` doesn't return. Accepted writes go out as `client-state-changed` on the status stream. Deleting a workspace removes its rows.
- The dashboard writes through `clientStorage` (`lib/client-state.ts`), which writes localStorage and pushes the key 500 ms later. `shared/client-state-keys.ts` lists the synced keys and their scope; any other key stays on the device (for example `band.agent-mode`, per device on purpose). A synced key can split into several entries: `band-tab-state:<ws>` shares view mode and language and keeps scroll per device type.
- Unsaved file edits and untitled buffers are shared too, one key per file (`band-unsaved:<ws>:<path>`). Last save wins. When another device's copy of a file arrives while this device has edits of its own, the file leaf shows a banner offering to load theirs or keep its own; with no local edits the leaf just loads the new copy. Untitled numbers start above every `untitled:N` in the shared tab list, so two devices don't share a buffer by accident.
- Hydration runs before first read: `ClientStateGate` in `__root.tsx` waits for the global keys, and the center dockview's data query waits for its workspace's keys (both give up after 1.5 s so an offline load still renders). A local value the server doesn't have is uploaded, which migrates existing localStorage.
- The center dockview shares only which tabs are open, their order and the active tab (`band:center-tabs:<ws>`, `lib/center-tabs.ts`). Its full layout, with splits and sizes, is per device type. While a workspace is on screen, another device's change only opens and closes tabs; order and active tab apply the next time it is shown.
- A load on `/` (every desktop launch, a phone's home-screen icon) reopens the workspace this device type last showed (`band:last-workspace`, `lib/last-workspace.ts`). `ClientStateGate` picks it after hydration and before the shell renders, skips a workspace that no longer exists, and prefers the selected label's last workspace when the two disagree. The desktop window's bounds and maximized / full-screen state live in `~/.band/desktop-window.json` (`apps/desktop/src/main/services/window-state.ts`).
- e2e specs whose tests share one server call `resetClientState(tmpHome)` in `beforeEach`, because UI state no longer resets with each new browser context.

## Architecture: Web Server vs Terminal Daemon

Terminal PTYs do not live in the web server. They live in the **terminal daemon** (`apps/hub/terminal-daemon.ts`, bundled to `dist/terminal-daemon.mjs`), a detached process the server launches on the first terminal spawn, so shells survive a server restart (desktop relaunch, auto-update, `pnpm dev` reload, crash). The restarted server reattaches to the same shells, and the browser replays their screens over the unchanged `/terminal` WebSocket.

- `TerminalService` talks to a `TerminalBackend` (`packages/host-local/src/terminals/terminal-backend.ts`). `DaemonTerminalBackend` is the default. `InProcessTerminalBackend` is used on Windows, when `BAND_TERMINAL_DAEMON=0`, and as a fallback when the daemon cannot start; its terminals die with the server. Nothing outside `packages/host-local/src/terminals/` touches node-pty.
- The daemon knows nothing about workspaces, layouts or events. It runs a `TerminalPool` behind a Unix socket (NDJSON, token hello, separate control and stream connections). The wire protocol is in `packages/host-local/src/terminals/daemon/protocol.ts`; bump `PROTOCOL_VERSION` on any change to it that an older peer would misread. A new `ControlNotify` that is safe to ignore (like `hold` / `release`) is the one exception, because a daemon drops notifies it doesn't know and new sessions only start on a daemon of the server's own build.
- Runtime files live in `~/.band/run/` (mode 0700): `terminal-daemon-v1.sock`, `.token`, `.pid`, and `terminal-daemon.log`. If the socket path would exceed the 104-byte `sun_path` limit, the socket moves to `/tmp/band-<uid>/`, named by a hash of the run dir.
- Socket publishing follows orca's endpoint-ownership rules (see the header of `daemon/endpoint.ts`): never unlink a socket you did not create, only a refused or missing connect proves a daemon dead, and a daemon never removes its endpoint on shutdown.
- Output to a server shares one stream socket per server. When that socket holds more than 128 KB, the daemon pauses the PTY of each session that has sent over 4,096 characters since the socket was last empty, and resumes them on `drain`. Floods stop at the shell instead of burying other terminals' echo, and a server is only dropped (at 64 MB unread) when it stops reading entirely.
- Output to a browser is parse-acknowledged (ported from orca). The browser attaches with `flow: true` and sends `{ type: "ack", bytes }` once xterm has parsed output; `api/terminals/output-flow.ts` holds the PTY while more than 256 KB is unacknowledged and releases it below 32 KB, through `TerminalAttachment.setOutputHeld` (in-process: `TerminalPool.holdOutput`; daemon: the `hold` / `release` notifies, one per server). A client that never opted in is paced on `ws.bufferedAmount`, one that acknowledges nothing for 5 s is written off, and a terminal nobody can see (parked, or in a hidden page) acknowledges on receipt so it never pauses a PTY another device is watching. In the browser, `terminal-output-queue.ts` drains visible output in 16 KB slices with at most 128 KB unparsed in xterm. It writes visible output up to the last DEC 2026 end marker and holds only an unfinished frame's tail until its end arrives (or 100 ms, or 64 KB): xterm skips any render while a frame is open, so a TUI redrawing back to back, whose frames arrive as several 1 KB messages, otherwise painted only on xterm's 1 s timeout. Panes get `CLAUDE_CODE_FORCE_SYNC_OUTPUT=1`, without which Claude Code, not recognising the terminal from `TERM_PROGRAM`, repaints the whole screen on every wheel tick instead of scrolling a DECSTBM region.
- Server shutdown only disconnects. A session ends when its tab is closed, its workspace is deleted (or found deleted at boot), or its shell exits.
- The daemon exits on its own, following orca's daemon: when it has no shells, no spawn in flight and no connection, the moment its last server disconnects (or 2 minutes after launch if none ever connects). If its socket is replaced or removed, it drains: no new sessions, existing shells keep working over already-open connections, and it exits when the last one ends. If `~/.band/run` disappears, it kills its shells and exits.
- New sessions only start on a daemon of the server's own build (issue #652). The build ID is the size and mtime of the daemon entry file. When the endpoint is served by a daemon of another build, or by one whose entry file (recorded in its pid file) no longer exists, the server's first spawn launches a daemon of its own build with `--supersede <dev>:<ino>`. That daemon hardlinks the old socket to a private retired name (`.r<tag>` beside the socket, plus `terminal-daemon-v1.retired-<tag>.token` and `.pid` in the run dir), then renames itself over the endpoint. The old daemon sees its endpoint lost and drains. Servers keep reattaching its shells, including after a restart, through the retired name. It exits when its last shell ends, and the daemon that created the retired names removes them then. A daemon stays alive while it holds retired names.
- **Node-pty loads eagerly at daemon startup**, before the socket binds (`preloadNodePty()` in `packages/host-local/src/terminals/node-pty-loader.ts`, called from `runDaemon`). Node's ESM loader caches a failed CommonJS evaluation for the life of the process, so a daemon that served spawn requests after a failed load would fail every one of them forever, even once the underlying problem is gone — failing fast instead (exit code `EXIT_NODE_PTY_UNAVAILABLE`, `protocol.ts`) means the next spawn launches a fresh process with a fresh module cache. `DaemonTerminalBackend.openConnection` retries a failed launch once before giving up and falling back to `InProcessTerminalBackend` (`TerminalService.spawn`'s existing behavior, unchanged). A `pty.spawn` failure during a normal spawn (missing native module, resource exhaustion) is turned into a short human message by `packages/host-local/src/terminals/pty-error-hints.ts` before it reaches the pane; the raw error stays in the daemon log.
- **"Restart the terminal service"** (Settings > Terminal, `band terminals restart-daemon`, `terminal.restartDaemon`) SIGTERMs the current-build daemon directly and lets its own shutdown path (kill every PTY, exit) do the work — no new wire message. Losing the connection already makes `DaemonTerminalBackend.handleDisconnect` report every session as exited, the same path a crash takes, so panes show "exited" and can be reopened. Only ever signals the current-build daemon; a daemon of another build, or one already draining after being superseded, is untouched and keeps its shells.
- **Cold restore**: each daemon-hosted terminal periodically checkpoints its scrollback (serialized ANSI, via the existing headless-mirror/`serialize()` machinery) and cwd to `~/.band/terminal-history/<encoded terminalId>/` (`packages/host-local/src/terminals/terminal-history.ts`), bounded in size and pruned only by an explicit `kill` / `killWorkspace` (the tab or workspace is actually closed or deleted). Any other way a PTY goes away — a natural shell exit, a daemon crash, or the `killAll` a restart triggers — leaves the checkpoint in place, so the next `spawn()` for that terminalId writes it into the fresh session's scrollback/cwd before the client's first snapshot. If the checkpoint's saved command was a plain `claude` invocation, `packages/host-local/src/terminals/claude-resume.ts` looks for the newest Claude Code session transcript under `~/.claude/projects/<cwd slug>/` and relaunches with `--resume <id>` instead of just restoring scrollback; other agents/commands are not auto-relaunched.
- Tests: the server helpers' `close()` stops the home's daemon (`tests/helpers/terminal-daemon.ts`), because it is detached and escapes the process-group kill. Pass `{ keepTerminalDaemon: true }`, or use the e2e fixture's `restart()`, to model a restart.

## Band CLI Skills

The Band CLI ships **seven domain-specific skills**, each authored directly as `apps/cli/skills/<name>/SKILL.md` — that file is the single source of truth and is baked into the Rust binary via `include_str!`:

- `band/SKILL.md` — workspaces, projects, agents, cronjobs, tunnel, settings, schema, notify, skills install.
- `band-chat/SKILL.md` — chat panes (`band chats ...`).
- `band-terminal/SKILL.md` — terminal sessions (`band terminals ...`).
- `band-browser/SKILL.md` — browser tabs (`band browsers ...`).
- `band-start/SKILL.md` — kickoff flow: create a workspace and submit the first agent task (`band workspaces create --prompt ...`) with Jira/GitHub ticket auto-detection and branch-name generation.
- `band-loop/SKILL.md` — schedule a recurring agent prompt against a workspace via `band cronjobs`, with an optional self-deleting "stop when criteria is met" wrapper. Native answer for users who would otherwise reach for Claude Code's `/loop`.
- `band-subscribe/SKILL.md` — wait for events instead of polling (`band subscriptions ...`): when to subscribe (after opening a PR, after asking a question), how to call the CLI or the MCP tool, and to unsubscribe when the wait is over.

Each `SKILL.md` is self-contained: the per-skill `## Commands` reference is written out in the file itself, not rendered from the CLI schema. (Earlier these were generated from the live schema by a `band generate-skills` command via a `<!-- COMMANDS -->` placeholder + `commands:` frontmatter; that command and the whole rendering pipeline were removed in favour of authoring the files directly — issue #331.) The split into one skill per task type improves trigger precision and keeps each SKILL.md scoped to one domain. When you change the CLI surface, update the affected skill's `## Commands` section by hand so it stays accurate.

### Installed skill layout (shared + symlinks)

Skills are installed once into a canonical, agent-agnostic location and then linked into each detected coding-agent's skills directory:

```
~/.agents/skills/<name>/SKILL.md          ← canonical content (one copy)
~/.claude/skills/<name>            → ~/.agents/skills/<name>     (symlink)
~/.codex/skills/<name>             → ~/.agents/skills/<name>     (symlink)
~/.gemini/skills/<name>            → ~/.agents/skills/<name>     (symlink)
~/.config/opencode/skills/<name>   → ~/.agents/skills/<name>     (symlink)
```

The symlinks are created with **absolute** targets (`symlinkSync(target, link, "dir")` in TS / `std::os::unix::fs::symlink` in Rust, both fed the canonical `~/.agents/skills/<name>` path). That keeps the link valid regardless of where it lives in the agent's directory tree, at the cost of breaking if the home directory ever moves — acceptable since each user only installs into their own `$HOME`.

Editing a `SKILL.md` in `~/.agents/skills/` is reflected in every linked agent without re-running the installer.

**Supported coding agents** (Band creates a symlink for each one whose config dir is present on the host):

| Agent type     | Detected via         | Skills dir                       |
| -------------- | -------------------- | -------------------------------- |
| `claude-code`  | `~/.claude/` exists  | `~/.claude/skills/`              |
| `codex`        | `~/.codex/` exists (`$CODEX_HOME` honored) | `~/.codex/skills/` |
| `gemini-cli`   | `~/.gemini/` exists  | `~/.gemini/skills/`              |
| `opencode`     | `~/.config/opencode/` exists | `~/.config/opencode/skills/` |

`cursor-cli` is deliberately excluded — Cursor has no documented user-scope skills directory.

The list of supported agents lives in `packages/coding-agent/src/install-skills.ts::SUPPORTED_AGENT_TYPES` (a single place to update when a new agent adds skills support). The write/symlink logic lives in the Rust CLI (`apps/cli/src/skills.rs::install_skills`); the web server's `apps/hub/src/server/services/cli-skills-service.ts::installSkills` shells out to `band skills install` on every boot from `runFirstTimeSetup`. It's idempotent: an existing symlink pointing at the right shared dir is left alone, an existing symlink pointing elsewhere (or a real directory occupying the path) is reported as a conflict rather than overwritten.

### Install

- `band skills install` — write the seven embedded SKILL.md files into `~/.agents/skills/`, then symlink each detected coding agent's skills directory. Idempotent. Useful for users running the CLI outside the Band dashboard, or for forcing a re-sync without rebooting the web server. The Band web server invokes this same subcommand on every boot from `runFirstTimeSetup`, so most users never need to call it directly.

To change a skill's content, edit `apps/cli/skills/<name>/SKILL.md` directly and rebuild the CLI — there is no generation step.

Optional flags on `band skills install`:

- `--home <path>` — override the destination home dir (mostly for tests).
- `--filter <substr>` — only install skills whose name contains the substring (e.g. `--filter chat`).
