# Architecture: MCP proxy

The hub proxies HTTP MCP servers at `/mcp-proxy/<name>` and adds the credential from the vault, so an agent never holds it (plan step 4.2). The request flow is `api/mcp-proxy/handler.ts`, the state is `services/mcp-proxy-service.ts` (`mcp_servers`, `mcp_proxy_tokens`, `mcp_proxy_audit`), and `services/_utils/mcp-policy.ts` and `mcp-sse.ts` hold the pure filter rules and the SSE rewriting.

- Servers: `mcp.list | add | update | remove` (admin only, `band mcp list | add | remove`). A server has a `url` (https, or http on loopback, no credentials in it), an optional `vaultItemId` (an `api_key` or `oauth` item), `allowTools` (null means every tool), `readOnly`, `readOnlyTools` and `enabled`. An API key goes out as `<headerName>: <headerPrefix><key>` (default `Authorization: Bearer <key>`), an OAuth access token always as `Authorization: Bearer`. Only streamable HTTP upstreams work over a URL. Legacy SSE transport is not proxied.
- Session tokens: `mcpProxyService.issueSessionToken(sessionId, servers, ttlMs)` (also `mcp.issueSessionToken`, admin only, for the agent launcher in step 4.3) returns an `mcp_` token once. Only its SHA-256 is stored. A token names the servers it may use, expires (1 hour by default, 24 at most) and is revoked when `agent-session-ended` or `chat-removed` fires for its session id (`mcp.revokeSession` does it by hand). A missing, unknown, expired or revoked token gets 401, a token that does not name the server gets 403, a disabled server 404. The route is answered before the device-token check, and the hub's own tokens are no credential for it.
- Filters: `tools/list` answers keep only tools in `allowTools` and, with `readOnly`, tools named in `readOnlyTools` or annotated `readOnlyHint`. A `tools/call` for any other tool is answered by the hub with JSON-RPC error -32602 and never reaches the upstream. A read-only call for a tool the proxy has not seen in a `tools/list` makes the proxy list the upstream's tools first, and an unknown tool is refused. A batch with a refused call is answered whole, with one error per request. `resources/*` and `prompts/*` pass through unfiltered.
- Streaming: a request with no `tools/list` or `tools/call` in it streams through unbuffered. When one is in flight, a JSON answer is read whole (up to 8 MiB) and an SSE answer is parsed one event at a time, so progress notifications reach the client while the call runs. Request bodies are capped at 4 MiB, and the client leaving aborts the upstream request.
- Credentials: the client's `Authorization` and every other header except `content-type`, `accept`, `mcp-protocol-version`, `mcp-session-id` and `last-event-id` stay on the hub. An upstream 401 on an OAuth server makes the hub refresh the token (`vaultService.getCredential(id, true)`) and retry once. A second 401, or a refresh that fails, answers the client 502, never 401, so it is not mistaken for a bad proxy token. Redirects from the upstream are refused.
- Audit: one `mcp_proxy_audit` row per `tools/call` (server, tool, session, ok, and `not-allowed`, `upstream-error`, `no-response` or `upstream-<status>` as the error), kept 30 days, read with `mcp.audit`. Arguments and results are never stored, and no token or credential is logged.
- Workers: an agent on a worker calls `<relay>/mcp-proxy/<name>` with `Authorization: Bearer <mcp token>` and its relay token in the `band_token` cookie or `X-Band-Relay-Token`. On this route the worker relay reads its credential from there, forwards the `Authorization` header, and the hub replays the call without its own token. The relay lets any `/mcp-proxy/<name>` call from a worktree on that worker through, and the proxy's token check decides the rest. `mcp.*` is left out of the MCP endpoint and the relay's procedure list.
- Tests: `apps/hub/tests/mcp-proxy.test.ts` (real hub, the SDK's MCP client, real SDK MCP servers in `fixtures/mcp-stub.ts`, the vault's OAuth stub), `mcp-proxy-relay.test.ts` (real worker), `mcp_add_list_remove` in `apps/cli/tests/integration.rs`.
- Stdio servers (step 4.4, `api/mcp-proxy/stdio.ts`, `services/mcp-stdio-service.ts`). `mcp.add` with `transport: "stdio"`, `hostId`, `command`, `args`, `env` and `cwd` (admin only, like every `mcp.*` call) makes a server that runs as a process on that worker. The command is an executable, not a shell line, and only an admin sets it. `env` entries hold a literal value or a vault item id (`api_key` or `env` kind). The hub reads the vault plaintext when it opens a process and sends it inside `mcp.stdio.open`, and the worker hands it to the process. No log line, audit row or file holds it, and the worker drops the process's stderr for the same reason. The route and the session tokens are the same as for HTTP servers. The `initialize` POST starts one process and answers with an `Mcp-Session-Id`. A later request must carry that id with the token that started it, or it gets 404. `DELETE`, a revoked token (`mcp.revokeSession`, `agent-session-ended`), a changed or removed server, 15 idle minutes (`BAND_MCP_STDIO_IDLE_MS`, also enforced on the worker) and a lost link all kill the process. The worker method `mcp.stdio.open` (`apps/worker/src/methods-streams.ts`, `HostMcp` in `packages/host-api`) opens one link channel for the process, checks `cwd` against the worker's roots, and kills the process when the hub resets the channel. A worker that is offline or unknown answers 503 with its id. Filters and audit run through `api/mcp-proxy/filter.ts`, shared with the HTTP path. Each POST answers with one JSON body. A server message that answers no request goes to the `GET` stream if one is open, and is dropped otherwise. A call that takes longer than `BAND_MCP_STDIO_CALL_TIMEOUT_MS` (10 minutes) answers 504. Test: `apps/hub/tests/mcp-stdio-relay.test.ts` (real worker, `fixtures/mcp-stdio-server.mjs`).
- Sessions (step 4.3): `agent-session-service.ts` (`sessionMcpServers`) puts the servers a chat may use in `mcpServers` of `session/new`, `session/load` and `session/resume`, as `http` entries `<hub URL>/mcp-proxy/<name>` with `Authorization: Bearer <mcp token>`. A server reaches a session when it is enabled and the session's repo is in `scopeRepos` and its worker id in `scopeHosts` (null means no limit; set with `mcp.add` / `mcp.update`, no CLI flag yet). The token's session id is the chat id, each attach revokes the chat's older tokens and issues a new one, and the agent process exiting also revokes them. An agent on a worker gets the relay URL and an extra `X-Band-Relay-Token` header. An agent whose `initialize` lacks `mcpCapabilities.http` gets no entries and the hub logs "agent does not support HTTP MCP servers". Tests: `apps/hub/tests/mcp-session-servers.test.ts` and `mcp-session-servers-relay.test.ts` (the stub agent's `mcpCall` step calls a tool through the entry Band passed).
- Settings > MCP (step 4.5, `McpSettings.tsx`): list with status, add and edit form, tool allowlist, read-only, scope (all, repos or workers) and a per-server audit log. `mcp.test` (admin) connects to an upstream with the SDK client and returns every tool with its `readOnlyHint`, ignoring the allowlist, for a saved server (`name`) or an unsaved form (`url` and credential fields). The status on each row is the same call. `mcp.audit` takes `offset` and returns `hasMore`. The form also takes a stdio server (worker, command, args, cwd, env with vault references). A non-admin token sees only a notice. `mcp.test` also takes a stdio form (worker, command, args, env, cwd) or a saved stdio server: it opens the process through `mcpStdioService`, runs `initialize` and `tools/list`, and kills it. A stdio row's status is whether its worker is online, because a status check never starts a process. Tests: `apps/hub/tests/mcp-settings-api.test.ts`, `apps/web/e2e/settings-mcp.spec.ts`, `apps/web/e2e/settings-mcp-stdio.spec.ts` (real worker).
