# Architecture: remote workers

A worker (`apps/worker`, `band-worker`) is a machine the hub runs worktrees on. It dials the hub, so it needs no inbound port.

- Registering: Settings > Workers (or `tokens.issueWorkerBootstrap`) creates a `hosts` row and a one-time bootstrap token. `band-worker --hub <url> --token <bootstrap>` calls `POST /api/workers/exchange` (answered before the device-token check, in `services/worker-link-service.ts`). The hub binds the token to the worker id it was issued for, answers `{ sessionToken, workerId }`, and the worker adopts that id. A second exchange of the same token gets 401, with one generic message for every reason. The worker then opens `GET /api/workers/connect`, a WebSocket whose `hello` carries the session token. `LinkServer` authenticates it with `TokenService.authenticate`, which accepts worker tokens only. A device token cannot connect as a worker, and a worker session token fails the device-token check on every other endpoint.
- Revoking a worker's session token calls `LinkServer.drop`, which closes its socket and channels. The worker's redial then fails the hello, and it exits with code 1.
- `WorkerLinkService` keeps the `hosts` row current: `online` with the worker's `info` and build on connect, `offline` when the socket closes or the session expires, `lost` after three missed heartbeats. Each change goes out as a `host-status-changed` status event, which Settings > Workers follows. At boot every non-local `hosts` row becomes a `RemoteHost` in `HostRegistry`, and a hub restart sets `online` rows to `offline` until the worker redials.
- `RemoteHost` (`packages/host-remote`) implements `Host` over the link session, so a service that calls `worktree.host.*` needs no change. A call to an offline worker rejects with `HostOfflineError`. `TerminalService` skips an unreachable worker when it looks a terminal up, so local terminals keep working.
- A worktree on a remote worker has `worktrees.host_id` set. `worktrees.create` takes `hostId` and, the first time a repo is used on that worker, `hostRepoPath` (the repository on the worker, kept in `repo_hosts`). The worktree goes under `<first worker root>/.band-worktrees/<repo>/<branch>`. `syncWorktrees` and `repos.list` pass remote worktrees through, since this machine's `git worktree list` cannot see them, and `RepoQueries.saveAll` keeps the `repo_hosts` rows of remote workers.
- Files the hub keeps for a worktree live on its worker. A worker reports `dirs` in `host.info` (`<first root>/.band-uploads` and `.band-shared`). `saveWorktreeUploads` (`services/_utils/upload-utils.ts`) writes a remote worktree's chat uploads to `<uploads>/<worktreeId>/` through `host.fs`, and the hub keeps no copy. The chat renders them from `/api/uploads/<worktreeId>/<name>`, which streams from the worker. The shared dir (`services/_utils/shared-dir.ts`) is `<shared>/<worktreeId>/<chatId>/` on the worker, one folder per chat so two chats in a worktree never see each other's files. It is listed with `host.fs.list` after each completed tool call and served from `/api/shared/<worktreeId>/<chatId>/<name>`. The older `/api/shared/<worktreeId>/<name>` form still serves files in the old per-worktree folder. The web card opens the file in a center `file` tab whose path is `shared:<chatId>/<name>` (`SharedFileLeaf.tsx`). ACP `additionalDirectories` name these worker paths.
- Explorer download. `GET /api/worktree-file/<worktreeId>/<path>?download=1` (device token, after the auth check) serves one file as `Content-Disposition: attachment` (`attachmentDisposition`, RFC 6266 `filename*`) with `nosniff`, streamed through `worktree.host.fs.readStream`, so a remote worktree's bytes come from its worker and the stream is destroyed when the client leaves. A folder answers 400, and the path rules are those of the preview route (`..` and symlinks out answer 400). The UI's Download item (`FileBrowser.tsx`, `adapter.downloadWorktreeFile`) fetches with the Bearer header or cookie and saves a Blob, so no token goes in a URL and it works from `app://`. The worker relay lists no such route, so an agent gets 403. Tests: `worktree-file-serve.test.ts`, `worktree-file-serve-remote.test.ts`, `apps/web/e2e/explorer-download.spec.ts`. The same route answers single-range `Range` requests (206 with `Content-Range`, 416 past the end, `Accept-Ranges: bytes` on every answer) through `host.fs.readStream(path, { start, end })`, so a video seeks and iOS plays it. The web viewer's `VideoPreview` (`.mp4 .m4v .mov .webm .ogv`) and the Expo app's `VideoPlayer` (`components/files/video-view.tsx`, `expo-video`, Bearer header) play it; images already preview in both. Tests add `worktree-file-serve*.test.ts` Range cases, `host-api` contract range case, `apps/web/e2e/explorer-media-preview.spec.ts` (desktop and mobile layout), `apps/mobile/tests/files.test.ts`. The Expo player needs a native rebuild for `expo-video`. Not done yet: folders (zip), and streaming to disk instead of a Blob for very large downloads.
- Worker relay (`apps/worker/src/relay.ts`, `services/worker-relay-service.ts`, `services/relay-scope.ts`). `host.relay.issue({ worktreeId, chatId })` sends `relay.register` with a hub-generated `brt_` token, and the worker answers with its relay URL (`http://127.0.0.1:<port>`, loopback only, started on the first registration). The hub puts `BAND_SERVER_URL` and `BAND_TOKEN` in the env of the agent (`ensureProcess`) and of each terminal on a remote worker (`TerminalService.spawn`, never saved in the layout), and revokes the token when the process exits. A call to the relay needs that token as a Bearer header or `band_token` cookie, or it gets 401. The worker forwards it as one `relay.http` request on its link, and the hub checks it (`checkRelayRequest`), replays it against its own HTTP server on loopback, and streams the answer down a channel. The worker's session token and the hub's tokens never reach an agent. Agents may call only the procedures in `RELAY_PROCEDURES` (`services/relay-scope.ts`, an exact list, so a procedure added to a router later stays refused until it is listed), `/mcp` and the chat routes. Every call must name a worktree (or a chat, a browser tab, a terminal or a `cwd`) on that worker's worker, and `chats.create` / `browsers.create` refuse a chosen id that already belongs to another worktree. `repos.list` is allowed too, and the hub cuts its answer down to that worker's worktrees (`filterReposReply`). Cronjobs are allowed, keyed by a worktree on the worker (a create names it in `worktreeId`, and an update that moves the job to another worktree is refused). `worktrees.create` from a worker always creates on that worker (the relay writes `hostId` into the body and refuses another), and `worktrees.remove` is limited to worktrees on it. `settings` stays refused. Repo management is allowed (`repos.add`, `addFromWorker`, `addByUrl`, `inspectFolder`, `resolveRemote`, `gitInit`, `promoteToGit`, `update`, `reorder`, `remove`): these name a repo or a worker instead of a worktree, so `checkRepoCall` skips the worktree check, and the hub replays them with its own admin token. The one limit is a repo's allowed workers (`repoHostRefusal` in `cross-host-policy.ts`): a call on a repo limited to workers that exclude the caller's gets 403 naming the repo, and `addFromWorker` refuses an `allowedHostIds` that excludes the folder's `hostId`. `addFromWorker` may name any worker but is refused with `addRoot` (widening a worker's roots needs a person). A re-add found only by the folder's remote is checked against the folder's worker by `assertHostAllowed`, not against the caller's. `apps/hub/tests/helpers/relay-cli-commands.ts` lists the CLI commands the skills name, and `relay-cli-skills-drift.test.ts` fails when a skill names one that is neither tested through the relay nor listed as refused with a reason. A refused tRPC call answers in tRPC's error shape (code FORBIDDEN, message naming the procedure), so the CLI prints it. Anything else, or a worktree on another worker, gets 403. WebSocket routes are not relayed, and a request body is capped at 512 KiB. Hooks work through it unchanged: `band notify` reads `BAND_SERVER_URL` and `BAND_TOKEN` from the agent's env. Tests: `apps/hub/tests/remote-relay.test.ts`.
- `worktrees.remove` of a worktree on an offline worker removes it from the hub at once and records the checkout in `pending_removals`. `WorktreeService.finishPendingRemovals` deletes it when the worker connects. `system.listWorktrees` also lists each remote worker's worktrees (with `hostId`) and `duBytes` runs on that worker. `formatFile` reads a remote worktree's JSON Prettier config through `host.fs` and ignores its `plugins`. `killAllLspServers` stops them on every worker.
- What a worker offers. `workers.list` returns `agents`, `roots`, `capabilities` and `home` for each worker, filled from the worker's hello and `host.info` (the local worker is described live). `models.availability` says per worker whether each configured agent can start, and `models.refresh` takes a `hostId`: without one it uses the local worker when it can start the agent, else the first online worker that can, so a Docker hub with no agents refreshes on a worker. Settings > Agents has a worker picker per agent. A `hostRepoPath` for a remote worker may start with `~` (the worker's `home`) and must otherwise be absolute. An error for a missing directory or a path outside the roots names the roots, and the New Worktree dialog lists them under the field.
- `workers.remove` (admin) deletes a worker that is offline with no worktrees, after revoking its live tokens. The local worker, an online or lost worker and a worker with worktrees are refused. UI: Remove in Settings > Workers. CLI: `band workers remove <id>`.
- The `band` CLI on a worker. A worker carries its own CLI and the hub serves none (`apps/worker/src/cli.ts`, `resolveCliBinary`). The lookup order is `BAND_CLI_PATH`, the optional dependency `@band-app/worker-cli-<platform>-<arch>` (darwin-arm64, linux-x64, linux-arm64, published by the release workflow before the worker and pinned by `apps/worker/scripts/cli-packages.mjs`), `Resources/binaries/band` beside the desktop app's bundled worker, then `apps/cli/target/{release,debug}/band` in a checkout. At start the worker points `<state dir>/bin/band` (a symlink, replaced by rename) at that binary, runs `band skills install` with it, and puts `<state dir>/bin` first on PATH for every agent (`acp.spawn`) and terminal (`pty.spawn`) it starts, so a shell or agent that outlives an update still finds `band` after the update moves the CLI package. On Windows, or when the link cannot be made, the CLI's own folder goes on PATH. With none found it logs one line naming the package and runs without `band`. The `cli.fetch` link method is gone, so an older worker's call gets method-not-found, which it logs and survives, keeping any copy it cached. The worker image builds the CLI in a cargo stage and sets `BAND_CLI_PATH`. Tests: `apps/hub/tests/remote-relay.test.ts`.
- Stable agent environment (`apps/worker/tests/stable-agent-env.test.ts`). What an agent or shell holds in its environment must work after a worker restart. The git credential socket is `<state dir>/run/git-credential.sock` (0600 in a 0700 dir; a hashed name under `/tmp/band-<uid>/` when the path is too long for a socket), unlinked and recreated by each start. The relay listens on the loopback port saved in `<state dir>/relay.json` (0600) and listens at start when that file exists. The file also holds the live grants as token SHA-256 hashes with their scopes, never the tokens, and `relay.revoke` removes one. A saved port taken by another process falls back to a random one. The band CLI path is described above. A revoke the hub sends while the worker is down is not replayed, so that grant stays valid until the hub revokes it again.
- Persistent terminals on a worker (`apps/worker/src/terminals.ts`, `packages/host-local/src/terminals/daemon/exit-records.ts`). `band-worker` runs terminals in the terminal daemon (the hub's daemon code, entry `apps/worker/src/terminal-daemon.ts`, bundled to `dist/terminal-daemon.mjs`), with its run dir at `<state dir>/run`, so shells outlive the worker. One daemon per worker state dir, not one holder per terminal: the daemon already has the scrollback mirror, replay, reattach and supersede-on-upgrade. The socket is 0600 in a 0700 dir (in `/tmp/band-<uid>/` when the state dir path is too long). A daemon started with `--record-exits` writes `run/exits/<id>.json` for a shell that exits while no server is connected, and `DaemonTerminalBackend.recoverExits` (called on each link connect) connects and sends those as `pty.exit` once. `Worker.start` takes `persistentTerminals` (only `main.ts` sets it, so in-process test workers leave no daemon), and `BAND_TERMINAL_DAEMON=0` turns it off. `install-service` writes `KillMode=process` and `AbandonProcessGroup`, and `uninstall-service` ends the daemons (`stopTerminalDaemons`). The hub's own local worker is unchanged. Test: `apps/worker/tests/terminal-persistence.test.ts` (real `band-worker` binary killed and restarted).
- Remote browser (plan step 7.3, `packages/host-local/src/browser/chromium.ts`, `host.browser`). `browser.open` on a worker starts one Chromium per worktree with `--remote-debugging-port=0 --remote-debugging-address=127.0.0.1` and a profile in `<state dir>/browser/<worktree id>` (headless unless the worker has `DISPLAY`; the binary is `BAND_CHROMIUM_BIN`, a system Chromium or a Playwright download). `browser.connect` opens a `browser.cdp` channel to the browser-level endpoint, one length-prefixed frame per CDP message (`encodeFrame` in `packages/link/src/frames.ts`). The hub's `/cdp?worktreeId=<id>` (`infra/browser-host/cdp-proxy.ts`; `bandTabId` alone keeps the desktop path, and a `bandTabId` with a `worktreeId` must belong to it) opens the browser through `setRemoteCdpOpener` (`services/browser-service.ts`) and relays frames both ways, with no Default-profile check because the profile belongs to the worktree. A local worktree gets close code 4000 there. `browser.close` sends `Browser.close` so cookies are written, then SIGTERM and SIGKILL. `worktrees.remove` and the worker stopping close it. The relay reply carries `browserPortFile`, and the agent's env gets `BAND_CDP_PORT_FILE` (Chromium's `DevToolsActivePort`, first line the loopback port). Tests: `apps/worker/tests/browser.test.ts` (cookies across a reopen) and `apps/hub/tests/remote-browser.test.ts`, both skipped with no Chromium. Not done yet: `band browsers` commands driving this browser, and the pane choosing it in the UI.
