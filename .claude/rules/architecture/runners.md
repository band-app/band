# Architecture: runners

`RunnerService` (`services/runner-service.ts`) fulfils worker requests by running the `runners` entries of `~/.band/settings.json` (`services/_utils/runner-config.ts` validates them; `settings.update` refuses a bad list, the service skips a bad entry and `runners.list` reports it). The guide is `docs/runner-hooks.md`.

- Every second each runner with a free `maxConcurrent` slot calls `placementService.lease` with its `labels` (and `provides`, which lets a request's `requires` be checked), so the lease's guarded SQL update is what keeps two runners off one request. The service issues a worker bootstrap token (`issueWorkerBootstrap`, which creates the worker row), runs `spawn` with the contract environment, renews the lease every 10 s, polls for that worker to be `online`, and calls `fulfil` (with the `BAND_WORKER_REPO_PATH=` line the hook may print). A non-zero exit, a `spawn` still running at `timeoutSec` or no hello in time fails the attempt: `destroy` runs, the worker row is removed, and one more attempt starts with a new worker. The second failure fails the request with the reason and the last 20 log lines. A cancelled request or a lost lease stops the run and runs `destroy`.
- Hooks get a minimal environment (`PATH`, `HOME`, `LANG`, `LC_ALL`, `TMPDIR`, `USER`, `SHELL`, `SSH_AUTH_SOCK`, the runner's `env`, then the contract variables). The bootstrap token is in the environment only. Hook output goes to `BAND_HOME/runners/logs/<request id>.log` with the token and anything shaped like a Band token replaced by `[redacted]`. `runners.list` and `runners.log` read them (Settings > Runners, `band runners list | log`). `runners.*` is left out of the MCP endpoint and the worker relay.
- `runners/local` starts an ephemeral `band-worker` with its own HOME and `BAND_HOME` under `$BAND_RUNNER_DIR/<worker id>`. `runners/ssh` sends a script to `ssh $BAND_SSH_TARGET 'sh -s'` on stdin. `runner-service.ts` and `runner-config.ts` are on the exempt list of the machine-access Biome override in `biome.json`: the hooks run on the hub's own machine by design, and the logs are hub state.
- Tests: `apps/hub/tests/runners.test.ts` (real `local` hook and worker, the `ssh` hook against a fake `ssh` that runs the script locally because sshd is not on every CI runner, failing and hanging hooks, concurrency, token scrubbing) and `apps/web/e2e/settings-runners.spec.ts`.
- Machines and the reaper (`services/runner-reaper-service.ts`, `runner_machines` table, `infra/db/queries/runner-machines.ts`, step 3.7; guide: `docs/runner-hooks.md#the-reaper`). `RunnerService` records the machine of every attempt (`spawning` until the hello, then `running`) with the handle `spawn` prints as `BAND_MACHINE_HANDLE=<id>`, and passes it to `destroy` as `BAND_MACHINE_HANDLE`. A runner may also set `status` (a hook that prints its live handles), `maxLifetimeSec` and `lifetimeGraceSec` (default 600). The reaper sweeps every `BAND_REAPER_INTERVAL_MS` (default 30 s) and destroys a spawn no attempt owns that got no hello within `timeoutSec` + `BAND_REAPER_HELLO_GRACE_MS`, a machine whose worker row is gone or whose worker was offline for `BAND_REAPER_OFFLINE_MS`, a handle `status` lists that no live row has, and a machine past `maxLifetimeSec`. For the last it sends the worker `lifecycle.sleep` (`packages/link/src/relay.ts`), which runs the same hand-off as an idle worker, and runs `destroy` only after the worker exited with every worktree stored. Until the hard deadline (`maxLifetimeSec` + `lifetimeGraceSec`) a machine with unstored worktrees is kept. After it the machine is destroyed anyway and the hub logs an error naming the worktrees. A failing `destroy` is retried on later sweeps, and the third failure marks the machine `lost`. `runners.machines` and `runners.destroyMachine` are admin only (the latter refuses unstored worktrees without `force`), and Settings > Runners lists the "Workers started". Tests: `apps/hub/tests/runner-reaper.test.ts` (fake hooks, then the real `local` hook and worker) and `apps/web/e2e/settings-runners.spec.ts`.
- `runners/docker` starts the worker image with `docker run --detach --rm`, ported from Bunny's hardening: uid 65532, `--cap-drop ALL`, `no-new-privileges`, a read-only root with a `/tmp` tmpfs and an anonymous `/work` volume, pids, memory and cpu limits (from `environment.resources`), `band.runner`, `band.request` and `band.worker` labels, and no mounts, so never the docker socket. The container clones the repository itself. The hub passes the repo's current environment image as `BAND_REPO_IMAGE` (`RunnerService.repoImage`) and the hook runs it when its docker daemon has or can pull it, else the worker base image. `destroy` runs `docker rm --force --volumes`. `BAND_DOCKER_*` and `DOCKER_HOST` in the runner's `env` configure it (`docs/runner-hooks.md`).
- Isolation levels (`services/_utils/isolation.ts`): a request's level is `placement.environment.isolation` (default `worktree`), a runner's is its `isolation` setting (`process` is `worktree`). `placementService.lease` skips a request whose level is above the runner's `filter.isolation`, and `RunnerService.tick` passes it. `place()` never reuses a worker for `container` or `vm`, and a worker the hub starts for one carries the label `band.isolation=<level>`, which `place()` skips for `worktree` requests too. `band worktrees create --isolation worktree|container|vm` sets the level. `placeWorktree` throws `No runner offers isolation <level>` at once when no runner in settings offers it, instead of waiting out the placement timeout.
- Tests also cover isolation: `apps/hub/tests/runner-isolation.test.ts` (the `local` hook as a runner that declares a level) and `apps/hub/tests/runner-docker.test.ts` (real docker, skipped without `BAND_DOCKER_TEST_IMAGE`, run by the CI `docker` job).
- `runners/k8s` starts a worker as a Pod (or Job, or agent-sandbox Sandbox) with `kubectl`: `render.mjs` builds the manifests, `spawn.sh` creates the workload, then a token Secret owned by it (the token is only on kubectl's stdin), and prints `BAND_MACHINE_HANDLE=<ns>/<name>`. `destroy.sh` and `status.sh` go by the `band.worker` label. The hardening matches the docker hook (uid 65532, drop ALL, read-only root with emptyDir `/tmp` and `/work`, RuntimeDefault seccomp, no service account token), and `isolation: vm` needs `BAND_K8S_RUNTIME_CLASS`. Examples in `deploy/k8s/` (namespace, RBAC with no Secret read, hub Deployment, `check-rbac.sh`). A worker takes plain http only for loopback, so Pods need an https hub URL. `BAND_K8S_CA_CONFIGMAP` mounts a private CA for the hub. Tests: `apps/hub/tests/runner-k8s.test.ts` (stub `kubectl` through `BAND_KUBECTL_BIN`) and `runner-k8s-kind.test.ts` (real cluster, run by the CI job `k8s (kind)`, skipped without `BAND_K8S_TEST_IMAGE` and `BAND_K8S_TEST_KUBECONFIG`). Not done yet: the reaper (3.7). The idle and ephemeral lifecycle is below.
- `runners/hetzner` and `runners/contabo` (`spawn`, `destroy`, `status`, plan step 3.8) create a VM per request. Both render one cloud-init (`runners/_shared/cloud-init.mjs`) that starts `band-worker --ephemeral` under systemd with `ExecStopPost=+poweroff`, and print `BAND_MACHINE_HANDLE`. Contabo is monthly, so its default is a reuse pool (reinstall an idle instance). Provider credentials come from the runner's own env. Tests: `apps/hub/tests/runner-vm-hooks.test.ts` against Express stubs of both APIs (`HCLOUD_API_URL`, `CONTABO_AUTH_URL`, `CONTABO_API_URL`). Guide: `docs/runner-hooks.md`.
- Snapshots (plan step 3.10, `docs/runner-hooks.md#snapshots`). A runner with `snapshot` and `restore` hooks (plus `snapshotDelete`, `snapshotKeep`, `snapshotTtlSec`, `snapshotTimeoutSec`) gets a machine snapshot on every sleep, after the git and session state is stored, which stays the fallback. `RunnerService.snapshotHost` runs `snapshot` with `BAND_MACHINE_HANDLE` and `BAND_WORKTREE_IDS` and reads `BAND_SNAPSHOT_ID` (and `BAND_SNAPSHOT_SIZE`) from its output into `runner_snapshots`, `RunnerService.destroyMachine` (the reaper's call) runs `destroy` once the worker is gone, and the machine, its runner and its handle come from the `runner_machines` row of the worker id, which the snapshot row points to with `machine_id`. A wake leased by the same runner runs `restore` instead of `spawn`; a failing `restore` runs `destroy` and then `spawn` in the same attempt. After a restore says hello the snapshot row has `restored_at`, and `EphemeralLifecycleService.restore` skips the git checkout for a worktree whose worktree is at its stored `baseSha`, writing only the agent sessions. The hub deletes a snapshot through `snapshot-delete` when a wake used it, a newer one replaced it, it expired or it is beyond `snapshotKeep` (`sweepSnapshots`, `BAND_SNAPSHOT_SWEEP_MS`, default 60 s). `runners.snapshots` lists them. The docker hook snapshots `/work` into an image `band-snapshot:<worker>-<time>` (a helper container, because `docker commit` skips volumes) and restores by filling a new container's `/work` volume from it. The hetzner hook uses `create_image` and creates a server from the image. The restore hooks must delete the saved `session-token`, because a worker prefers it to the bootstrap token. Tests: `apps/hub/tests/runner-snapshots.test.ts` (fake runner wrapping the `local` hook), `runner-docker-snapshot.test.ts` (real docker, skipped without `BAND_DOCKER_TEST_IMAGE`, run by the CI `docker` job) and the snapshot cases in `runner-vm-hooks.test.ts`.
