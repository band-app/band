# Architecture: subscriptions

`subscriptions.create | list | remove | events` (`apps/hub/src/server/api/subscriptions/router.ts`) are tRPC procedures, so the MCP endpoint lists them as `band_subscriptions_*`. A call carrying `x-band-chat-id` and `x-band-worktree-id` headers (an agent's `BAND_CHAT_ID` and `BAND_WORKTREE_ID`) can omit both ids. ACP chat agents get both variables; terminals get only `BAND_WORKTREE_ID`, since a terminal has no chat.

- Webhook source: `create` with `source: "webhook"` returns a token once and stores only its SHA-256 (`subscriptions.config`). `POST /api/hooks/:id` is answered before the server's auth check, takes the token in `X-Band-Webhook-Token` or `Authorization: Bearer`, and compares hashes in constant time. 404 for an unknown id, 401 for a bad token, 202 otherwise.
- Timer source: `source: "timer"` with `at` (epoch ms, one-off, forced to `maxWakeups: 1` so it removes itself after delivery) or `cron` (croner syntax, optional seconds field; it ends after `maxWakeups` fires, default 50, or at the 180-day cap). Timers are re-armed from the database in `SubscriptionService.start()`.
- GitHub source (the plugin's `SubscriptionSourceProvider` in `plugins/github/src/server/subscriptions.ts`, `webhook.ts` and `check-runs.ts`, driven by `services/subscription-source-service.ts` in the core): `create` with `source: "github"`, `repo` and exactly one of `pr` (comments, reviews, review comments, lifecycle; key `github:pr:owner/repo#N`) or `branch` (CI; key `github:ci:owner/repo@branch`, kinds `["ci"]`). `POST /api/hooks/github` is answered before auth. The core reads the secret in `BAND_GITHUB_WEBHOOK_SECRET` or `~/.band/github-webhook-secret` (`infra/subscriptions/webhook-secret.ts`, generated on the first registration, mode 0600) and the provider checks `X-Hub-Signature-256` against it in constant time, because the scheme is GitHub's; 401 for a bad or missing signature, 202 otherwise, and 404 when `github` is in `plugins.disabled`. The plugin fires `reviews.changed` for each verified delivery. Repeated `X-GitHub-Delivery` ids are dropped. A completed `check_run`, `check_suite` or `workflow_run` makes the hub fetch the commit's check runs with `gh api` (`BAND_GH_BIN`); it pages through them 100 at a time and delivers one event per commit and verdict only when no check is pending. A failure names the failed checks; with no failure, a cancelled run is reported as its own `cancelled` outcome. The first subscription for a repo registers the webhook with `gh api repos/{o}/{r}/hooks --input -` (the body, secret included, goes over stdin, never argv) when `BAND_PUBLIC_URL` or the running tunnel gives a public origin (the tunnel's `?token=` is dropped); otherwise `webhook.status` is `waiting-for-url`.
- Guards (`SubscriptionService.ingest`, `services/pushed-sha-service.ts`): without `maxWakeups` a CI subscription gets 10 and any other 50, and every subscription expires within 180 days. After a successful `worktree.gitPush` or `worktrees.gitPush`, Band records the branch head in `pushed_shas`. A `push` or PR `synchronize` event whose commit is in that table is flagged `self` and recorded with `dropped_reason = "self"`, not delivered, so an agent's own push does not wake it. A CI failure on a commit in the table is delivered as a fix trigger. A CI failure on any other commit carries `fix: false`, and the message says the commit is not Band's and must not be fixed. Comments, reviews and review comments are delivered only from `config.allowedSenders` (`create` takes `allowedSenders` with `pr`; the default is the repo owner plus the authenticated `gh api user` login, and a list replaces it, ignoring case). Other senders' events are recorded with `dropped_reason = "sender"`.

- Polling fallback (`services/subscription-poll-service.ts`, with the GraphQL query and parsing in `plugins/github/src/server/pr-activity.ts`): the branch-status poller calls `poll()` on its CI ticks, so it follows the activity cadence and needs the GitHub plugin enabled. It serves GitHub subscriptions whose repo has no registered webhook (`webhook.status` is `waiting-for-url` or `failed`). When the hub has a public URL by then, it first tries to register the webhook, and a repo with any `registered` subscription is no longer polled. A PR subscription reads new comments, reviews and review comments with one GraphQL query per repo, from a cursor in `subscription_cursors` (the newest `createdAt` seen, starting at the subscription's creation time). A branch subscription reads the head commit's check runs and delivers through the same `aggregateChecks` as the webhook path. The provider splits a repo's subscriptions into units (`pollUnits`) and reads one (`poll`) from each subscription's cursor; the core keeps the cursors, the budget and the backoff. One poll makes at most 6 `gh` calls (a branch whose check pages exceed what is left waits for the next poll), taking turns across repos and branches, and a source that fails is skipped for 2, 4, 8 and then 16 polls.
