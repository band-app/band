# Architecture: Web Server vs Terminal Daemon

Terminal PTYs do not live in the web server. They live in the **terminal daemon** (`apps/hub/terminal-daemon.ts`, bundled to `dist/terminal-daemon.mjs`), a detached process the server launches on the first terminal spawn, so shells survive a server restart (desktop relaunch, auto-update, `pnpm dev` reload, crash). The restarted server reattaches to the same shells, and the browser replays their screens over the unchanged `/terminal` WebSocket.

- `TerminalService` talks to a `TerminalBackend` (`packages/host-local/src/terminals/terminal-backend.ts`). `DaemonTerminalBackend` is the default. `InProcessTerminalBackend` is used on Windows, when `BAND_TERMINAL_DAEMON=0`, and as a fallback when the daemon cannot start; its terminals die with the server. Nothing outside `packages/host-local/src/terminals/` touches node-pty.
- The daemon knows nothing about worktrees, layouts or events. It runs a `TerminalPool` behind a Unix socket (NDJSON, token hello, separate control and stream connections). The wire protocol is in `packages/host-local/src/terminals/daemon/protocol.ts`; bump `PROTOCOL_VERSION` on any change to it that an older peer would misread. A new `ControlNotify` that is safe to ignore (like `hold` / `release`) is the one exception, because a daemon drops notifies it doesn't know and new sessions only start on a daemon of the server's own build.
- Runtime files live in `~/.band/run/` (mode 0700): `terminal-daemon-v3.sock`, `.token`, `.pid`, and `terminal-daemon.log`. If the socket path would exceed the 104-byte `sun_path` limit, the socket moves to `/tmp/band-<uid>/`, named by a hash of the run dir.
- Socket publishing follows orca's endpoint-ownership rules (see the header of `daemon/endpoint.ts`): never unlink a socket you did not create, only a refused or missing connect proves a daemon dead, and a daemon never removes its endpoint on shutdown.
- Output to a server shares one stream socket per server. When that socket holds more than 128 KB, the daemon pauses the PTY of each session that has sent over 4,096 characters since the socket was last empty, and resumes them on `drain`. Floods stop at the shell instead of burying other terminals' echo, and a server is only dropped (at 64 MB unread) when it stops reading entirely.
- Output to a browser is parse-acknowledged (ported from orca). The browser attaches with `flow: true` and sends `{ type: "ack", bytes }` once xterm has parsed output; `packages/worktree-ops/src/output-flow.ts` holds the PTY while more than 256 KB is unacknowledged and releases it below 32 KB, through `TerminalAttachment.setOutputHeld` (in-process: `TerminalPool.holdOutput`; daemon: the `hold` / `release` notifies, one per server). A client that never opted in is paced on `ws.bufferedAmount`, one that acknowledges nothing for 5 s is written off, and a terminal nobody can see (parked, or in a hidden page) acknowledges on receipt so it never pauses a PTY another device is watching. In the browser, `terminal-output-queue.ts` drains visible output in 16 KB slices with at most 128 KB unparsed in xterm. It writes visible output up to the last DEC 2026 end marker and holds only an unfinished frame's tail until its end arrives (or 100 ms, or 64 KB): xterm skips any render while a frame is open, so a TUI redrawing back to back, whose frames arrive as several 1 KB messages, otherwise painted only on xterm's 1 s timeout. Panes get `CLAUDE_CODE_FORCE_SYNC_OUTPUT=1`, without which Claude Code, not recognising the terminal from `TERM_PROGRAM`, repaints the whole screen on every wheel tick instead of scrolling a DECSTBM region.
- Daemon kit (`packages/host-local/src/daemon-kit/`): the parts of a daemon that host nothing in particular. `endpoint.ts` (endpoint ownership), `protocol.ts` (NDJSON framing, hello, run-dir file names, exit codes), `private-files.ts`, `connection.ts` (client sockets, handshake, `retireDaemon`), `launch.ts` and `exit-records.ts`. The terminal daemon passes its own name, `PROTOCOL_VERSION` and exit-code text. A Biome rule bans node-pty, xterm and `terminals/` imports in the kit.
- Server shutdown only disconnects. A session ends when its tab is closed, its worktree is deleted (or found deleted at boot), or its shell exits.
- The daemon exits on its own, following orca's daemon: when it has no shells, no spawn in flight and no connection, the moment its last server disconnects (or 2 minutes after launch if none ever connects). If its socket is replaced or removed, it drains: no new sessions, existing shells keep working over already-open connections, and it exits when the last one ends. If `~/.band/run` disappears, it kills its shells and exits.
- New sessions only start on a daemon of the server's own build (issue #652). The build ID is the size and mtime of the daemon entry file. When the endpoint is served by a daemon of another build, or by one whose entry file (recorded in its pid file) no longer exists, the server's first spawn launches a daemon of its own build with `--supersede <dev>:<ino>`. That daemon hardlinks the old socket to a private retired name (`.r<tag>` beside the socket, plus `terminal-daemon-v3.retired-<tag>.token` and `.pid` in the run dir), then renames itself over the endpoint. The old daemon sees its endpoint lost and drains. Servers keep reattaching its shells, including after a restart, through the retired name. It exits when its last shell ends, and the daemon that created the retired names removes them then. A daemon stays alive while it holds retired names.
- **Node-pty loads eagerly at daemon startup**, before the socket binds (`preloadNodePty()` in `packages/host-local/src/terminals/node-pty-loader.ts`, called from `runDaemon`). Node's ESM loader caches a failed CommonJS evaluation for the life of the process, so a daemon that served spawn requests after a failed load would fail every one of them forever, even once the underlying problem is gone — failing fast instead (exit code `EXIT_NODE_PTY_UNAVAILABLE`, `protocol.ts`) means the next spawn launches a fresh process with a fresh module cache. `DaemonTerminalBackend.openConnection` retries a failed launch once before giving up and falling back to `InProcessTerminalBackend` (`TerminalService.spawn`'s existing behavior, unchanged). A `pty.spawn` failure during a normal spawn (missing native module, resource exhaustion) is turned into a short human message by `packages/host-local/src/terminals/pty-error-hints.ts` before it reaches the pane; the raw error stays in the daemon log.
- **"Restart the terminal service"** (Settings > Terminal, `band terminals restart-daemon`, `terminal.restartDaemon`) SIGTERMs the current-build daemon directly and lets its own shutdown path (kill every PTY, exit) do the work — no new wire message. Losing the connection already makes `DaemonTerminalBackend.handleDisconnect` report every session as exited, the same path a crash takes, so panes show "exited" and can be reopened. Only ever signals the current-build daemon; a daemon of another build, or one already draining after being superseded, is untouched and keeps its shells.
- **Cold restore**: each daemon-hosted terminal periodically checkpoints its scrollback (serialized ANSI, via the existing headless-mirror/`serialize()` machinery) and cwd to `~/.band/terminal-history/<encoded terminalId>/` (`packages/host-local/src/terminals/terminal-history.ts`), bounded in size and pruned only by an explicit `kill` / `killWorktree` (the tab or worktree is actually closed or deleted). Any other way a PTY goes away — a natural shell exit, a daemon crash, or the `killAll` a restart triggers — leaves the checkpoint in place, so the next `spawn()` for that terminalId writes it into the fresh session's scrollback/cwd before the client's first snapshot. If the checkpoint's saved command was a plain `claude` invocation, `packages/host-local/src/terminals/claude-resume.ts` looks for the newest Claude Code session transcript under `~/.claude/projects/<cwd slug>/` and relaunches with `--resume <id>` instead of just restoring scrollback; other agents/commands are not auto-relaunched.
- Tests: the server helpers' `close()` stops the home's daemon (`tests/helpers/terminal-daemon.ts`), because it is detached and escapes the process-group kill. Pass `{ keepTerminalDaemon: true }`, or use the e2e fixture's `restart()`, to model a restart.
